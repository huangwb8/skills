# auto-test-project 改进计划

**测试 ID**: v202601141945
**检查时间**: 2026-01-14 19:45
**改进来源**: auto-test-skill v2.1.0 的优秀策略

---

## 改进概述

本文档记录将 `auto-test-skill` 的优秀策略迁移到 `auto-test-project` 的改进计划。

**核心改进点**：
1. **强制数量要求**：每轮 A 轮至少 10 个问题，B 轮至少 10-20 个建议
2. **建设性建议标准**：新增 `references/CONSTRUCTIVE_SUGGESTION_GUIDELINES.md`
3. **问题挖掘技巧**：新增 `references/ISSUE_DISCOVERY_TECHNIQUES.md`
4. **反例库**：新增 `references/ANTI_PATTERNS_LIBRARY.md`
5. **强化 B 轮修复要求**：明确 P0/P1 修复率要求

---

## 问题分析

### 当前 auto-test-project 的不足

| 维度 | auto-test-skill | auto-test-project | 差距 |
|------|-----------------|-------------------|------|
| **数量要求** | ✅ 每轮至少 10 个，鼓励 15-20 个 | ❌ 无明确数量要求 | 高 |
| **建设性标准** | ✅ 详细的 `CONSTRUCTIVE_SUGGESTION_GUIDELINES.md` | ❌ 无 | 高 |
| **问题挖掘技巧** | ✅ 10 大类技巧库 | ❌ 无 | 高 |
| **反例库** | ✅ 七大原则反例库 | ❌ 无 | 中 |
| **B 轮修复要求** | ✅ 明确 P0 100%、P1 80% 修复率 | ⚠️ 仅提及"针对性修复" | 中 |

### 具体问题

#### 问题 1: 无明确的数量要求

**位置**: `auto-test-project/SKILL.md` 第 A.2 节

**当前表现**:
- 只说"写出可执行计划"，无最低数量要求
- 容易导致 AI "偷懒"，只列出 3-5 个表面问题

**影响**:
- 测试深度不足
- 遗留潜在问题
- 多轮迭代的价值降低

**修复建议**:
参考 `auto-test-skill` 的做法，在 SKILL.md 和 config.yaml 中明确数量要求：
- 每轮 A 轮至少 10 个问题（P0 + P1 + P2）
- 鼓励达到 15-20 个问题
- B 轮至少 10-20 个建议

**优先级**: P0

---

#### 问题 2: 缺少建设性建议标准

**位置**: `auto-test-project/references/` 目录

**当前表现**:
- 无 `CONSTRUCTIVE_SUGGESTION_GUIDELINES.md`
- AI 不清楚"什么是建设性建议"
- 容易产出"建议增加更多日志"这类泛泛而谈的建议

**影响**:
- 建议质量参差不齐
- 可执行性差
- 用户需要二次澄清

**修复建议**:
1. 从 `auto-test-skill` 复制 `CONSTRUCTIVE_SUGGESTION_GUIDELINES.md`
2. 在 SKILL.md 中引用该文档
3. 在 config.yaml 中添加 `constructive_suggestion_required: true`

**优先级**: P0

---

#### 问题 3: 缺少问题挖掘技巧库

**位置**: `auto-test-project/references/` 目录

**当前表现**:
- 无 `ISSUE_DISCOVERY_TECHNIQUES.md`
- AI 发现问题的方式随机、不系统
- 容易停留在表面问题

**影响**:
- 问题挖掘不深入
- 同类问题反复出现
- 测试效率低

**修复建议**:
1. 从 `auto-test-skill` 复制 `ISSUE_DISCOVERY_TECHNIQUES.md`
2. 在 SKILL.md 中强调"每轮使用 3-5 个技巧组合"
3. 在 A 轮计划模板中添加"使用的挖掘技巧"字段

**优先级**: P0

---

#### 问题 4: 缺少反例库

**位置**: `auto-test-project/references/` 目录

**当前表现**:
- 无 `ANTI_PATTERNS_LIBRARY.md`
- AI 需要每次"记住"常见反例
- 容易遗漏经典问题

**影响**:
- 重复发现相同类型的问题
- 新轮次无法利用历史经验
- 学习曲线陡峭

**修复建议**:
1. 从 `auto-test-skill` 复制 `ANTI_PATTERNS_LIBRARY.md`
2. 将七大原则反例扩展为"项目级七大原则"版本
3. 添加项目级特有的反例（如跨模块接口不一致）

**优先级**: P1

---

#### 问题 5: B 轮修复要求不够明确

**位置**: `auto-test-project/SKILL.md` 第 B.2 节

**当前表现**:
- 只说"对 P0/P1 进行针对性修复并验证"
- 无明确的修复率要求
- 无"遗留问题"处理规范

**影响**:
- 修复标准不统一
- 可能遗漏关键问题
- 验收标准模糊

**修复建议**:
参考 `auto-test-skill` 的做法，明确：
- B 轮发现的 **所有 P0 问题必须修复**（100%）
- B 轮发现的 **所有 P1 问题必须修复或有明确的"不修复"理由**
- 每个修复必须有验证证据
- 修复后必须更新 `CHANGELOG.md`

**优先级**: P1

---

#### 问题 6: 完成条件缺少数量要求

**位置**: `auto-test-project/SKILL.md` "完成条件"节

**当前表现**:
- 无"每轮平均问题数量 ≥ 10 个"的要求
- 无"建议数量达标"的验收标准

**影响**:
- 可能提前结束测试
- 测试质量无法保证

**修复建议**:
在完成条件中添加：
- [ ] 每轮 A 轮平均问题数量 ≥ 10 个（P0 + P1 + P2 总和）
- [ ] B 轮建议数量 ≥ 10 个

**优先级**: P1

### 阶段 2: 更新 SKILL.md（P0）

#### 2.1 添加数量要求

**位置**: SKILL.md 第 A.2 节

**添加内容**:
```markdown
**数量要求**（强制）：
- 每轮至少发现 10 个问题（P0 + P1 + P2 总和）
- 鼓励达到 15-20 个问题（深入挖掘）
- 如首轮无明确问题列表，必须先进行"静态检查 + 一致性检查 + 逻辑推演"再列出问题清单
```

---

#### 2.2 添加建设性要求

**位置**: SKILL.md 第 A.2 节

**添加内容**:
```markdown
**建设性**：每条建议必须可执行、有证据、有价值、可验证（详见 `references/CONSTRUCTIVE_SUGGESTION_GUIDELINES.md`）
```

---

#### 2.3 添加挖掘技巧要求

**位置**: SKILL.md 第 A.2 节

**添加内容**:
```markdown
**问题挖掘技巧**：`references/ISSUE_DISCOVERY_TECHNIQUES.md` ⚠️ 强烈建议：每轮使用 3-5 个技巧组合
```

---

#### 2.4 强化 B 轮修复要求

**位置**: SKILL.md 第 B.2 节

**替换内容**:
```markdown
⚠️ **强制修复要求**：
- B 轮发现的 **所有 P0 问题必须修复**
- B 轮发现的 **所有 P1 问题必须修复或有明确的"不修复"理由**
- 每个修复必须有验证证据（命令输出、文件对比、测试结果）
- 修复后必须更新 `CHANGELOG.md`

**验证报告必须包含**：
1. 修复清单：每个 P0/P1 问题的修复方案和证据
2. 遗留问题：未修复的 P2 问题及原因
3. 变更记录：更新目标项目的 CHANGELOG.md

**完成条件**：
- [ ] P0 问题修复率 = 100%
- [ ] P1 问题修复率 ≥ 80%（或 100%，取决于问题严重性）
- [ ] 所有修复都有可复现证据
```

---

#### 2.5 更新完成条件

**位置**: SKILL.md "完成条件"节

**添加内容**:
```markdown
- [ ] 每轮 A 轮平均问题数量 ≥ 10 个（P0 + P1 + P2 总和）
- [ ] B 轮建议数量 ≥ 10 个
- [ ] B 轮 P0 问题修复率 = 100%，P1 问题修复率 ≥ 80%
```

---

### 阶段 3: 更新 config.yaml（P1）

#### 3.1 添加数量要求配置

**位置**: config.yaml `test_rounds` 节

**添加内容**:
```yaml
test_rounds:
  # A轮每轮必须提出的最小建议数量（P0 + P1 + P2 总和）
  min_suggestions_per_round: 10
  # A轮建议数量目标范围
  target_suggestions_range: [15, 20]
```

---

#### 3.2 添加 B 轮要求配置

**位置**: config.yaml `b_round_check` 节

**添加内容**:
```yaml
b_round_check:
  # B轮必须提出的最小建议数量（P0 + P1 + P2 总和）
  min_suggestions: 10
  # 建议数量目标范围
  target_suggestions_range: [15, 20]
  # 建设性建议是否需要满足标准
  constructive_suggestion_required: true
  # P0问题修复率要求（百分比）
  p0_fix_rate_required: 100
  # P1问题修复率要求（百分比）
  p1_fix_rate_required: 80
```
