# 建设性建议标准（项目级）

**文档版本**：v1.0.0
**创建时间**：2026-01-14
**用途**：为 auto-test-project 提供"什么是建设性建议"的判断标准

---

## 核心定义

**建设性建议** = 具体可执行的改进方案，包含明确的修复路径和验证方法。

**项目级特点**：
- 涉及跨模块、跨文件的分析
- 需要考虑模块间依赖关系
- 修复可能影响多个模块

---

## ✅ 建设性建议的特征

### 1. 可执行

每条建议必须包含具体的修复方案，不是"应该改进XX"这种泛泛而谈。

**示例**：
- ❌ "建议增加更多日志"
- ✅ "在 `module_a/src/processor.py` 第 42 行的 `except` 块中，记录具体的异常类型和堆栈信息"

### 2. 有证据

每条建议必须基于具体文件/行号/代码，不是凭空猜测。

**示例**：
- ❌ "建议优化文档结构"
- ✅ "CLAUDE.md 第 30 行的描述与 `module_b/config.yaml` 第 15 行不一致，应统一为'XXX'"

### 3. 有价值

修复后能带来明显的质量提升（安全性/可维护性/用户体验）。

**示例**：
- ❌ "建议优化注释风格"（价值低）
- ✅ "建议增加跨模块接口一致性检查"（可维护性提升）

### 4. 可验证

每条建议必须包含明确的验证方法，确认修复成功。

**示例**：
- ❌ "建议修复配置加载逻辑"
- ✅ "建议修复配置加载逻辑：验证方法 → 在项目根目录运行空配置文件测试，确认有默认值回退"

---

## ❌ 非建设性建议的例子

### 类型 1：泛泛而谈

| ❌ 泛泛建议 | ✅ 建设性建议 |
|------------|--------------|
| "建议增加更多日志" | "在 `module_a/scripts/foo.py` 第 42 行的 `except` 块中，记录异常类型和堆栈" |
| "建议优化文档" | "CLAUDE.md 第 30 行与 `module_b/config.yaml` 第 15 行不一致，应统一为..." |
| "建议增强测试" | "缺少跨模块集成测试，应在 `tests/integration/` 中增加验证用例" |
| "建议改进错误处理" | "第 88 行的 `except` 块捕获了所有异常但未记录，应细化为具体异常类型" |

### 类型 2：无具体位置

| ❌ 无位置建议 | ✅ 建设性建议 |
|--------------|--------------|
| "某个配置项没有说明" | "`module_a/config.yaml` 第 23 行的 `timeout` 项缺少单位说明，应补充为'秒'" |
| "代码中有重复逻辑" | "`module_a/src/bar.py` 第 105-110 行与 `module_b/src/util.py` 第 45-50 行完全相同，应提取到共享模块" |
| "示例无法运行" | "README.md 第 18 行的示例命令缺少必需的 `--project-root` 参数" |

### 类型 3：价值不明确

| ❌ 价值不明确 | ✅ 建设性建议 |
|--------------|--------------|
| "建议统一注释风格" | "建议统一注释风格：当前混用 `#` 和 `//`，导致某些编辑器语法高亮失效" |
| "建议优化变量命名" | "建议优化变量命名：`tmp1`/`tmp2` 无法表达用途，改为 `input_path`/`output_path`" |
| "建议重构函数" | "建议重构 `process()` 函数：当前 200 行，包含 3 层嵌套，难以测试" |

### 类型 4：无验证方法

| ❌ 无验证方法 | ✅ 建设性建议 |
|--------------|--------------|
| "建议修复路径验证" | "建议修复路径验证：验证方法 → 构造输入 `../../etc/passwd`，确认被拒绝" |
| "建议增加默认值" | "建议增加默认值：验证方法 → 删除配置项，确认仍能运行" |
| "建议更新文档" | "建议更新文档：验证方法 → 按照文档步骤执行，确认能成功运行" |

## 建设性建议的"黄金公式"

```
位置 + 问题现象 + 影响分析 + 涉及模块 + 具体修复方案 + 验证方法
```

### 完整示例（项目级）

**位置**：`module_a/scripts/validator.py:45-48`

**问题现象**：
```python
# 当前代码
if path.startswith("../"):
    raise ValueError("Invalid path")
```

**影响分析**：
- 只检查 `../` 前缀，无法防御 `..\\`（Windows）、`./../`、绝对路径绕过等攻击向量
- 存在路径遍历漏洞风险
- **涉及模块**：`module_a`（入口）、`module_b`（文件处理）、共享工具库

**具体修复方案**：
```python
# 修复后代码（在共享工具库中）
import os

def validate_path(path, base_dir):
    """验证路径在 base_dir 内"""
    resolved = os.path.realpath(path)
    base_resolved = os.path.realpath(base_dir)

    if not resolved.startswith(base_resolved):
        raise ValueError(f"Path {path} is outside base directory")

    return resolved
```

**跨模块影响**：
- `module_a` 需要调用共享工具库的 `validate_path()`
- `module_b` 需要替换本地路径验证逻辑

**验证方法**：
1. 构造恶意输入 `../../etc/passwd`，确认被拒绝
2. 构造绕过输入 `./../../etc/passwd`，确认被拒绝
3. 构造合法输入 `data/test.csv`，确认通过验证
4. **跨模块测试**：验证 `module_a` 和 `module_b` 都使用相同的路径验证逻辑

## 建议质量自检清单

在提交建议前，确认每条建议都满足：

- [ ] **包含具体位置**：文件名 + 行号（如 `module_a/SKILL.md:30`）
- [ ] **包含修复方案**：不是"建议"而是"改为..."
- [ ] **包含验证方法**：如何确认修复成功
- [ ] **有明确价值**：能提升安全性/可维护性/用户体验
- [ ] **可独立执行**：不需要额外的上下文信息
- [ ] **考虑跨模块影响**：说明修复会影响哪些模块

## 常见反模式

### 反模式 1："应该"式建议

❌ "应该增加错误处理"
✅ "第 42 行缺少对 `FileNotFoundError` 的处理，应增加 `try-except` 块"

### 反模式 2："问题列表"式建议

❌ "问题：1) 无日志 2) 无测试 3) 无文档"
✅ 拆分为 3 条独立建议，每条都有位置和修复方案

### 反模式 3："模糊优化"式建议

❌ "建议优化性能"
✅ "第 88 行的循环嵌套复杂度为 O(n²)，建议改用字典降低到 O(n)"

### 反模式 4："假设用户会"式建议

❌ "建议用户先创建目录"
✅ "脚本应自动创建目录，而非假设用户已创建（见 `scripts/foo.py:55`）"

## 不同优先级的建议标准

### P0 建议（必须修复）

**特征**：
- 阻塞性问题：不修复就无法继续
- 安全风险：路径遍历、命令注入、敏感信息泄露
- 核心功能缺失：缺少关键功能、无法完成基本任务
- **跨模块阻塞**：模块间接口不兼容，导致项目无法运行

**示例**：
- "存在路径遍历漏洞（`module_a/scripts/validator.py:45`），用户可访问任意文件"
- "模块 A 和模块 B 的接口定义不一致，导致集成失败"
- "项目缺少必需的配置项 `project_root`，导致脚本无法启动"

### P1 建议（强烈建议）

**特征**：
- 重要优化：显著提升质量/安全性/可维护性
- 测试覆盖不足：核心功能缺少测试
- 文档缺失：用户无法理解如何使用
- **跨模块一致性**：模块间命名、接口、配置不一致

**示例**：
- "缺少跨模块集成测试，应在 `tests/integration/` 中增加验证用例"
- "CLAUDE.md 第 30 行缺少步骤 2 的详细说明，用户无法正确执行"
- "模块 A 和模块 B 使用不同的日志格式，应统一为共享日志配置"

### P2 建议（可选）

**特征**：
- 改进体验：提升可用性、易读性
- 完善细节：注释、代码风格、命名
- 后续迭代：不影响当前使用的改进

**示例**：
- "变量名 `tmp1`/`tmp2` 不够直观（`module_a/src/bar.py:105`），建议改为 `input_path`/`output_path`"
- "建议统一注释风格：当前混用 `#` 和 `//`（`module_a/scripts/*.py`）"
- "建议将重复的配置合并到项目级 config.yaml"

## 数量要求

根据 auto-test-project 的要求：

- **每轮 A 轮**：至少 10 个问题（P0 + P1 + P2 总和），鼓励 15-20 个
- **B 轮检查**：至少 10-20 个建设性建议

**建议分布**（参考）：
- P0：2-4 个（如无严重问题，可少于 2 个）
- P1：4-8 个（重点）
- P2：4-8 个（锦上添花）

**项目级特点**：
- 更多的 P1 问题（跨模块一致性、集成测试）
- 更少的 P2 问题（项目级优化通常更重要）

---

## 本轮建议质量检查

在提交建议前，回答以下问题：

1. **位置明确吗？** 每条建议都包含文件名和行号
2. **方案具体吗？** 每条建议都描述了"改为..."而非"建议..."
3. **可验证吗？** 每条建议都有明确的验证方法
4. **有价值吗？** 每条建议都能带来明显的质量提升
5. **数量达标吗？** 总数 ≥ 10，且 P0+P1 占比 ≥ 60%
6. **考虑跨模块影响吗？** 涉及多模块的建议是否说明了影响范围

---

## 项目级特有注意事项

### 1. 跨模块依赖

在提出修复建议时，必须考虑：
- 修复模块 A 是否会影响模块 B？
- 是否需要同步更新多个模块？
- 是否需要更新项目级文档（CLAUDE.md 等）？

### 2. 项目级一致性

在提出建议时，优先考虑：
- 模块间接口一致性
- 配置文件一致性
- 命名规范一致性
- 日志格式一致性

### 3. 测试覆盖

在提出建议时，优先考虑：
- 跨模块集成测试
- 端到端测试
- 回归测试
