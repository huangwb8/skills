# 问题挖掘技巧（项目级）

**文档版本**：v1.0.0
**创建时间**：2026-01-14
**用途**：为 auto-test-project 提供"如何深入挖掘问题"的技巧库

---

## 核心思想

**问题挖掘** = 系统化的质疑 + 多角度的验证 + 边缘情况的探索

本文档提供 10 大类问题挖掘技巧，帮助 AI 在每轮 A 轮中发现 10-20 个建设性问题。

**项目级特点**：
- 跨模块分析：不仅看单个模块，还要看模块间关系
- 项目级一致性：检查整个项目的命名、配置、接口一致性
- 集成测试：验证模块协同工作是否正常

---

## 技巧 1: 跨模块交叉验证

### 方法

检查 A 文件/模块引用的内容，在 B 文件/模块中是否存在/一致。

### 检查清单

- [ ] CLAUDE.md 引用的配置项，在各个模块的 config.yaml 中是否存在？
- [ ] README.md 中的示例，与实际项目结构是否一致？
- [ ] 脚本注释中的"路径"，与实际目录结构是否匹配？
- [ ] 文档中引用的模板文件（`references/XXX.md`），实际是否存在？
- [ ] 模块 A 的接口定义，与模块 B 的调用是否一致？

### 典型发现

```
问题：CLAUDE.md 第 30 行说"参考 module_a.config.output_dir"，但实际是 "module_a.config.output.directory"
位置：CLAUDE.md:30, module_a/config.yaml:15
优先级：P1
涉及模块：module_a（配置定义）、项目文档（文档引用）
修复：统一为 "output.directory"
```

## 技巧 2: 逻辑推演找漏洞

### 方法

问自己："如果 X 发生，会怎样？"（X 是异常情况）

### 检查清单

- [ ] 如果用户跳过步骤 1，直接执行步骤 2 会怎样？
- [ ] 如果某个模块的 config.yaml 中的参数是空值会怎样？
- [ ] 如果用户输入的路径包含空格或特殊字符会怎样？
- [ ] 如果网络请求失败会怎样？有重试机制吗？
- [ ] 如果某个模块的输入文件是空的会怎样？
- [ ] 如果模块 A 的输出格式变化，模块 B 能正确处理吗？

### 典型发现

```
问题：如果 module_a/config.timeout 为空，整个项目初始化会崩溃（未设置默认值）
位置：module_a/scripts/init.py:42
优先级：P0
涉及模块：module_a（初始化）、项目根（启动脚本）
修复：增加默认值 timeout = config.get("timeout", 30)
```

## 技巧 3: 文档"读心术"

### 方法

找出文档中的"模糊词"和"未验证的假设"

### 关键词搜索

搜索以下词汇，发现潜在问题：
- `应该` → 通常意味着"实际上没做"
- `会` → 通常意味着"假设会发生"
- `自动` → 通常意味着"没有手动验证"
- `例如`、`如` → 检查示例是否真的可运行
- `详见`、`参考` → 检查被引用的文件是否存在
- `用户` → 检查是否假设用户会做某事
- `模块` → 检查是否假设模块存在

### 典型发现

```
问题："用户应先创建输出目录" → 假设用户会手动创建，实际不会
位置：CLAUDE.md:55
优先级：P1
涉及模块：所有模块（共享输出目录）
修复：项目级启动脚本应自动创建目录（见 scripts/init.py:12）
```

## 技巧 4: 代码/文档"模式匹配"

### 方法

使用 Grep 工具搜索特定模式，发现隐藏问题

### 搜索模式

| 模式 | 目的 | 典型问题 |
|------|------|----------|
| `TODO`、`FIXME`、`HACK` | 未完成的技术债 | 功能未完成、临时方案未清理 |
| `print(`、`console.log` | 未清理的调试代码 | 生产代码包含调试输出 |
| `#` 注释中的"临时"、"测试" | 未清理的临时内容 | 标记为临时的代码仍在使用 |
| `except:` (无异常类型) | 过于宽泛的异常捕获 | 隐藏真实错误、难以调试 |
| `os.system`、`subprocess.call` | 潜在的命令注入风险 | 未验证用户输入 |
| `pass` | 空的实现 | 函数/类未实现 |
| `import os.path` | 路径处理方式不一致 | 不同模块使用不同的路径处理方式 |

### 典型发现

```
问题：module_a/src/processor.py:88 包含 `except:` 捕获所有异常，隐藏真实错误
位置：module_a/src/processor.py:88
优先级：P1
涉及模块：module_a（错误处理）
修复：细化为具体异常类型（如 FileNotFoundError, ValueError）
```

## 技巧 5: "挑刺"清单

### 方法

系统化地检查每个"应该有"的东西是否真的存在

### 通用清单

- [ ] 每个配置项都有说明吗？
- [ ] 每个示例都能运行吗？
- [ ] 每个引用的文件都存在吗？
- [ ] 每个步骤都有验证方法吗？
- [ ] 每个错误都有明确的错误提示吗？
- [ ] 每个函数都有 docstring 吗？
- [ ] 每个脚本都有 `if __name__ == "__main__"` 保护吗？

### 项目级专项清单

- [ ] 每个模块都有独立的 config.yaml 吗？
- [ ] 模块间的接口定义一致吗？
- [ ] 项目级文档（CLAUDE.md）与各模块文档一致吗？
- [ ] 有跨模块集成测试吗？
- [ ] 有项目级启动脚本吗？
- [ ] 有项目级 CHANGELOG.md 吗？

### 典型发现

```
问题：module_a/config.yaml 第 23 行的 `retry_delay` 配置项在文档中无说明
位置：module_a/config.yaml:23
优先级：P2
涉及模块：module_a（配置管理）
修复：在 config.yaml 中增加注释说明用途和默认值
```

## 技巧 6: 边缘情况压力测试

### 方法

构造极端输入，验证项目的鲁棒性

### 测试场景

| 输入类型 | 测试值 | 预期行为 |
|----------|--------|----------|
| **路径** | `../../etc/passwd` | 被拒绝（路径遍历防御） |
| **路径** | `path with spaces` | 正常处理（路径规范化） |
| **路径** | 空字符串 `""` | 有明确错误提示 |
| **配置** | 空文件 `{}` | 使用默认值 |
| **配置** | 无效值（如 `timeout: -1`） | 有明确错误提示 |
| **输入** | 超大文件（>1GB） | 有进度提示或分块处理 |
| **输入** | 空文件 | 有明确错误提示 |
| **输入** | 特殊字符（`\n`, `\0`） | 正确转义或拒绝 |

### 项目级测试

| 场景 | 测试值 | 预期行为 |
|------|--------|----------|
| **模块依赖** | 模块 A 缺失 | 有明确错误提示 |
| **接口不兼容** | 模块 A 接口变化 | 模块 B 能检测并报错 |
| **配置冲突** | 模块 A 和 B 配置冲突 | 启动时检测并报错 |
| **循环依赖** | 模块 A 依赖 B，B 依赖 A | 启动时检测并报错 |

### 典型发现

```
问题：路径验证只检查 `../` 前缀，无法防御 `./../` 绕过
位置：module_a/scripts/validator.py:45
优先级：P0
涉及模块：module_a（路径验证）、module_b（文件处理）
修复：使用 os.path.realpath() 规范化后再验证
```

## 技巧 7: "自我质疑"法

### 方法

对每个设计决策问："真的需要吗？有更简单的方式吗？"

### 质疑清单

- [ ] 这个配置项真的需要可配置吗？还是可以硬编码？
- [ ] 这个函数/类真的需要抽象吗？还是可以简化？
- [ ] 这个步骤真的需要用户手动执行吗？还是可以自动化？
- [ ] 这个检查真的需要吗？还是过度防御？
- [ ] 这个文档真的需要单独文件吗？还是可以合并？
- [ ] 这个模块真的需要独立吗？还是可以合并到其他模块？
- [ ] 这个项目级配置真的需要吗？还是可以模块级配置？

### 典型发现

```
问题：output_format 配置项只有 "json" 一个有效值，过度设计
位置：module_a/config.yaml:30
优先级：P2
涉及模块：module_a（配置管理）
修复：移除配置项，直接硬编码为 "json"
```

## 技巧 8: 安全性扫描

### 方法

系统性检查常见安全漏洞

### 扫描清单

- [ ] **路径遍历**：用户输入的路径是否验证？
- [ ] **命令注入**：用户输入是否直接用于系统命令？
- [ ] **敏感信息泄露**：日志/错误中是否包含密钥、密码？
- [ ] **不安全的反序列化**：对不可信数据直接反序列化？
- [ ] **硬编码密钥**：API 密钥、密码是否写在代码中？
- [ ] **跨模块安全**：模块间通信是否安全？

### 典型发现

```
问题：用户输入直接用于 os.system，存在命令注入风险
位置：module_a/scripts/runner.py:67
优先级：P0
涉及模块：module_a（命令执行）、项目根（启动脚本）
修复：使用 subprocess.run 与参数化参数
```

## 技巧 9: 用户体验（UX）审查

### 方法

模拟真实用户，评估使用体验

### 评估维度

- [ ] **第一印象**：新用户能在 5 分钟内理解项目结构吗？
- [ ] **错误恢复**：出错时，文档是否告诉用户如何恢复？
- [ ] **反馈及时**：长时间操作是否有进度提示？
- [ ] **错误友好**：错误信息是否告诉用户具体问题和解决方法？
- [ ] **可预测性**：用户能预期每一步的结果吗？
- [ ] **模块发现**：用户能快速找到需要修改的模块吗？

### 典型发现

```
问题：错误信息 "Error: failed" 无法告诉用户具体问题
位置：module_a/scripts/loader.py:52
优先级：P1
涉及模块：module_a（错误处理）
修复：改为 "Error: failed to load module_a/config.yaml: file not found"
```

## 技巧 10: "如果我是恶意用户"测试

### 方法

站在攻击者视角，尝试破坏项目

### 攻击场景

1. **路径遍历攻击**：输入 `../../etc/passwd`
2. **命令注入攻击**：输入 `; rm -rf /`
3. **配置注入**：输入恶意 YAML（如利用 YAML 解析器漏洞）
4. **资源耗尽**：输入超大文件（>1GB）
5. **并发竞态**：同时修改配置文件
6. **符号链接攻击**：创建符号链接到敏感文件
7. **模块污染**：修改模块输出，影响下游模块

### 典型发现

```
问题：未验证符号链接，用户可能通过 symlink 读取任意文件
位置：module_a/scripts/reader.py:34
优先级：P0
涉及模块：module_a（文件读取）
修复：验证解析后的路径是否在 base_dir 内
```

## 组合使用技巧

### 单轮检查策略

为达到 10-20 个问题，建议组合使用：

1. **技巧 1（跨模块交叉验证）**：3-5 个问题（项目级重点）
2. **技巧 2（逻辑推演）**：2-3 个问题
3. **技巧 3（读心术）**：2-3 个问题
4. **技巧 4（模式匹配）**：1-2 个问题
5. **技巧 6（边缘情况）**：2-3 个问题
6. **技巧 8（安全性）**：1-2 个问题（如无安全问题可跳过）
7. **技巧 9（UX 审查）**：1-2 个问题

**总计**：12-20 个问题

### 深度挖掘策略

当表面问题已发现完，需要深入挖掘时：

1. **逐模块阅读**：从第一个模块开始，逐模块质疑
2. **执行演练**：假装执行项目工作流，记录每个卡点
3. **反向思考**：从输出倒推，验证每个模块是否必要
4. **对比分析**：与类似项目对比，找出差异点

## 数量达标策略

### 策略 1: "每个技巧至少 1 个问题"

使用 10 大技巧，每技巧至少发现 1 个问题 = 10 个问题

### 策略 2: "逐模块地毯式搜索"

对每个模块使用"挑刺清单"：
- CLAUDE.md：3-5 个问题
- 模块 A：2-3 个问题
- 模块 B：2-3 个问题
- 模块 C：2-3 个问题
- 项目级配置：2-3 个问题

总计：11-17 个问题

### 策略 3: "优先级分布法"

- P0：2-4 个（安全/阻塞问题）
- P1：5-8 个（重要优化）
- P2：3-6 个（锦上添花）

总计：10-18 个问题
