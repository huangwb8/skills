## 1. 硬编码/AI 功能规划

**状态**: ✅ / ⚠️ / ❌

### 核心原则
**确定性操作应脚本化，启发式判断由AI处理**。两者应协调配合，让项目功能发挥更完全。

### 判断标准（项目级）

#### ✅ 合理的硬编码/AI分工
- **确定性操作已脚本化**：跨模块的文件解析、目录创建、命名规范、数据验证等操作已通过脚本实现
- **可配置参数已集中**：阈值、路径、模板、选项等参数已提取到项目级或模块级 `config.yaml`
- **AI专注启发式任务**：AI仅负责需求理解、方案设计、内容生成、语义判断等需要灵活性的任务
- **跨模块重复操作已识别并提取**：多个模块中重复的逻辑已提取为共享脚本或工具
- **无重复造轮子**：AI不会在每次执行时重复编写相同的代码逻辑

#### ⚠️ 需要改进的信号
- 多个模块中存在相似的操作，但未提取为共享脚本
- 配置值硬编码在多个文件中，而非从config.yaml读取
- AI每次都要"手动"执行固定操作（如"创建目录X"、"复制模板Y"）
- 跨模块的通用逻辑（如日期格式、路径拼接）未脚本化

#### ❌ 严重问题示例
- 让AI反复编写相同的跨模块操作代码
- 相同的配置参数在多个模块中重复定义
- 跨模块的基础逻辑未脚本化，依赖AI"每次记得正确执行"

### 典型反例（项目级）

**反例1**：跨模块重复逻辑
```
模块A：手动创建目录 output/{timestamp}/
模块B：手动创建目录 reports/{timestamp}/
模块C：手动创建目录 logs/{timestamp}/
```
**问题**：时间戳生成和目录创建逻辑重复，应提取为共享脚本

**反例2**：配置分散
```
模块A/config.yaml: timeout: 30
模块B/config.yaml: timeout: 30
模块C/config.yaml: timeout: 30
```
**问题**：通用配置应提升到项目级config.yaml

### 改进方向（项目级）
- 识别跨模块的重复操作，提取到共享脚本
- 将通用配置提升到项目级config.yaml
- 创建工具脚本处理常见的跨模块操作

## 3. 安全性检查

**状态**: ✅ / ⚠️ / ❌

### 核心原则
**预防常见安全漏洞和风险**。确保项目在输入处理、文件操作、依赖管理等方面无重大安全隐患。

### 判断标准（项目级）

#### ✅ 安全性良好
- **输入路径已规范化和校验**：用户提供的路径已验证其合法性，确保在项目范围内
- **无敏感信息泄露**：日志、错误消息、示例中不包含密钥、凭证、内部路径等敏感信息
- **外部调用可控**：网络请求、系统调用等外部操作显式、可控、可复现
- **依赖包安全**：依赖包无已知的高危安全漏洞，定期更新
- **配置安全**：敏感配置（API密钥、密码）使用环境变量或加密存储，不硬编码

#### ⚠️ 潜在安全风险
- 用户输入直接用于文件路径操作，未做边界检查
- 错误消息中包含详细路径或系统信息
- 外部调用使用用户输入作为参数，未做验证
- 依赖包版本过旧，存在已知漏洞
- 配置文件中包含明文密钥或密码

#### ❌ 严重安全漏洞
- 路径遍历漏洞：允许访问项目目录外的文件
- 命令注入风险：用户输入未过滤直接传递给系统命令
- 敏感信息泄露：API密钥、密码等硬编码在代码或配置中
- 依赖注入：使用不可信的数据直接执行代码或查询

### 典型反例（项目级）

**反例1**：路径遍历风险（跨模块）
```python
# 模块A
def process_file(user_path):
    # 危险：未验证路径范围
    with open(user_path, 'r') as f:
        return f.read()

# 模块B
def load_config(user_path):
    # 同样的问题
    return parse_yaml(user_path)
```
**问题**：多个模块存在相同的安全漏洞

**反例2**：敏感信息泄露
```python
# 项目级日志
logger.info(f"Processing {user_path} with API key {api_key}")
# api_key不应出现在日志中
```

**反例3**：依赖漏洞
```
requirements.txt:
requests==2.20.0  # 已知存在多个安全漏洞
```

### 改进方向（项目级）
- 建立项目级的安全工具脚本，统一处理路径验证
- 制定敏感信息处理规范，确保所有模块遵循
- 定期更新依赖包，使用安全扫描工具
- 建立安全配置模板（如.env.example）

## 4. 过度设计检查

**状态**: ✅ / ⚠️ / ❌

### 核心原则
**用奥卡姆剃刀原则审视每个设计决策**。避免为"未来可能用到"的场景预留功能，优先选择最简单的解决方案。

### 判断标准（项目级）

#### ✅ 设计简洁适度
- **只实现当前需要的功能**：无"为未来预留"的复杂抽象或扩展点
- **模块边界清晰**：每个模块职责单一，接口明确
- **配置项合理**：项目级和模块级配置项数量适中，不过度抽象
- **架构直观**：使用最直观、最易理解的架构方式
- **无冗余中间层**：不存在只起到简单传递作用的中间层

#### ⚠️ 存在过度设计信号
- 项目级配置项过多（超过30个）且大量嵌套
- 引入了多层抽象解决简单问题
- 存在"管理器工厂的建造者"等过度抽象
- 模块职责不清晰，存在"万能模块"
- 文档中大量解释"这个设计是为了未来的XX场景"

#### ❌ 严重过度设计
- 明显的YAGNI违反：为"未来可能需要"的功能预留接口/模块
- 过度泛化：试图用一套架构处理所有场景
- 不必要的抽象层次：引入"中间层"但只起到简单传递作用
- 模块间耦合度过高，或过度解耦导致简单操作需要多层调用

### 典型反例（项目级）

**反例1**：过度抽象的架构
```
项目结构：
core/
  abstracts/
    BaseProcessor.py
    AbstractFactory.py
    BuilderPattern.py
  factories/
    ProcessorFactory.py
    FactoryCreator.py
  impl/
    ConcreteProcessor.py
```
**问题**：实际只有一个Processor，不需要这么多抽象层

**反例2**：预留的扩展点
```yaml
# project/config.yaml
modules:
  pdf_processor:
    enabled: true
  docx_processor:
    enabled: false  # 未来可能支持
  html_processor:
    enabled: false  # 未来可能支持
```
**问题**：未实现的功能不应硬编码在配置中

**反例3**：过度解耦
```
用户操作 → Controller → Manager → Service → Repository → Database
          (5层，但Controller只转发给Manager，Manager只转发给Service...)
```
**问题**：中间层只做简单传递，无实际价值

### 改进方向（项目级）
- 删除未使用的"预留"模块和配置
- 合并职责相似的模块，减少层次
- 简化项目级配置，使用合理的默认值
- 遵循KISS原则：能用简单方法解决的，不引入复杂设计

## 5. 通用性检查

**状态**: ✅ / ⚠️ / ❌

### 核心原则
**避免不必要的场景和年份限制**。提高项目复用性，使其能适应更广泛的场景和时间跨度。

### 判断标准（项目级）

#### ✅ 通用性良好
- **无时间敏感性**：不包含具体年份、日期等会过时的信息（除非是命名规范要求）
- **无场景限制**：不过度限定使用场景，可适配多种类似需求
- **无平台依赖**：不强制依赖特定平台或工具（除非是项目核心定位）
- **使用相对时间**：描述使用"当前版本"、"最新版"等相对时间表述
- **跨平台兼容**：文档和示例考虑跨平台兼容性（路径、命令等）

- 项目级文档中包含"2024年版"、"2025年"等具体年份（非必要）
- 模块硬编码了特定场景（如"专为XX公司设计"）
- 假设了特定语言或文化背景
- 依赖特定平台的特有功能（非核心需求）
- 示例只适用于单一平台

#### ❌ 严重通用性问题
- 项目名称或描述中包含年份（如`myproject-2025`）
- 硬编码了特定工作流或业务流程
- 包含特定品牌的专有术语或缩写（无解释）
- 强制依赖特定操作系统或平台

```
模块B：专为Notion API设计
```
**问题**：限制了平台，实际逻辑可通用化

**反例3**：平台特定示例
```bash

```
**问题**：未考虑跨平台兼容性

### 改进方向（项目级）
- 将具体年份改为相对时间表述（"当前版本"）
- 将特定场景泛化为通用场景
- 提供扩展机制（如config.yaml），而非硬编码特定配置
- 使用跨平台的路径和命令示例

## 6. 一致性检查

**状态**: ✅ / ⚠️ / ❌

### 核心原则
**确保文档、配置、实现三者一致**。避免相互矛盾、描述不符、版本不匹配等问题。

### 判断标准（项目级）

#### ✅ 一致性良好
- **项目指令文件与实际状态一致**：

  - 模块级config.yaml不与项目级配置冲突

## 7. 项目指令文件瘦身检查

**状态**: ✅ / ⚠️ / ❌

### 核心原则
**遵循渐进披露（Progressive Disclosure）原则**。项目指令文件（CLAUDE.md、AGENTS.md）应保持简洁，只包含项目级核心信息；详细内容应模块化到各模块的 `references/` 或 `docs/`。

### 判断标准（项目级）

#### ✅ 项目指令文件瘦身良好
- **行数合理**：CLAUDE.md/AGENTS.md 不超过 400 行（建议阈值，项目级适当放宽）
- **核心内容保留**：项目目标、核心工作流、目录结构、模块关系、通用原则
- **详细内容已模块化**：各模块的详细策略、标准、模板已移至模块级 `references/`
- **配置说明已分离**：配置项的详细说明已移至相应 config.yaml 注释
- **技术细节已下沉**：各模块的技术实现细节已移至模块级文档

#### ⚠️ 存在臃肿信号
- 项目指令文件超过 400-500 行
- 包含大量单个模块的详细策略说明（可移至模块级文档）
- 包含完整的模板内容（可移至模块级 `assets/` 或 `references/`）
- 包含冗长的模块级配置项说明（可移至模块级 config.yaml）
- 包含详细的模块技术实现细节

#### ❌ 严重臃肿问题
- 项目指令文件超过 600 行
- 包含多个模块的完整模板内容
- 包含大量模块级配置的详细说明
- 包含详细的模块技术架构和实现细节
- 各模块的 `references/` 目录几乎为空，但项目指令文件非常长

### 渐进披露策略（项目级）

| 内容类型 | 保留位置 | 示例 |
|---------|---------|------|
| **项目级核心原则** | CLAUDE.md/AGENTS.md | 项目目标、工作流、目录结构、模块关系 |

### 典型反例（项目级）

**反例1**：模块级内容嵌入项目指令
```markdown
# CLAUDE.md（臃肿）
## 模块A详细说明

### 工作流程
... 100行详细说明 ...

### 配置项
... 50行配置说明 ...

### 模板
... 完整模板内容 ...
```
**问题**：应移至 `modules/A/references/` 或 `modules/A/docs/`

**反例2**：详细技术实现
```markdown
# CLAUDE.md（臃肿）
## 技术架构

### PDF处理实现
使用PyPDF2库... [100行技术说明]

### API集成实现
使用requests库... [80行技术说明]
```
**问题**：应移至相应模块的技术文档

**反例3**：模块级配置说明
```markdown
# CLAUDE.md（臃肿）
## 配置说明

### 模块A配置
- processor.type: 处理器类型...
- parser.timeout: 解析超时...

### 模块B配置
- formatter.output: 输出格式...
... 20+ 个模块的配置说明
```
**问题**：应移至各模块的 config.yaml 注释

### 瘦身操作指南（项目级）

#### 步骤1：识别可迁移内容
- [ ] 单个模块的详细策略/工作流（移至模块级 references/）
- [ ] 完整的模块模板文件（移至模块级 assets/ 或 references/）
- [ ] 模块级配置项的详细说明（移至模块级 config.yaml）
- [ ] 技术实现细节（移至模块级文档或注释）

#### 步骤2：执行迁移
- 在项目指令文件中使用引用：`详见 modules/A/references/XXX.md`
- 在各模块的 config.yaml 中添加注释说明配置项
- 在各模块中创建详细文档
- 保持项目指令文件只包含项目级通用信息

#### 步骤3：精简项目指令文件
- 保留项目级核心原则和工作流
- 保留目录结构和模块关系说明
- 使用简洁的描述，避免冗长说明
- 用链接/引用替代详细内容
