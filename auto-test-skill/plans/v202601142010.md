## 问题清单（P0-P2）

### P0（阻塞/安全/核心）

#### 问题 1: 缺乏"每轮最小建议数量"的强制要求

**位置**: `SKILL.md` 第 58-117 行（A 轮工作流）

**影响**:
- AI 可能每轮只提出 3-5 个问题就认为"完成"
- 无法满足用户"10-20 条建议/轮"的明确期望
- 8 轮迭代后总优化点不足（预期 80-160 条，实际可能只有 24-40 条）

**修复建议**:
1. 在 A.2 节（问题分析与计划生成）增加强制性要求：
   ```markdown
   **数量要求**：
   - 每轮至少发现 10 个问题（P0 + P1 + P2 总和）
   - 鼓励达到 15-20 个问题（深入挖掘）
   - 如首轮无明确问题列表，必须先进行"静态检查 + 一致性检查 + 逻辑推演"再列出问题
   ```
2. 在 A.4 节（是否进入下一轮）增加退出条件：
   ```markdown
   **进入下一轮的条件**：
   - [ ] 本轮已提出至少 10 个问题（P0 + P1 + P2 总和）
   - [ ] P0 和 P1 问题已全部修复或已有明确修复计划
   - [ ] 用户指定的轮次数未完成
   ```
3. 在完成条件中增加数量门槛：
   ```markdown
   - [ ] 每轮 A 轮平均问题数量 ≥ 10 个
   ```

**验证方法**:
- 阅读更新后的 SKILL.md，确认包含明确的"至少 10 个问题"要求
- 用 auto-test-skill 自我测试，验证是否能产出 10+ 问题

#### 问题 2: B 轮检查模板缺乏"挑衅性"和"挑战性"

**位置**: `templates/B_ROUND_CHECK_TEMPLATE.md` 第 25-612 行

**影响**:
- 当前模板是"说明性"的（告诉 AI 什么是好的/坏的）
- AI 容易"轻松通过"检查，未深入挖掘问题
- 缺乏"刁钻"的边缘情况和压力测试要求

**修复建议**:
在七个维度的每个检查中，增加"挑衅性检查项"（Challenging Checks）：

**示例（硬编码/AI 功能规划维度）**：
```markdown
#### 🚨 挑衅性检查（必须回答）
1. **找出一个"伪脚本化"的例子**：看似已脚本化，但 AI 仍在手动执行的操作
2. **找出一个"过度配置化"的例子**：本应硬编码的常量，却放到了 config.yaml
3. **质疑隐式假设**：文档假设用户会做 X（如"用户会先创建目录"），实际可能不会
4. **边缘情况挑战**：如果用户输入的路径是 `../../etc/passwd`，当前逻辑能防御吗？
```

**在模板末尾增加全局挑衅性检查**：
```markdown
---

## 🚨 全局挑衅性检查（必须全部回答）

### 1. 最挑剔的问题：这个 skill 有哪些"自我感动"的设计？
- 列出 3 个"看似专业，实际无用"的过度设计

### 2. 边缘情况压力测试
- 如果用户输入空目录会怎样？
- 如果用户输入包含特殊字符的路径会怎样？
- 如果 config.yaml 被用户删空会怎样？

### 3. 隐式假设挖掘
- 列出 5 个文档未说明、但 AI 默认假设会成立的条件
- 这些假设在什么情况下会失效？

### 4. "如果我是恶意用户"测试
- 尝试构造 3 个恶意输入场景，验证 skill 是否安全

### 5. 文档与实现的"鸿沟"
- 找出 3 个"文档说 A，实际做 B"的不一致之处
```

**验证方法**:
- 阅读更新后的 B_ROUND_CHECK_TEMPLATE.md，确认包含挑衅性检查
- 用更新后的模板检查一个 skill，验证是否能发现 10+ 问题

#### 问题 3: 缺乏"建设性"的定义和示例

**位置**: SKILL.md 全文

**影响**:
- AI 可能提出"无用建议"（如"增加日志"、"优化注释"等泛泛而谈）
- 缺乏"什么是建设性建议"的标准
- 无法保证建议质量

**修复建议**:
在 SKILL.md 或 references/ 中新增"建设性建议标准"：

```markdown
## 建设性建议标准

### ✅ 建设性建议的特征
1. **可执行**：包含具体的修复方案，不是"应该改进XX"这种泛泛而谈
2. **有证据**：基于具体文件/行号/代码，不是凭空猜测
3. **有价值**：修复后能带来明显的质量提升（安全性/可维护性/用户体验）
4. **可验证**：包含明确的验证方法

### ❌ 非建设性建议的例子
- ❌ "建议增加更多日志" → ✅ "在 `scripts/foo.py` 第 42 行的 `except` 块中，记录具体的异常类型和堆栈信息"
- ❌ "建议优化文档" → ✅ "SKILL.md 第 30 行的描述与 config.yaml 第 15 行不一致，应统一为..."
- ❌ "建议增强测试" → ✅ "当前缺少对`--dry-run`参数的测试，应在 `tests/` 中增加验证用例"

### 建设性建议的"黄金公式"
```
位置 + 问题现象 + 影响分析 + 具体修复方案 + 验证方法
```

### 本轮建议质量检查
- [ ] 每条建议都包含具体位置（文件:行号）
- [ ] 每条建议都包含修复方案（不是"建议"而是"改为..."）
- [ ] 每条建议都包含验证方法（如何确认修复成功）
```

**验证方法**:
- 在 references/ 中创建 `CONSTRUCTIVE_SUGGESTION_GUIDELINES.md`
- 在 SKILL.md 中引用该文件
- 检查历史建议是否符合标准

#### 问题 5: 缺乏"问题挖掘技巧"的指导

**位置**: SKILL.md

**影响**:
- AI 可能不知道如何"深入挖掘"问题
- 容易停留在表面，发现的都是显而易见的问题
- 难以达到 10-20 条建议的数量要求

**修复建议**:
在 references/ 中新增 `ISSUE_DISCOVERY_TECHNIQUES.md`：

```markdown
## 问题挖掘技巧

### 技巧 1: 文件间交叉验证
- 检查 A 文件引用的配置，在 config.yaml 中是否存在
- 检查 README.md 中的示例，与 SKILL.md 的工作流是否一致
- 检查脚本注释中的"路径"，与实际目录结构是否匹配

### 技巧 2: 逻辑推演找漏洞
- "如果用户跳过步骤 1，直接执行步骤 2 会怎样？"
- "如果 config.yaml 中的这个参数是空值会怎样？"
- "如果用户输入的路径包含空格或特殊字符会怎样？"

### 技巧 3: 文档"读心术"
- 找出文档中"应该"、"会"、"自动"等模糊词 → 这些通常是未验证的假设
- 找出文档中"例如"、"如"等示例 → 这些示例是否真的可运行？
- 找出文档中"详见"、"参考"等引用 → 被引用的文件是否存在？

### 技巧 4: 代码/文档"模式匹配"
- 搜索 `TODO`、`FIXME`、`HACK` 等标记 → 未完成的技术债
- 搜索 `print(`、`console.log` 等调试语句 → 未清理的调试代码
- 搜索 `#` 注释中的"临时"、"测试"、"备份" → 未清理的临时内容

### 技巧 5: "挑刺"清单
- [ ] 每个配置项都有说明吗？
- [ ] 每个示例都能运行吗？
- [ ] 每个引用的文件都存在吗？
- [ ] 每个步骤都有验证方法吗？
- [ ] 每个错误都有明确的错误提示吗？
```

**验证方法**:
- 创建 `references/ISSUE_DISCOVERY_TECHNIQUES.md`
- 在 SKILL.md 的 A.2 节中引用
