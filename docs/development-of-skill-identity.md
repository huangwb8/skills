# Agent Skill 身份基础设施开发计划

本文整理 Skill Identification System 的拟议设计，供开发前审查。当前状态为**待审查，尚未实施**；字段与引用格式均为设计建议，不代表现行公开协议。按审查要求，本计划直接保存在 `docs/`，不作为已有源码行为的说明。

## 通俗解释：究竟要解决什么

当一个工作流要求 Agent 使用某个 Skill 时，同名文件夹并不能证明它就是预期的那个 Skill。不同作者可能都发布名为 `pdf` 的技能，攻击者也可以复制正版名称、作者说明和版本号，再把其中的脚本替换掉。

这类似按商品名称收货：名称帮助我们找到商品，但还需要知道供货方、具体批次，以及收到的物品是否被调换。对应到本项目，供货方是发布者，商品是具有稳定身份的 Skill，批次是一次发行，验收则是对实际文件进行验证。

例如，现在一个流写着“使用 research-literature-search”，Agent 可能按名字找到用户级或项目级的某个目录。改进后，流引用特定发布者的稳定 Skill 身份，本地程序解析并固定一份经过验证的发行内容；同名替代品会被识别为另一个身份，文件被修改则会报告内容不一致。

**总体建议：建立开放的身份协议和独立参考实现。AI 判断任务适配性，程序确认身份与内容，宿主决定是否允许加载和执行。**

## 专业判断：现有基础与缺口

### 已有能力

根据本轮本地源码阅读，现有能力可以复用，但用途需要区分。

| 现有机制 | 已解决的问题 | 尚不能证明的事实 |
|---|---|---|
| bensz-router 的流版本、固定解析和契约摘要 | 流的选择与正文版本可固定、可追溯 | 流提到的 Skill 就是宿主实际加载的 Skill |
| router 的 Skill 目录 SHA-256 比较 | 源副本和安装副本是否存在内容差异 | 比较依据是否来自获授权发布者 |
| 本项目安装器的 MD5 与来源 manifest | 更新判断、安装来源与过程记录 | 发布主体真实性、抗冒充、运行前内容完整性 |
| State／Verifier canonical ID 与 alias | 特定对象的稳定命名与别名解析 | Skill 发行包的发布者认证与供应链安全 |

本仓库可定位的依据包括[安装器实现](../skills/alpha/install-bensz-skills/scripts/install.py)、[安装器配置](../skills/alpha/install-bensz-skills/config.yaml)、[State 命名规范](state-id-naming.md)和 [Kernel 身份模块](../packages/bensz-skill-kernel/src/bensz_skill_kernel/identity.py)。router 侧阅读范围为其工作流协议、工作流定义结构及客户端 `adapters.py`，跨仓库接入时应重新核对对应版本。

安装器当前部分更新判断会读取已保存的 MD5，而不是每次重新计算实际目录。它是更新优化机制，不能作为运行前防篡改证明。直接把 MD5 换成 SHA-256 也不足以认证发布者，因为攻击者仍可同时替换内容和自报摘要。

### 必须分开的安全判断

系统需要分别回答四个问题：这是哪个 Skill；这些文件属于哪次发行；谁有权发布这次发行；当前环境是否允许使用它。

身份验证通过只说明发布关系和文件内容满足验证条件。它不证明代码无害，也不授予读取凭据、访问网络或启动进程的权限。合法发布者可能作恶，发布密钥也可能被盗，因此身份验证需要与本地授权、撤销和宿主执行边界配合。

另一个关键假设尚待验证：目标 Harness 是否允许在 Skill 描述和正文进入模型上下文前实施检查。已有 hooks、MCP 或工具执行检查不自动证明存在这个入口。如果只能事后检查，系统应明确报告支持范围。

## 要达到什么目标

完成首个端到端版本后，应当能够观察到以下变化：

- 同名 Skill 可以共存，程序依靠稳定身份解析，不依赖目录搜索顺序选择正版。
- 流可以声明结构化 Skill 依赖，本地将它解析为精确身份、版本和内容摘要。
- 清单、签名、发布者授权和实际文件相互绑定，抄写 ID 或修改脚本不能通过验证。
- 一次运行使用固定内容；自动更新、路径遮蔽或文件替换不会静默改变本次依赖。
- 至少一个真实宿主完成受控接入，能够验证加载前检查和内容绑定是否实际生效。
- 第三方发布者、自托管环境和不使用 bensz-router／BSK 的工具均能独立采用协议。

首版不建设公共 Skill 市场、全球名称注册中心、评分平台或区块链身份系统；不承诺证明任意 Skill 无恶意，也不实现完整操作系统沙箱。身份检查不依赖 State／Verifier Pack，普通 Skill 不需要因此接入 BSK。

本轮交付仅为计划。下述包、协议、安装器调整及跨仓库接入均属于后续开发范围。

## 改进方向

### 建立稳定身份，保留易读名称

建议把 Skill 身份拆成发布者身份和发布者命名空间内的稳定键。显示名称继续用于发现和对话，仓库地址用于获取内容，两者都不直接决定身份。

| 对象 | 拟议含义 | 变化规则 |
|---|---|---|
| `publisher_id` | 发布主体的密码学身份锚点 | 首版由根公钥指纹派生；信任须另外建立 |
| `skill_key` | 该发布者名下的稳定 Skill 键 | 发布后不因展示名称或目录调整而改变 |
| `skill_id` | 发布者身份与 Skill 键的组合 | 用于依赖、锁定和审计 |
| 显示名称／alias | 人和 AI 使用的易读名称 | 允许修改；必须经过可信映射解析 |
| 版本 | 发布者声明的发行版本 | 与身份分离，发布后不可对应不同内容 |
| 内容摘要 | 一份发行内容的精确指纹 | 任何受保护内容变化均产生新摘要 |

概念引用形式可以是 `skill://<publisher-id>/<skill-key>`。最终语法、字符集和编码在协议阶段固定；身份键采用明确的 ASCII 规则，易读展示名可以保留多语言。

同名不同发布者是不同身份；同一发布者的不同 Skill 键也是不同身份。Fork 使用新的身份，并可以记录来源关系。仓库迁移和可信镜像保持同一身份。不能仅因代码相同、作者名相同或路径相同，就推断两个 Skill 是同一身份。

别名冲突必须返回歧义。一个发布者不能仅靠自签名宣称自己拥有 `bensz` 等易读名称；别名与身份的对应关系由本地显式配置或受信登记来源确认。已有 State／Verifier ID 继续使用原有协议，不与 Skill ID 混用。

对使用者而言，这意味着仍可输入熟悉的名字，但一旦进入运行，系统会明确使用哪位发布者的哪一个 Skill。

### 用签名发行清单认证发布关系

发行清单应绑定稳定 Skill ID、版本、内容摘要、文件清单、依赖和签名授权信息。程序先检查清单结构及资源限制，再验签、校验授权范围和实际文件；验证过程中不能运行 Skill 自带脚本或安装钩子。

建议首版采用离线根密钥与可轮换发布密钥：根公钥指纹确定 `publisher_id`，根签名授权某个发布密钥在限定范围和有效期内发布。每个发布者可以有多个 Skill，但发布密钥不必拥有全部 Skill 的发布权。

信任根必须来自使用者显式接受的配置、管理员策略或已受信的安装渠道。不能从待验证包里取出一把公钥，看到自签名成立就认定发布者可信。首次接入未知发布者时返回“未受信”，供人审查；无人值守流程不得自动接受。

常规发布密钥轮换保持 Skill 身份不变。首版根密钥更换会产生新的发布者身份，旧身份可以在仍可信时签发接续声明，但客户端是否接受迁移仍由本地策略决定。根密钥遗失或被攻破时，不以同名账号或新仓库作为自动恢复依据；通过外部受信管理渠道撤销旧身份并重新建立信任。自动保持 ID 不变的复杂根恢复方案留待后续论证。

实现采用成熟密码学库，不手写签名算法。离线 Ed25519 签名作为首版优先方案；在实现前核对库依赖、签名封装与 DSSE 的适配成本。Sigstore 和 TUF 分别作为未来签名来源、透明记录及安全更新元数据的候选，不把它们视为可互换的机制，也不声称已完成选型验证。

对使用者而言，复制正版 ID 和作者说明将无法获得正版的发布证明。

### 明确内容边界，覆盖实际会影响行为的资产

内容摘要必须覆盖 `SKILL.md`、配置、脚本、references、模板、内部子 Agent 及其它会影响执行的包内文件。文件路径、类型和必要的执行属性也应纳入规范，不能只对文件正文或压缩包偶然产生的字节做比较。

首版建议使用显式文件清单、确定性排序和原始字节摘要：不自动归一化换行，不因操作系统差异静默接受不同字节。路径统一为受限的相对路径；拒绝越界、绝对路径、重复项、大小写碰撞、符号链接及不支持的特殊文件，并限制文件数量、大小和总展开体积。

发行内容与发行元数据分离：包内容摘要不包含自身清单与签名，以避免循环哈希；签名保护完整清单，清单再保护文件集合。安装记录、缓存和运行输出放在受管旁路位置，不混入受保护内容。清单外的额外可加载文件也应被发现并拒绝，不能成为绕过摘要的入口。

当前安装器会排除部分文件，不能直接假定原有过滤规则适合安全验证。首版优先将同一份运行资产原样分发；需要裁剪时，由签名清单声明有限的安装视图，分别固定摘要。不得由客户端临时忽略文件后仍声称完整发行包验证通过。

Skill 包签名不自动覆盖外部 Python／npm 依赖、系统工具、远程文档或动态下载代码。包内的 Skill 依赖进入精确锁定记录；其它依赖必须说明验证范围。运行时下载可执行内容必须另行固定来源和摘要，并获得本地策略允许，不能把它继承为已验证包内代码。

对使用者而言，检查结果会说明究竟验证了哪些资产，修改参考指令或脚本都能被识别。

### 把验证结果绑定到实际加载内容

独立参考实现负责解析身份、验证清单、解析依赖和产生锁定记录。锁定记录固定每个 Skill 的 ID、精确版本、发行清单摘要和内容摘要，并记录影响验证的信任策略与撤销信息版本；本地位置只用于受控加载，不作为公开身份。

建议对外区分三个结果维度，避免一个 `trusted: true` 掩盖事实：

| 维度 | 需要表达的结果 |
|---|---|
| 身份与内容 | 已验证、未验证、签名错误、身份不符、内容不符 |
| 本地政策决定 | 允许、拒绝、需要显式审查；同时给出稳定原因码 |
| 宿主保证范围 | 仅文件检查、已验证加载绑定、加载及受控工具执行绑定 |

第三个维度来自适配器的实际能力和验收证据，不允许 Skill 自报。返回结果应绑定当前请求、锁定记录和实际内容，防止复用过期回执。

验证顺序是：解析依赖 → 验证发布关系与文件 → 检查本地策略 → 固定受管内容 → 宿主加载 → 受控执行。存储可按摘要寻址，但只读属性本身不能消除替换风险；适配器必须保证消费验证过的字节，或在受保护执行边界重新验证。需要检查检查后替换、并发更新、目录遮蔽和旧回执重放。

特别要控制发现阶段。未验证的 Skill 描述也可能包含诱导指令，不能先交给模型，再让模型负责识别真假。受控目录只能向模型提供已验证候选元数据。若原生宿主无法拦截自动发现，应验证隔离技能目录或受控启动方式是否可行，并公开说明覆盖范围。

身份运行时不承担任意 Shell 的全局拦截；用户或模型经其它工具读入的指令也不自动获得身份保证。真正的进程、网络和文件权限限制属于 Harness 或沙箱。不能把 Skill 自报的能力需求当作授权。

对使用者而言，“已验证”将有明确含义：它可能只是一次目录检查，也可能已经落实到实际加载，两者不会混为一谈。

### 接入安装器和 bensz-router

安装器接入独立身份运行时，在受管临时区验证候选发行后再原子发布。发现签名错误、身份冲突或内容不符时，不覆盖当前有效安装。原有 MD5 可暂时保留用于兼容更新判断，但不参与安全判定；镜像必须提供相同的签名发行内容，不能因为地址位于允许列表就跳过验证。

发行版本继续以 Skill 的 `config.yaml:skill_info.version` 为人工维护来源，发行清单在打包时读取并生成版本字段，不新增一份手工维护版本号。同一身份、同一版本对应不同内容时返回冲突。

router 侧增加结构化 `skill_requirements`，表达稳定身份和版本约束，必要时指定精确内容摘要。AI 只判断需求适配，本地程序负责解析与验证。流中的普通名称提及仍是文字，不自动成为可执行依赖；AI 动态提出新增 Skill 依赖时，也须走同一解析和策略过程。

服务端可以校验引用结构，但无法据此证明用户机器上的安装内容。客户端锁定记录是本地验证依据，不需要上传用户任务、绝对路径或完整 Skill 清单。已有流版本、路由快照摘要与 Skill 内容摘要继续分别表达不同对象，不能互相替代。

受保护流只为已下发的当前步骤声明所需 Skill；后续步骤在下发时验证并增补锁定记录，保留此前绑定，避免依赖解析提前暴露完整隐藏流程。

对使用者而言，流引用的能力将落到明确的一份发行内容；跨机器或跨镜像安装也能验证一致性。

### 支持撤销、安全更新和旧 Skill 迁移

首版至少支持撤销发布密钥、具体发行版和发布者身份。撤销及授权更新必须可验证，并具备单调修订号和有效期；客户端保存已接受的修订，拒绝更新时静默回退到更旧的安全元数据。根密钥泄露时，不能仅依赖被攻破密钥签发的记录完成恢复。

正常更新不改变进行中运行的锁定内容；明确撤销则在下一个受控加载或执行边界阻止继续使用。已经进入模型历史的文本无法被删除，重大撤销后需要新的会话边界。显式版本回退仍需符合当前撤销与授权策略。

离线行为须在协议中写清：可在本地策略允许且安全元数据仍有效的期限内验证已缓存发行；超出期限的严格运行停止对应依赖，报告无法确认最新撤销状态。不能把“离线可验签”说成“已确认未被撤销”。

旧 Skill 标为未验证，不伪造发布者身份。兼容模式只能通过使用者显式允许使用，且不得满足一个要求已验证身份的依赖。名称冲突、摘要冲突、签名错误或被撤销等情况不能退回名称搜索。

本地开发副本可以使用项目专用开发身份和快照摘要，明确标注为开发内容；修改后需重新快照，不能沿用正式发行的验证状态。第三方未签名 Skill 可由分发者重新打包并以其自身身份签名，但必须标注分发者与上游作者的区别，不能冒充上游官方发行。

兼容回滚可以恢复旧版软件和安装流程，但会失去新增保证；严格依赖应保持受阻，不能自动降级为允许执行。

## 模块职责与开发范围

建议新增独立运行时包，暂名 `packages/bensz-skill-identity/`，最低 Python 3.11。包负责协议解析、摘要与签名验证、信任和撤销判断、依赖锁定及可复用 API／CLI。不得在包中放入领域 Skill 工作流。

| 组件 | 负责 | 不负责 |
|---|---|---|
| 身份协议与运行时 | 发布身份、发行真实性、内容绑定、确定性结果 | 判断科研／开发任务应选哪个 Skill |
| 发布工具 | 生成清单、校验版本、调用成熟签名能力 | 未经授权保管或上传发布私钥 |
| 安装器 | 获取、验证、受管安装及安装证据 | 仅凭名称自动建立发布者信任 |
| router 适配 | 结构化依赖、本地解析衔接、步骤绑定 | 替用户机器证明文件已加载 |
| Harness 适配 | 加载入口、实际内容绑定、受控调用 | 承诺未覆盖工具具有同等防护 |
| BSK | 将来按需消费已验证 Skill 身份 | 托管该体系的中央认证与发布业务 |

协议、包和宿主适配应可以分别演进，公开结果格式需版本化。现阶段不扩张 BSK，不自动修改系统级 Skill 副本，也不预设新增 State／Verifier。

本仓库后续变更以新包、协议文档、安装器及相应测试为主。bensz-router 是独立仓库，其修改应作为后续明确授权的接入任务；本计划的审查通过不等于对该仓库或线上服务的写入授权。

## 实施范围与顺序

### 阶段一：冻结最小协议，验证宿主接入可行性

先明确身份、文件清单、签名授权、版本不可变、撤销与锁定记录的契约，并用两个同名 Skill 和一个被篡改发行包检验设计。同步对一个候选宿主做最小验证原型，确认发现／加载入口、项目级遮蔽行为和受控目录方案。

交付协议草案、固定测试向量和宿主能力报告。退出条件是每个身份判断都有确定依据，且宿主接入路径得到真实验证。若没有可用加载边界，必须缩小产品保证或改用受控启动方式，不能直接进入“已阻止冒充加载”的实施承诺。

### 阶段二：实现独立身份运行时与发行工具

实现清单生成、签名与授权验证、实际文件检查、显式信任配置、有限的密钥轮换／撤销、依赖精确锁定及稳定错误输出。解析发行内容时不执行包内代码，发行工具不自动发布或上传资产。

交付可安装的包、API／CLI 文档、有效与无效发行的测试向量。退出条件是第三方调用方可在不安装 router／BSK 的环境中验证同一份发行，且失败结果可复现。

### 阶段三：接入安装器，提供显式兼容路径

先选少量维护中的 Skill 作为发行样本，验证完整文件边界、镜像一致性、安装过滤和同名冲突；再接入安装记录、原子更新与开发模式。第三方未签名源继续显示真实保证范围。

交付安装器接入、迁移说明和仓库公开入口集成测试。退出条件是无效候选不能替换有效安装，旧版更新判断与新的真实性验证职责清晰，且不强制迁移全部 Skill。

### 阶段四：完成 router 与单个真实宿主的端到端接入

在另行授权后，为 router 增加结构化 Skill 依赖及本地解析衔接；在阶段一验证的宿主路径中落实发现前检查、固定加载内容和撤销检查。受保护步骤按需增补依赖。

交付最小流示例、宿主适配、真实加载证据及能力限制说明。退出条件是能够从流要求追踪到精确本地内容，并在同名遮蔽、篡改和并发替换时阻止错误依赖被受控路径使用。

### 阶段五：在验证收益后扩大生态

根据前述阶段结果，再评估第二种宿主、企业信任分发、自托管登记、Sigstore、TUF 或透明日志。新增来源必须保持同一身份与内容协议，避免各平台重新定义“同一个 Skill”。

这一阶段不是首版完成条件。是否建设公共注册服务，应依据发布者规模、信任维护成本和实际接入需求单独决策。

## 如何确认完成

验收同时覆盖协议、安装和宿主真实行为。单元测试通过、命令返回成功或 AI 自报调用成功，都不能代替实际加载绑定证据。

| 场景 | 预期结果 | 验证层次 |
|---|---|---|
| 两个发布者提供同名 Skill | 稳定身份不同；名称有歧义时拒绝自动选择 | 协议、解析器 |
| 冒充者复制 ID、版本和作者说明 | 无法通过获授权签名校验 | 运行时 |
| 修改正文、脚本、reference 或子 Agent | 内容校验失败；报告相对文件定位 | 运行时、安装器 |
| 添加清单外可加载文件、路径穿越或链接 | 在加载／安装前拒绝 | 运行时、安装器 |
| 相同身份与版本发布不同内容 | 返回不可变发行冲突 | 发布、安装器 |
| 项目级 Skill 遮蔽用户级正版 | 受控加载仍使用锁定内容，或明确拒绝 | 真实宿主 |
| 检查后替换文件或并发自动更新 | 实际消费原固定内容，或在使用前阻止 | 真实宿主、并发集成 |
| 发布密钥正常轮换 | 经有效授权的新密钥可用，身份不变 | 协议、运行时 |
| 发行被撤销，或安全元数据被回放 | 在受控边界拒绝；过期／离线状态明确 | 运行时、宿主 |
| 包含恶意指令的未验证描述 | 不进入受控候选上下文 | 真实宿主发现入口 |
| 有效签名 Skill 请求越权操作 | 签名不提供授权，宿主政策仍决定执行 | 适配器及其覆盖边界 |
| 丢失 Skill、别名歧义或依赖环 | 确定性错误，不静默换用其它 Skill | 解析器、router 接入 |
| 缓存可用但撤销信息过期 | 严格模式受阻，兼容例外显式可见 | 运行时、离线集成 |
| 旧 Skill 或开发副本 | 未验证／开发状态真实，不冒充正式发行 | 迁移、安装器 |
| 仅具有文件检查能力的适配器 | 不能报告已完成加载或执行绑定 | 结果协议、真实宿主 |

测试组织遵循仓库边界：包内测试放在新包自己的 `tests/`，仓库安装入口与跨包集成测试放根级 `tests/`；运行夹具和产物放 `tmp/`，Python 与工具缓存放 `.bensz-api/`。正常与恶意样本使用合成数据，不包含真实私钥、凭据或用户任务。

首个端到端版本只有在阶段一至四通过后，才能声明支持已验收宿主中的加载绑定。若只完成阶段二或三，应准确表述为“身份验证与安装完整性可用”。

## 风险与审查重点

**最主要的风险是宿主能力。** 身份格式和签名易于演示，难点是保证宿主不会从其它位置先加载同名指令。阶段一将它设为前置验证，避免实现大量协议后才发现只能提供事后检查。

**第二个风险是信任运维。** 离线根密钥、发布授权和撤销需要可靠的维护流程。首版选择有限、可解释的机制；根密钥恢复不承诺无感完成，公共注册服务也不作为必需依赖。

**第三个风险是过度承诺。** 验签不等于安全审计；只读目录不等于抵抗本机高权限攻击；撤销不能抹去模型已看到的内容。首版威胁范围聚焦同名冒充、包内容替换、依赖漂移和受控路径的加载绑定。本机管理员、被攻破宿主或身份运行时本身受到控制时，不声称仍能提供上述保证。

审查时建议优先确认以下取舍：

- 是否同意采用“开放协议＋独立包＋消费者适配”的边界，暂不扩张 BSK。
- 是否接受首版以根公钥指纹锚定发布者身份，根更换通过显式身份迁移处理。
- 是否同意把真实宿主加载前验证设为端到端完成的必要条件。
- 是否接受旧 Skill 的显式兼容路径，以及严格身份依赖验证失败时停止该依赖。
- 第一批发行样本与目标宿主选择哪个；建议选择资产边界较小的维护中 Skill，并以阶段一结果确定宿主。

上述事项是设计审查点，不表示实现、系统安装、密钥配置、跨仓库写入或发布已经获得批准。审查意见确认后，再据此收敛协议和实施范围。
