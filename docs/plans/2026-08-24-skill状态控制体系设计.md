# Agent Skill 运行时状态控制体系实施计划

## 通俗解释：究竟发生了什么

- **一句话说明：** 不同 Skill 都在记录自己的进度，但这些记录还不能用同一套最小规则回答“任务现在处于什么阶段、为什么停下、凭什么可以交付”。
- **具体场景：** 这像一个需要分拣、质检和签收的包裹。分拣单、质检单和签收单可以各自保留专业信息，但物流系统只需要一套共同的账本，记录发生过什么、当前能否继续、交付是否满足契约。
- **对应到本问题：** 事件是账本中的事实；当前状态是根据账本整理出的摘要；phase、子任务和副作用是不同 Skill 声明的规则；验证证据是质检记录；正式输出是签收件。
- **改变前后：** 现在网络中断可能只留下一个含义不清的阶段文件；改进后，系统追加一条阻塞事实，保留已生成证据，状态摘要显示等待原因和下一动作，恢复时从同一历史继续而不覆盖原记录。

## 专业判断：问题在哪里

### 已确认的现状

现有 Skill 已分别实现了工作区隔离、`run_id`、阶段恢复、预览/应用/报告模式、网络重试、备份快照、并行汇聚、编译和引用校验等机制。它们大致覆盖短报告、确定性闭环、项目写回、联网长流水线和并行候选五类流程。

这些局部机制本身并不缺少能力，真正的问题是它们缺少一套更小的共同语义：

- 相同词语在不同 Skill 中含义不同；
- Skill 内部阶段不能代表整个任务已经完成；
- `state.json`、阶段文件和报告之间谁是事实来源不清楚；
- 等待用户、等待依赖、等待子任务都可能被不同地解释；
- 写回或发布发生部分成功时，现有记录难以说明外部真实状态；
- 旧 Skill 不能一次性重写，也不能被迫猜测旧状态的含义。

### 设计判断

本体系借鉴的是“极简核心、数据结构优先、可解释状态、错误可恢复和组合优于堆叠”的原则，不试图实现 Git 的对象库、分支或合并机制。

运行时的最小核心只负责四件事：

1. 追加不可覆盖的事实事件；
2. 用确定性规则把事实投影为当前生命周期状态；
3. 检查完成、恢复和交付所需的证据；
4. 为 Skill 声明的领域策略提供统一执行边界。

phase DAG、子任务汇聚、重试策略和外部副作用不是新的核心状态，而是可声明、可组合的策略。

## 要达到什么目标

### 完成后的变化

- 任一需要留痕的任务都能回答：当前生命周期状态、领域阶段、等待原因、下一动作、证据、正式输出和是否需要用户介入。
- 当前状态可以从事件历史确定性重建；`state.json` 只是可删除、可重建的投影，不是第二套事实来源。
- Skill 可以保留自己的阶段和专业字段，但必须通过适配器接入统一的事件、证据、验证和交付边界。
- 失败、暂停、阻塞、恢复、返工、补偿和部分交付都追加历史，不覆盖原记录。
- 运行时提供稳定的 Python API 和 CLI；Skill 不再手写状态转移或直接覆盖事件账本。

### 不在本次处理范围

- 不把 `Generate`、`Search`、`Write` 等领域动作升格为全局生命周期状态。
- 不引入 Git 式对象数据库、branch、merge 或常驻远程服务；这些不是当前问题的必要条件。
- 不一次性重写全部 Skill；先做适配器和三类代表性试点，再渐进迁移。
- 不记录模型内部思维链，不把每个微小工具调用都写入事件流。
- 不把 Skill 包自身的 `draft/stable/deprecated` 生命周期混入任务运行状态。
- 不自动公开 bug，不替代 `bensz-collect-bugs` 的脱敏和上报门禁。

## 改进方向

### 收缩为“事实、投影、契约、证据”四个核心概念

运行时只固定以下四类概念：

- **事实（event）：** 已发生且不可覆盖的事件，如任务接纳、状态转移、等待、错误、验证、交付和恢复。
- **投影（projection）：** 根据事件历史计算出的 `current_state`、`phase`、`outcome`、`next_action` 和摘要字段；`state.json` 保存该投影及其 `last_seq`，损坏后可以重建。
- **契约（contract）：** 任务目标、required 产物、阶段依赖、等待/重试/汇聚规则和交付前置条件；契约描述“什么条件才算完成”，不直接伪造事实。
- **证据（evidence）：** 产物、验证结果、授权记录和外部副作用的执行/探测记录；证据必须可引用、可定位并标明来源。

任何 API 调用都遵循“请求动作 → 校验契约 → 追加事实 → 更新投影”的顺序。运行时不接受 Skill 直接覆盖状态文件。

这项改变的意义是：以后新增 Skill 时，主要增加契约和适配器，不再扩大运行时核心。

核心不变量固定为：

- 事实事件只能追加，不能被后续运行覆盖；
- 当前投影必须能由事件历史确定性重建；
- 没有 required 产物和验证证据，不能形成 `completed`；
- 所有状态转移都必须满足契约前置条件，并留下可定位的事件；
- 外部副作用必须有授权、幂等键和可验证结果，未知结果不能伪装成成功；
- 旧状态无法证明含义时只能降级或等待，不能猜测为成功。

### 用八个生命周期状态表达最小可用控制面

将原先含义相近的 `waiting_user` 和 `blocked` 合并为 `waiting`，具体原因放入 `wait_reason`。运行时固定以下状态：

| 生命周期状态 | 含义 | 允许的后续状态 |
|---|---|---|
| `planned` | 目标、范围、契约和前置条件已登记，尚未执行 | `active`、`waiting`、`cancelled` |
| `active` | 正在执行某个领域阶段或动作 | `active`、`waiting`、`checking`、`cancelled`、`failed` |
| `waiting` | 暂时不能继续，原因由 `wait_reason` 说明 | `active`、`cancelled`、`failed` |
| `checking` | 候选结果正在接受质量、安全、边界和回归检查 | `active`、`waiting`、`delivering`、`failed`、`cancelled` |
| `delivering` | 正在写入、发布、签收或执行已授权的补偿 | `active`、`waiting`、`checking`、`completed`、`failed`、`cancelled` |
| `completed` | 生命周期已闭合，交付证据已登记 | 终态 |
| `failed` | 已确认无法继续完成，原因和证据完整 | 终态 |
| `cancelled` | 用户或系统明确终止 | 终态 |

`wait_reason` 至少支持 `input`、`authorization`、`approval`、`choice`、`dependency`、`quota`、`children`、`schedule` 和 `operator_pause`。用户界面可以把 `waiting + input` 显示为“等待用户”，把 `waiting + dependency` 显示为“依赖阻塞”，但不把这些文案扩张成新的核心状态。

其他字段保持正交：

- `phase`：领域阶段及其声明式依赖；
- `outcome`：只在闭合时说明 `success`、`partial`、`degraded`、`failed`、`cancelled` 或 `superseded`；
- `child_summary`：子作用域数量、完成数、失败数、等待数和汇聚策略；
- `artifact_status`：产物的计划、生成、验证、发布、缺失或撤回；
- `effect_status`：副作用的计划、已执行、已验证、补偿中、已补偿或未知；
- `attempt_id`、`authorization`、`retry_policy`、`budget` 和 `next_action`：恢复和执行上下文。

`completed + outcome=partial` 只表示契约允许的可选结果缺失；required 产物、验证证据或交付报告缺失时，运行时拒绝进入 `completed`。

### 明确事件账本是事实来源，快照只是投影

任务根目录保留：

- `README.md`：面向人的摘要、当前投影、正式交付和已知限制；
- `state.json`：带 `projection_version`、`last_seq` 和 `last_event_id` 的最新投影；
- `log/events.ndjson`：追加式事实事件。

事件使用规范化 JSON，至少包含 `seq`、`event_id`、`scope`、`actor`、`attempt_id`、事件类型、摘要、相对路径、证据引用和幂等键。允许命名空间扩展，但核心 reducer 只依赖稳定字段。

运行时负责原子追加、序号校验、哈希链校验、确定性重放、投影重建、默认脱敏和路径边界检查。快照写入失败不能抹掉已追加事实；事件损坏时必须明确报错，不得把最后一个快照静默当成新事实。

### 把 phase、子任务和副作用下沉为声明式策略

每个需要多阶段执行的 Skill 提供轻量 `contract`，只描述：

- phase 节点、依赖、required/optional 属性；
- 产物和验证器；
- 子作用域的 `join_policy`（`all`、`quorum`、`best_effort`）；
- 子任务失败传播规则（`fail_task`、`partial`、`warning`）；
- 重试、预算、授权和交付前置条件。

运行时只检查契约，不理解检索策略、写作方法或领域评分标准。子任务通过 `scope`、`parent_scope` 和 `attempt_id` 关联；真正等待子任务时使用 `waiting + wait_reason=children`。

策略必须定义结果传播：required 子任务失败如何影响父任务、`partial` 是否升级为 `degraded`、多层 scope 如何合并，以及未选候选的证据如何保留。

### 统一验证、交付和外部副作用边界

验证事实至少包含 `verdict`、`findings`、`repair_action`、`validator`、`validated_at` 和 `evidence_refs`。交付前检查正式输出边界、required 产物完整性、验证证据、敏感数据和交付报告。

写回、发布、上传、覆盖、删除和恢复动作均登记 `effect_id`、幂等键、授权来源、执行前置条件、执行结果、后置验证和补偿方式。`rollback` 仅表示可控本地状态恢复；`compensation` 表示语义上的反向动作；`reconciliation` 表示重新探测外部真实状态。外部结果未知时不得盲目重复执行，也不得伪装成成功。

### 以适配器渐进迁移现有 Skill

`SkillAdapter` 负责读取旧 `run_id`、阶段和报告，并转换为统一事实；只能导入可证实的旧状态，无法确认时标记 `outcome=degraded` 或进入 `waiting/failed`，不得猜测成功。旧目录只读兼容，新运行优先使用锁定任务根目录和统一账本。

首批只覆盖三类最能检验核心的流程：

- `research-literature-review`：长流水线、网络阻塞、恢复和正式发布；
- `transfer-old-latex-to-new`：快照、受保护写入、编译和本地恢复；
- `research-idea`：候选分支、并行审查和结果汇聚。

`paper-write-sci`、`nsfc-qc` 和 `nsfc-reviewers` 在首批稳定后作为第二波迁移，不把试点数量误当成核心完整性。

### 建设无第三方运行时内核

实现独立的 `bensz-skill-kernel`，Python 3.10+、无运行时第三方依赖，同时提供稳定 Python API 和统一的 `bsk --...` CLI。`bsk` 是对外唯一需要记录在文档中的命令前缀，具体动作采用长选项形式，例如 `bsk --status`、`bsk --append-event` 和 `bsk --rebuild`；完整选项集合在实现契约冻结时再确定。`python -m` 不作为公开使用入口，可以仅保留为开发或故障诊断方式。

包名、导入名和目录边界固定如下：

- Python 发布包：`bensz-skill-kernel`；
- Python 导入包：`bensz_skill_kernel`；
- CLI 入口：`bsk`；
- Python 项目目录：`packages/bensz-skill-kernel/`；
- Python 源码：`packages/bensz-skill-kernel/src/bensz_skill_kernel/`；
- 已有 Agent Skills：`skills/<skill-name>/`；
- 运行时测试：`packages/bensz-skill-kernel/tests/`；仓库级 Skill 接入测试：`tests/`。

仓库采用以下最小布局，避免把 Python 源码、Skill 定义和测试夹具混在同一层：

```text
.
├── packages/
│   └── bensz-skill-kernel/
│       ├── pyproject.toml
│       ├── src/
│       │   └── bensz_skill_kernel/
│       └── tests/
├── skills/
├── tests/
│   ├── runtime/
│   └── skills/
├── docs/
└── CHANGELOG.md
```

内核只包含：事件追加、确定性投影、合法转移、证据登记、完成守卫、重试/恢复、摘要和 JSON 查询；Skill 的领域逻辑、阶段策略和适配器留在 `skills/` 或其接入层中。

当前目录迁移已落地：仓库内 23 个可安装 Skill 均已位于 `skills/<skill-name>/`，根级不再保留同名副本；安装器已用 `--source ./skills` 完成预览验证。旧根级布局仅作为外部仓库的显式兼容来源保留。

锁或 compare-and-swap 用于防止并发覆盖，但不把“协调者是唯一写入者”当作正确性证明。跨主机锁、远程同步和签名留到真实需求出现后再评估。

## 实施范围与顺序

### 固化包名、CLI 和目录边界

先在 `packages/bensz-skill-kernel/pyproject.toml` 中登记 `bensz-skill-kernel`、`bsk` 入口和 Python 版本范围，建立独立项目的源码、测试和发布边界；未来其它独立 Python 包分别在 `packages/<project>/` 下维护自己的 `pyproject.toml`。先验证安装后可以导入包并运行 `bsk --help`，再开始实现状态协议。

### 固化最小契约

先冻结四个核心概念、八个生命周期状态、事件 envelope、投影重建规则、核心不变量、完成守卫和副作用未知语义；同时明确 phase/子任务/重试是策略字段，不新增顶层状态。

### 实现运行时内核

实现事件追加、序号/哈希校验、确定性 reducer、原子投影、合法转移、证据登记、交付守卫、重试恢复和摘要查询。先用纯本地夹具验证，不接入真实 Skill。

### 接入三类试点

按“只读映射 → 统一事实写入 → 故障恢复 → 交付验证”的顺序接入三个试点。发现协议缺口时优先修改核心契约或声明式策略，不为单个 Skill 增加一次性特判。

### 扩大迁移和治理

首批稳定后，再按短报告、确定性闭环、项目写回、联网长流水线和并行汇聚的风险顺序迁移其余 Skill。协议变化必须增加 `runtime_control_version` 迁移说明和 `CHANGELOG.md` 记录。

## 如何确认完成

### 包与命令边界

- 安装开发包后可以导入 `bensz_skill_kernel`，且 `bsk --help` 能返回稳定的帮助和退出码。
- 核心操作的文档、测试和示例统一使用 `bsk --...`，不再把 `python -m` 作为公开 CLI 写法。
- `skills/` 下每个直接可安装目录仍以自身 `SKILL.md` 为识别边界，运行时源码不会被安装器误识别为 Skill。

### 核心正确性

- 删除或损坏 `state.json` 后，能仅凭事件重建相同投影；重复重放不会产生不同结果。
- 非法状态转移、重复序号、哈希断链、并发更新和任务锁失效都有确定性错误。
- required 产物、验证证据或交付报告缺失时，运行时拒绝进入 `completed`。
- `waiting` 的原因、恢复条件和下一动作能被机器查询和人类理解。

### 策略组合

- phase DAG 能阻止跳过 required 阶段、逆序执行和未验证交付。
- `all`、`quorum`、`best_effort` 及三种失败传播规则都有测试，父子结果传播可追溯。
- 多层 scope、重试产生的新 `attempt_id` 和部分交付不会覆盖旧证据。

### 副作用和迁移

- 写入成功但快照失败、快照成功但发布失败、补偿失败和外部状态未知均能进入明确的恢复或终止路径。
- 重复执行同一 `effect_id` 不造成重复副作用；未知状态必须先探测或人工确认。
- 三个试点的旧状态、旧目录和新事件可以相互解释，迁移不删除原始报告。

### 安全和边界

- 中间文件只在锁定任务根目录，正式输出不落入中间目录。
- 路径越界、密钥、Cookie、私人路径和不必要的敏感字段会被拒绝或清洗。
- 只读 Skill 不修改输入源；写回 Skill 记录授权、备份、差异、后置验证和恢复方式。

## 风险与待确认事项

- **状态收缩的兼容性：** 旧 `waiting_user` 和 `blocked` 需要映射为 `waiting + wait_reason`，对外文案由投影层兼容。
- **事实与投影不一致：** 必须把事件账本定为唯一事实来源，并为 reducer/projection 保留版本。
- **策略泄漏：** 任何 Skill 特例都先检查能否表达为 contract 字段，禁止继续扩大核心状态集合。
- **外部状态失配：** 文档和测试必须覆盖探测、补偿失败和无法确认的终止路径。
- **首批范围：** 三类试点已经确定，第二波 Skill 不作为首版完成条件；迁移期间不得因为单个 Skill 的特殊需求扩大内核状态集合。
- **版本兼容：** Python 3.9 是否支持、`bsk` CLI 的公开选项、规范源文件名、`state.json + events.ndjson` 的公开格式，以及 `completed + partial` 的最终对外文案，须在实现前冻结。

本计划只定义最小可落地的事实记录、状态投影、契约策略和迁移顺序；它借鉴 Git 式设计哲学的约束，但不把运行时设计成 Git 的替代品。
