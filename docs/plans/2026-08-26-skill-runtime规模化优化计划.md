# Agent Skill Runtime 规模化优化计划

## 通俗解释：究竟发生了什么

- **一句话说明：** 未来如果有大量用户使用许多不同的 Skill，单看最终输出很难知道问题发生在哪一步，也很难把一次用户投诉转化为可复用的改进经验。
- **具体场景：** 这像一套面向大量门店的标准服务系统。每家门店可以提供不同的菜品和服务，但都需要记录订单经过了哪些环节、哪一步出了问题、质检依据是什么，以及顾客反馈对应哪一张订单。
- **对应到本问题：** Skill 是门店，状态机是订单流程，Verifier 是质检环节，运行事件是可追溯的订单记录，用户反馈是售后工单；统一运行协议只规定记录和交接方式，不规定每家门店必须提供相同的菜品。
- **改变前后：** 现在 Skill 往往只留下最终文本，出现问题时需要重新猜测执行过程；改进后，可以定位到具体 Skill 版本、具体阶段、具体产物和具体验证器，再决定是修流程、修规则、修 Prompt 还是补充输入契约。

## 专业判断：问题在哪里

### 当前判断

引入状态机和验证器不是为了给 Skill 开发流程增加形式化步骤，而是为了建设一个可长期运行的 Skill Runtime。它需要支持大量 Skill、不同领域的专业流程和持续的用户反馈，同时避免把所有 Skill 强行压缩成一张相同的业务流程图。

现有相关设计已经提供了重要基础：

- `docs/plans/2026-08-24-skill状态控制体系设计.md` 已定义事实事件、状态投影、契约、证据、恢复和副作用边界；
- `docs/plans/2026-08-25-verifiers基础设施评估与落地计划.md` 已定义 Verifier Pack、Evidence Contract、规则/Prompt/混合验证、统一结果和 Gate；
- 本轮讨论进一步明确了规模化目标：运行记录必须能支持反馈归因、版本比较、问题回放和经验沉淀。

### 核心缺口

状态机和验证器本身还不足以承担严肃的生产环境，缺口主要在于它们之间以及与反馈系统之间的连接：

- 只有状态名，没有不可覆盖的事件账本，就无法可靠回答“当时发生了什么”；
- 只有验证结论，没有证据引用和版本信息，就无法判断是哪一个规则或 Prompt 产生了问题；
- 只有用户点赞/点踩，没有 `run_id`、阶段和产物关联，就无法把反馈转化为工程修复；
- 只有通用状态图，没有 Skill 自己声明的领域契约，就会为了统一而压平差异；
- 只有模型型 Verifier，没有校准集、回归测试和灰度回滚，就不能把它当作稳定的质量门禁。

### 设计结论

应建设“轻量公共协议 + Skill 自有状态图 + 可插拔 Verifier + 反馈治理闭环”的 Skill Runtime，而不是一开始建设强制所有 Skill 使用的全能工作流平台。

## 要达到什么目标

### 完成后的变化

- 每次 Skill 运行都有稳定的 `run_id`、Skill/Verifier/模型版本和可重放的事件记录。
- 状态机能阻止未满足前置条件的跳步，并支持等待、重试、暂停、恢复和人工复核。
- Verifier 能以结构化结果阻止确定性错误继续传播，并保留证据、发现、不确定原因和修复建议。
- 用户反馈可以关联到具体运行、阶段、产物和验证器版本，形成可回归的改进案例。
- 不同 Skill 可以共享运行时、事件、证据和反馈基础设施，同时保留自己的领域状态、术语和判断规则。
- Skill 的改进可以通过版本、校准、灰度和回滚进行管理，而不是直接覆盖线上行为。

### 不在本次处理范围

- 不要求所有 Skill 立即重写或强制接入完整状态机。
- 不设计一张覆盖所有领域的统一业务状态图。
- 不把状态机和 Verifier 用于管理 Skill 的开发、发布生命周期；本计划关注 Skill 被调用后的运行过程。
- 不默认收集用户全部原始输入、模型内部思维链或不必要的敏感信息。
- 不让用户单次反馈自动改写生产规则、Prompt 或 Gate。
- 不在首版建设分布式调度、训练平台、通用模型网关或复杂在线学习系统。

## 改进方向

### 明确 Skill Runtime 的分层边界

把公共能力收缩为“运行时薄腰部”：事件追加、状态投影、合法转移、证据引用、验证结果、Gate、暂停/恢复、摘要查询和反馈关联。

每个 Skill 自己声明领域状态图、阶段依赖、产物契约和 Verifier Pack。运行时只理解公共协议，不理解“检索”“写作”“临床推理”等领域动作的具体含义。

这项改变对用户意味着：不同 Skill 的专业体验仍然可以不同，但它们都能被可靠地追踪、暂停和复核。

### 固化可追溯的运行协议

统一以下最小对象，并与现有状态控制计划和 Verifier 计划对齐：

- `Run`：运行身份、Skill 版本、输入摘要、权限和预算；
- `Event`：不可覆盖的事实，包括状态变化、等待、错误、验证和交付；
- `Projection`：从事件历史重建的当前状态、阶段、等待原因、下一动作和结果摘要；
- `Artifact`：阶段产物、摘要、哈希、来源和生命周期状态；
- `VerificationResult`：执行状态、业务 verdict、finding、证据引用、验证器版本和不确定原因；
- `GateDecision`：是否允许状态转移或交付；
- `FeedbackCase`：用户反馈、关联运行、问题阶段、影响等级、修复版本和验证结果。

事件账本是事实来源，状态快照只是可重建的投影。任何无法确认的旧状态或外部结果必须进入未知/等待路径，不能猜测为成功。

### 把反馈闭环设计成一等能力

用户反馈至少分为：输入不足、流程跳步、工具/外部状态失败、Verifier 误判、输出质量问题、越权/安全问题和文档理解问题。

每类反馈都应关联：

- `run_id`、Skill 和版本；
- 发生问题的状态、阶段或产物；
- 相关 Verifier/Prompt/Rule 版本；
- 脱敏后的证据片段；
- 人工确认的根因和修复动作；
- 修复后的回归结果。

反馈先进入脱敏和人工确认流程，再沉淀为校准样例、回归测试、规则修订或 Skill 版本变更，避免单个异常直接改变生产行为。

### 建立 Verifier 的质量治理

每个重要 Verifier Pack 都应有版本、适用范围、拒绝范围、校准集和不确定性政策。至少维护：

- 已知通过、已知失败、部分支持、证据不足和对抗输入；
- 规则型验证器的确定性回归测试；
- Prompt 型验证器的人工标注集和抽样复核；
- 误报、漏报、`unchecked` 和人工升级率；
- 版本升级前后的差异、灰度结果和回滚点。

验证器只负责提供可复核事实和判断，不直接修改正式产物，也不绕过 Gate 改变运行状态。

### 采用渐进式接入，而不是全量重写

先选择两到三个具有明显阶段和不同风险的 Skill 作为试点，例如：

- 一个需要长链路检索、证据整理和正式报告的 Skill；
- 一个需要受限文件写回、编译或后置核验的 Skill；
- 一个需要候选分支、并行汇聚或人工复核的 Skill。

先实现只读事件映射和阶段验证，再加入统一事实写入、暂停/恢复和交付 Gate。试点期间出现协议缺口时，优先完善公共契约或声明式策略，不为单个 Skill 增加核心特判。

### 补齐规模化运行所需的治理能力

在进入大量用户使用前，增加以下控制：

- 事件和反馈的脱敏、最小化采集、留存期限和访问边界；
- 按风险和成本分层的验证策略，不对每次运行都执行最昂贵的检查；
- Skill、Verifier、Prompt、模型和运行时协议的兼容性记录；
- 新版本灰度、异常率监控、紧急停用和回滚；
- 多租户隔离、配额、超时、幂等键和外部副作用保护；
- 事件回放和离线评估环境，避免在线调试直接影响用户任务。

## 实施范围与顺序

1. **重新定位架构边界：** 将现有状态控制和 Verifier 设计明确归入 Skill Runtime，区分运行时状态与 Skill 开发/发布状态，并冻结公共对象的最小语义。
2. **建立最小运行协议：** 实现 `run_id`、事件账本、状态投影、验证结果、Gate 和反馈关联；先支持本地可重放，不急于建设远程服务。
3. **完成代表性试点：** 接入不同类型的 Skill，验证阶段恢复、错误阻断、证据追踪和领域差异保留。
4. **建设反馈与验证器治理：** 将用户反馈沉淀为校准案例、回归测试和版本变更，加入灰度、抽样和回滚。
5. **评估是否扩展平台：** 只有当试点产生可复用的协议、验证器和运行数据后，才提取更完整的通用 Runtime 或服务化能力。

## 如何确认完成

- 任一次试点运行都能从 `run_id` 回放到最终结果，并定位每个阶段的产物、验证器和版本。
- 非法跳步、缺少 required 产物、确定性验证失败和未知外部结果不能直接进入交付状态。
- 任务中断后可以从最近一个已确认阶段恢复，不重复执行已完成且可复用的工作。
- 用户反馈能够关联到具体 Skill 版本、运行阶段和 Verifier，并能转化为可回归案例。
- Verifier 版本变更可以进行离线比较、灰度发布和回滚，且不会静默改变历史结论。
- 不同试点 Skill 的领域状态和专业规则保持独立，公共 Runtime 不出现领域特判堆积。
- 采集的运行记录经过脱敏和最小化处理，具备明确的留存、访问和删除策略。
- 试点结果显示：流程跳步、重复工具调用、错误结果向后传播和无法归因的用户反馈均有可观测改善；若改善不明显，暂停平台化扩展并调整协议。

## 风险与待确认事项

- **状态机过度僵化：** 通过 Skill 自有状态图、可选接入和层级状态控制，不把所有领域动作升格为核心状态。
- **Verifier 产生虚假确定性：** 强制区分 `fail`、`unchecked`、`uncertain` 和 `manual_review`，并用校准集与人工抽样监控质量。
- **反馈侵犯隐私或造成成本失控：** 默认只保存摘要、哈希和必要证据，采用风险分层与采样策略，不收集无关原始数据。
- **协议过早平台化：** 首版只建设本地可重放的薄协议；没有跨 Skill 的真实复用证据时，不扩展成分布式平台。
- **版本漂移和回归：** 为 Skill、Verifier、Prompt、模型和运行时协议建立兼容性矩阵，所有生产变更经过灰度和回滚准备。
- **反馈自动改规则的风险：** 用户反馈只能产生候选改进，必须经过人工确认、回归验证和版本发布后才能进入生产。

本计划的最终决策是：**值得建设 Skill Runtime，但应先建设公共运行协议和反馈闭环，再根据试点证据扩大状态机与 Verifier 基础设施；不要先建设一个假设所有 Skill 都适用的“大平台”。**
