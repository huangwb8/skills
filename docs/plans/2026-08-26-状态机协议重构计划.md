# 状态机协议重构实施计划

## 通俗解释：究竟发生了什么

- **一句话说明：** 现有状态机能展示“有哪些阶段”，却不能让 Agent 以同一种方式读取阶段规则、执行阶段检查并留下标准结果。
- **具体场景：** 把状态机看成快递流程。现在的系统有一张“揽收、运输、签收”的说明卡，但各门店仍要自行决定怎样查卡、怎样盖章和怎样交接；改进后，说明卡、检查动作和交接回执会采用同一套格式。
- **对应到本问题：** 说明卡是每个目录内的 `STATE.md`，可选脚本是阶段检查或演示工具，回执是 CLI 输出的标准 JSON；工作区建立是每次任务必须先完成的“揽收”。
- **改变前后：** 现在自定义状态与系统状态无法合并执行，状态转移只存在于内存对象；改进后，Skill 能声明可用状态，Agent 可用一个命令取得定义、执行可选检查并把状态快照写入任务工作区。

## 专业判断：问题在哪里

- **当前现象：** `FilesystemStateRegistry` 已支持 `STATE.md` 的目录发现，但 `--root` 只能选择一个根目录，`StateMachine` 没有持久化或 CLI 入口，工作区清单只把 `workspace.ready` 写成字符串。状态定义也未规定可执行入口或统一结果。
- **影响范围：** 每个接入状态机的 Skill 都会重复拼接系统状态、领域状态、检查脚本和日志格式，难以让 Agent 按统一命令可靠理解和执行。
- **已知原因：** 当前实现先完成了“可发现”与“工作区路径”两个独立能力，尚未冻结两者之间的状态运行协议。

## 要达到什么目标

- **完成后的变化：** kernel 提供目录化状态包的组合发现、可选 JSON-stdio 脚本执行、不可变工作区状态快照和标准 JSON 结果；Skill 通过一份小型声明选择可用元状态及初始状态。
- **不在本次处理范围：** 不在 kernel 中定义检索、写作、临床分析等领域流程；不强制迁移所有 Skill；不把旧生命周期事件账本替换为领域状态机。

## 改进方向

### 冻结目录状态包与 Skill 声明契约

每个元状态仍由 `STATE.md` 描述，但补充可机器读取的操作契约：标识、版本、类别、前置状态、不变量、允许转移、可选 JSON-stdio 入口和输出要求。Skill 用独立状态声明文件列出使用哪些状态包和入口状态，避免业务流程进入 Python 代码。

这意味着开发者只需维护状态说明和辅助脚本，kernel 只负责按统一格式发现和执行。

### 合并系统状态与 Skill 状态，并提供统一操作入口

注册表保留内置系统状态，同时按指定根发现 Skill 状态；若标识重复则显式失败。新增 `bsk state` 操作子命令，用相同的 JSON 请求和响应格式描述状态、检查转移、执行入口并返回状态快照与证据引用。

这意味着 Agent 无须猜测文件路径或不同脚本的输出格式，就能通过一条命令理解并遵守状态要求。

### 将 BenszAPI 工作区作为持久化的初始系统状态

工作区初始化通过状态运行协议建立 `workspace.ready` 快照；Skill 状态以该状态为前置条件。状态快照与现有事件账本分层保存：前者管理“当前元状态”，后者保留生命周期、验证和交付事实。

这意味着每项工作一开始就有固定的中间文件边界，后续领域状态无法脱离该边界运行。

### 以一个 beta Skill 作为可复制示例

为 `validate-md-ref` 增加最小状态声明与一个领域状态包，展示如何从 `workspace.ready` 进入准备、验证和交付阶段，并更新其运行说明。示例不改变已有引用核验业务逻辑。

这意味着其它 Skill 有一个实际可运行的参考，而不是只能从内核源码推断接入方式。

## 实施范围与顺序

1. 先冻结状态包、组合注册表、请求/结果和持久化快照的最小协议。
2. 再实现 CLI、工作区衔接和测试，确保工作区始终是初始状态。
3. 最后为试点 Skill 写声明和状态包，并更新使用文档、版本与变更记录。

## 如何确认完成

- `bsk state list` 同时显示内置与指定 Skill 的状态；`describe` 返回完整契约。
- 可以用 CLI 从工作区初始状态验证或执行一个允许的领域转移，并得到标准 JSON；非法转移与非法脚本输出被拒绝。
- 工作区状态快照可重开、可读取，且不会取代事件账本。
- 包内定向测试覆盖发现冲突、声明解析、脚本执行、状态快照和工作区初始状态。
- `validate-md-ref` 的声明及说明能通过该 CLI 被实际读取。

## 风险与待确认事项

- JSON-stdio 脚本只能作为辅助检查；其副作用边界仍由 Skill 和用户授权控制。
- 现有未提交改动已经包含状态目录化原型，本次将在其基础上增量完善，不回退或覆盖无关修改。
