# Agent 执行证据链静态加固计划

## 通俗解释：究竟发生了什么

- **一句话说明：** 项目已经有流程、质检和日志，但部分关键规则仍依赖调用方自觉，可能出现“检查不合格却完成交付”的路径。
- **具体场景：** 把一次 Skill 运行想象成寄送重要文件：State 是物流节点，Verifier 是质检员，EventLog 是物流记录。现在节点、质检和记录都有了，但需要确保质检员判定“不合格”后柜台绝不会放行；两个工作人员同时操作时，也不能把同一个包裹编号写坏。
- **对应到本项目：** 把 Markdown 中的约定收紧成 Kernel 强制门禁，同时记录版本、授权、证据和关键动作。
- **改变前后：** 现在主要能重建生命周期投影；改进后还能证明为什么允许或拒绝完成，并在并发、重试、超时、权限不足和 helper 异常时安全停止。

## 专业判断：问题在哪里

- `runtime.py` 的完成保护主要检查 artifact、validation 和 delivery report，尚未把 required Verifier Gate、required phase、产物存在性与哈希完整绑定到完成条件。
- `EventLog.append()` 是“读取后计算序号再追加”，没有跨进程写入保护；相同幂等键也没有校验请求内容是否一致。
- `run_stdio()` 只约束入口路径，不限制 helper 的环境、网络、输出体积或资源消耗；错误详情可能直接携带 stderr。
- 请求、事件和 Verifier 结果的结构校验偏宽松，协议版本、字段类型和证据绑定仍不完整。
- 事件账本能重放状态投影，但尚未形成包含模型、提示词、工具、授权和上下文摘要的执行审计轨迹。

## 要达到什么目标

- 任何高风险完成都必须经过内核可验证的 Gate，不能靠额外写一条“通过”事件绕过。
- 事件账本在并发、重试和异常情况下保持一致，重复请求可识别，意图冲突会阻止执行。
- Pack helper 默认最小权限、有限资源、稳定错误类别和脱敏输出。
- 每次运行都能绑定 Skill、契约、Verifier、模型/提示词/工具和授权的版本摘要，并区分“状态投影重放”和“执行现场审计”。
- 保持向后兼容：旧事件和旧 CLI 仍可读取；新增字段采用可选兼容策略，破坏性协议变更单独迁移。

### 不在本次处理范围

- 不把领域业务规则搬进 Kernel。
- 不要求所有 Skill 都采用复杂状态机。
- 不接入真实远程写入、生产数据或第三方 Durable Execution 服务。
- 不把 EU AI Act、FDA、HIPAA 等法规文字硬编码为通用业务判断。

## 改进方向

### P0：收紧完成门禁，堵住“假通过”路径

把完成条件统一收敛到一个内核入口：required artifact、required phase、required Verifier 结果和 Gate 必须全部满足；`unchecked`、`uncertain`、`timed_out`、`manual_review` 不得自动进入完成态。产物必须经过文件存在、路径范围和内容哈希检查。

涉及 `runtime.py` 的 completion guard、`Contract`/`Requirement` 的 required 语义、Gate 投影和 runtime 测试。

### P0：保证事件账本在并发和重试下不损坏

为事件追加建立单写入或文件锁策略；幂等键绑定请求摘要，相同键但不同意图必须返回冲突；补充并发追加、重复执行、崩溃中断和恢复后的完整性测试。

涉及 `runtime.py` 的 `EventLog.append()`、幂等事件字段和 runtime 测试；不改写既有事件格式。

### P0：把 helper 边界从“路径安全”提升到“运行安全”

为 `run_stdio()` 增加输入和 stdout/stderr 大小上限、稳定错误类别、环境变量白名单和副作用声明；对不可信 Pack 禁止默认执行。无法提供真正沙箱时，文档必须明确当前只是进程级边界。

涉及 `packs.py`、State/Verifier helper 协议和非法 JSON、超时、超大输出、stderr 脱敏测试。

### P1：冻结一次运行的契约快照

为每次运行记录 Skill 版本、runtime 配置摘要、State/Verifier 版本、模型/提示词/工具标识、证据清单和契约摘要哈希。新增字段采用可选兼容策略。

涉及 workspace manifest、`EventEnvelope`、`VerificationRequest/Result`、README 和事件协议文档。

### P1：补齐身份、授权和委托链

把单一 `actor` 扩展为可选的责任主体、委托者、授权范围、审批引用和策略版本。远程副作用必须经过授权、幂等、执行后回查；未知状态进入等待或人工复核。

涉及 `Effect`、事件 payload、authorization-scope/remote 相关 Verifier 契约和远程 Skill Adapter；Kernel 不实现业务 API。

### P1：建立执行审计轨迹

定义运行开始、模型调用、工具调用、验证结果、Gate、人工批准、Effect 回查、交付和恢复等事件。保存输入输出摘要哈希，不把不必要的原文写进日志；实现不重新调用模型的离线审计回放。

这一步要明确：当前 `reduce_events()` 是状态投影重放，不应宣传为完整执行回放。后续再提供 OpenTelemetry 映射，不把第三方遥测依赖直接塞进 Kernel。

### P2：增加保证等级、覆盖率和失败回放指标

给 Verifier 标注确定性规则、混合判断、LLM judge 或人工判断等 assurance tier；统计 required 覆盖率、`unchecked/uncertain` 比例、Gate 放行率、回放成功率、关键失败步骤定位率、成本和延迟。用真实历史失败与受控 mutation 共同建立回归集。

## 实施范围与顺序

1. 先完成 P0 的完成门禁、事件并发/幂等和 helper 边界加固，用本地恶意输入与并发测试证明关键路径不能绕过。
2. 再完成 P1 的运行契约快照、身份授权和执行审计轨迹，确保新事件可向后兼容并能离线回放。
3. 最后根据至少一个真实 Skill 的失败样本补 P2 指标、校准集和 OTel 映射；只有复用稳定后才考虑提升为共享 Pack。

## 如何确认完成

- Gate reject 或 required verifier 缺失时，任何路径都不能进入 `completed`。
- 缺少 required phase、产物不存在、哈希不一致或路径越界时，完成操作失败并留下可解释事件。
- 并发追加不会产生重复序号、断裂哈希链或静默覆盖；幂等键意图冲突会明确失败。
- helper 超时、非法 JSON、超大输出、非零退出和敏感 stderr 都得到稳定、脱敏的结果。
- 旧事件和新事件均可 rebuild，结果确定且协议兼容。
- 给定 `run_id`，离线工具可以列出版本、证据、验证、授权、工具调用和交付链；回放不需要重新调用模型。
- 通过 Kernel 包测试、Pack discovery/index、canonical/alias、非法输入、超时、越界、并发和完成门禁测试；安装后仍能发现 Pack 资产。
- 完成 P0/P1 后进行“拔掉 runtime 适配器”回归，确认 Skill 原有入口和正式产物语义没有被破坏。

## 风险与待确认事项

- 文件锁方案必须兼容 macOS、Linux 和 Windows；否则应采用单写入者或 SQLite，不能假设 append 天然安全。
- 旧事件缺少版本字段时，新增事件协议必须提供兼容读取和默认解释，不得改写历史事件。
- helper 的真正沙箱能力取决于宿主环境；路径检查不能宣传成完整安全隔离。
- 身份字段需要先确定采用用户授权、服务账号授权还是委托链模型。
- 报告中的法规和行业失败率用于方向判断，不直接作为本项目的合规认证或性能承诺。
