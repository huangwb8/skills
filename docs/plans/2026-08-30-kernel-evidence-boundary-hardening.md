# Kernel 证据边界与状态持久化加固实施计划

## 通俗解释：究竟发生了什么

- **一句话说明：** 当前系统已经能记录验证结果和状态变化，但有三处“账本、凭证和门锁”没有完全对齐：调用方可以伪造放行凭证，状态账本和状态文件可能在崩溃时分叉，事件记录还可能带出用户本地路径。
- **生活类比或具体场景：** 把 Kernel 想成仓库的出库系统。Verifier 是质检员，Gate 是仓库主管签字，事件账本是出库流水，状态快照是货架上的当前标签。现在的问题是：有人拿着自制签字单也可能被当成主管签字；流水写完后标签还没换就断电；流水里还写了客户家里的完整地址。
- **对应到本问题：** Gate 对应 `verification.gate`，流水对应 `events.ndjson`，状态标签对应 `meta-state.json`，用户路径对应验证结果中的 `facts.path`、快照路径和交付路径。
- **改变前后：** 现在可能出现“失败结果却带 allow Gate”“事件显示新状态但快照仍是旧状态”“审计文件暴露绝对路径”。改进后，Gate 必须由 Kernel 根据结果重算，事件和快照要么一起生效要么都不生效，事件只保留脱敏路径或路径哈希。

## 专业判断：问题在哪里

- **当前现象：** `EventLog.record_verification()` 会把带有 `result_refs` 的调用方 Gate 自动标记为 `computed_by=kernel`，但没有重新运行 Gate 规则。完成门禁随后信任该标记。
- **当前现象：** 当前未提交改动新增了 Skill 状态事件，并在写入 `meta-state.json` 前追加事件；崩溃窗口会造成事件账本与快照不一致，且缺失快照目前被重建逻辑容忍。
- **当前现象：** 验证结果长期以原始 Mapping 写入事件，可能包含 `facts.path` 等绝对私有路径；未提交改动又把绝对 `snapshot_path` 写入状态事件。
- **影响范围：** 任何直接调用 Kernel 公开 API 的 Skill/适配器都可能触发这些问题。最严重的影响是完成状态被错误放行；其次是恢复时无法确定真实状态；隐私问题会扩大中间账本的暴露面。
- **已知原因：** Gate 自动标记来自已提交 `074feea`；验证结果原样保存始于 `8fee842`；状态事件与快照的跨文件写入顺序来自当前未提交 diff。当前未提交的运行身份绑定和不变量检查属于已有加固，不是这些问题的根因。

## 要达到什么目标

- **完成后的变化：** Kernel 只接受可重算、可绑定、可审计的 Gate；状态事件和快照具备明确的一致性恢复策略；事件日志默认不保存绝对私有路径或敏感原文。
- **不在本次处理范围：** 不改变 `validate-md-ref` 的业务判定规则；不把 instruction-only Verifier 改造成自动语义判断；不重写整个事件协议；不删除既有历史事件，而是提供向后兼容的读取和迁移策略；不执行远程发布或 Git 提交。

## 改进方向

### Gate 可信边界：由 Kernel 计算并绑定结果

将 `record_verification()` 的 Gate 输入收紧为 Kernel 可验证的结构：调用方只能提交结果和需求声明，或提交一个明确的 `GateDecision` 候选；Kernel 必须基于同一批结果、同一组 required/optional requirements 再运行 `apply_gate()`，然后才写入 `verification.gate`。

持久化前同时校验：结果的 canonical verifier ID 与版本、Gate 的 `result_refs` 完整覆盖结果、`result_event_id` 指向本次结果、Gate 的 decision/unresolved 与重算值一致，以及 `run_id/attempt_id` 一致。`computed_by=kernel` 只能由这条成功的 Kernel 路径产生，不能由字段存在与否触发。

完成门禁也要按当前运行筛选结果和 Gate，避免历史运行的结果或旧 Gate 满足新任务；对于 required verifier，失败、缺失、`unchecked`、`uncertain`、超时均应保持 fail-closed。

普通用户看到的变化：验证结果不能再靠手写一个 `allow` 字段绕过最终检查，审计记录能说明“为什么放行”。

### 状态快照原子性：统一提交、恢复和缺失策略

为 Skill 状态转移设计单一提交协议，避免分别修改 `events.ndjson` 和 `meta-state.json`。优先采用可恢复的两阶段顺序：先生成并校验快照暂存内容，再在事件中写入稳定的 snapshot hash 和版本，最后以原子替换完成快照；若任一步失败，恢复逻辑必须能识别未完成提交并拒绝继续，而不是静默接受分叉状态。

同时明确历史兼容策略：旧事件没有快照字段时继续只读兼容；新事件只要声明了 `snapshot_hash/snapshot_path`，快照缺失、不可解析或哈希不匹配都应进入 `integrity_error`，不能继续重建为“看似成功”的投影。验证所有历史状态事件，而不只检查每个 Skill 的最后一条，或明确记录只校验最新快照的风险。

普通用户看到的变化：系统崩溃或被中断后会明确提示“状态未完成提交”，不会出现账本和当前状态各说一套。

### 事件隐私过滤：把审计证据与私有原文分开

在事件写入的公共边界建立统一脱敏函数，而不是只在 `record_audit()` 中处理少数字段。验证结果、Gate、状态快照和交付事件都要经过同一规则：绝对路径转换为项目内相对路径、稳定路径哈希或脱敏标签；prompt、文档内容、stdout/stderr 等原文只保存哈希；敏感键和值递归脱敏；错误消息不能回显完整输入或凭据。

保留足够的复核能力：事件仍能通过 content hash、artifact ID、evidence ref、运行身份和 pack/version 定位证据，但不把原始私有路径写进共享账本。对旧事件只读兼容，不在本次计划中批量改写历史链，必要时提供脱敏导出视图。

普通用户看到的变化：审计仍可重放和追责，但把日志交给其他人时不会顺带暴露本机目录结构。

## 实施范围与顺序

1. 先在 Verifier/Gate 层固定可信边界和运行身份绑定，因为完成门禁的正确性优先级最高；补齐伪造 Gate、历史 Gate 串台和 required/optional 组合的失败测试。
2. 再实现状态事件与快照的一致性协议，补充崩溃窗口、缺失文件、哈希漂移、重复重试和旧事件兼容测试；完成后才把当前未提交的状态事件改动纳入可提交范围。
3. 最后统一事件脱敏出口，覆盖 verification、state、delivery 和 audit 四类事件，并用私有路径/敏感字段夹具验证“可定位但不泄露”。
4. 将三部分接入同一套回归矩阵，再运行 Kernel、`validate-md-ref` QA、编译、Pack 发现和 BAC 校验；人工复核公开事件样例后，才决定是否提交。

## 如何确认完成

- 伪造 `allow` Gate、失败结果、缺失 required verifier、旧运行 Gate/结果串台时，完成转移均被拒绝。
- 合法 Gate 必须能由 Kernel 从结果重算得到；事件中的 `computed_by`、`result_event_id`、`result_refs` 和 run/attempt 身份彼此一致。
- 状态事件与快照在正常、重复、崩溃恢复和损坏场景下不会产生静默分叉；声明了哈希的快照缺失或漂移会返回稳定的完整性错误。
- 事件日志中不出现绝对用户路径、文档原文、prompt、stdout/stderr 或敏感值；仍能通过 hash/ref 重放审计关系。
- 运行现有 Kernel runtime 测试、`validate-md-ref` QA 和新增边界测试；再执行 `compileall`、`git diff --check`、Pack/index 一致性检查和 `bac verify`。
- 通过人工抽查一份“正常通过”、一份“manual_review”、一份“失败/中断恢复”的脱敏事件链。

## 风险与待确认事项

- **协议兼容：** 新 Gate 字段校验可能拒绝过去可接受的宽松输入，需要决定是直接 fail-closed，还是提供明确版本迁移入口。
- **历史账本：** 不建议重写既有哈希链；应确认审计工具是否需要“旧事件原样读取”和“脱敏导出”两种视图。
- **提交边界：** 当前未提交 diff 同时包含状态事件、快照校验、版本和文档改动。完成上述测试前，不应把它们拆散提交，以免只提交半套一致性协议。
- **终态语义：** `reported`、`workspace.closed` 和任务级 `completed` 仍需在 Skill 契约中保持区分；本计划不默认把 `manual_review` 改成自动失败，但任务级完成必须使用严格 Gate。
