# State/Verifier 共用 Contract Pack 执行层优化计划

## 通俗解释：究竟发生了什么

- **一句话说明：** 当前 State 和 Verifier 都已经支持“自然语言契约 + 可选脚本”，但两者只共享了目录发现和脚本进程边界，没有共享一套完整的契约执行、Agent 交接和混合结果记录机制。
- **具体场景：** 一个验收工位可以用尺子测量，也可以让专家按说明书判断，还可以要求主管签字。State 和 Verifier 现在各自有一套说明书和验收回执；它们已经共用取号、隔离房间和记录柜，却没有共用“如何安排尺子、专家和签字人”的验收流程。
- **对应到本问题：** `STATE.md`/`VERIFIER.md` 是契约；`scripts/verify.py` 或 State helper 是确定性工具；按正文执行的 Agent 是语义检查者；人工复核是授权确认；State 负责“是否允许转移”，Verifier 负责“命题是否成立以及是否放行”。
- **改变前后：** 现在各个 Skill 需要自行约定如何让 Agent 读取契约、组合脚本结果和记录人工判断；改进后，State 和 Verifier 共用一个底层 Contract Pack 执行层，再由各自适配器解释结果，不要求所有检查都写成代码，也不要求所有检查都交给模型。

## 专业判断：问题在哪里

- **已经存在的能力：** `packs.py` 已经为 State 和 Verifier 共用索引发现、目录/契约校验、入口路径约束、JSON-stdio、超时和输出限制。两类 Pack 也都以 Markdown 契约为主要人类可读入口，并允许没有脚本时由 Agent 按正文执行。
- **State 已体现目标模式：** `checking/STATE.md` 明确要求 Agent 执行 instruction-only 或 semantic review；没有 helper 的 State 不是“死代码”，而是等待 Agent 按契约完成阶段工作。
- **Verifier 的现状：** `VerifierSpec`/`VerifierPack` 已有 `rule`、`prompt`、`hybrid`、`human` 抽象，内存 `VerifierRunner` 可以运行 rule/prompt 组件；但目录型 Verifier 仍主要按“有一个 entrypoint/没有 entrypoint”处理，Agent 交接和混合编排没有统一协议。
- **核心缺口：** State 和 Verifier 都缺少共享的执行计划、组件模型、Agent/human 交接对象、组件依赖与合并策略；因此自然语言、脚本和人工方式虽然“可以用”，却主要靠外部 Skill 自己拼接。
- **语义边界不能直接合并：** State 的结果要约束状态转移和 invariant；Verifier 的结果要产生 verdict 并参与 Gate。二者不能共用同一个最终结果对象，但可以共用“契约如何被执行、证据如何被绑定、执行如何被审计”的底层。
- **不处理的后果：** 新增混合能力会继续复制到各个 Skill；不同适配器可能漏跑组件、让语义结果覆盖精确失败、丢失证据引用，或无法说明某次判断究竟使用了哪版契约和哪组输入。

## 要达到什么目标

### 完成后的变化

- 建立 State 和 Verifier 共用的 Contract Pack 执行层，统一契约发现、版本/alias、正文和索引元数据、契约哈希、执行组件、证据快照、执行者交接、结果归一化和审计绑定。
- 一个 Pack 可以按功能选择 `script`、`agent`、`human` 或它们的组合；纯规则、纯自然语言、纯人工和混合方式都使用同一套底层协议。
- Agent 可以获得明确的契约、最小 subject/context、证据摘要和输出要求，并把自然语言判断回传为标准组件结果；Kernel 不捆绑具体模型，也不假装自己完成了语义判断。
- State 适配器将通用组件结果解释为进入/离开条件、transition 和 invariant；Verifier 适配器将其解释为 verdict、required/advisory 和 Gate。
- 混合结果采用保守语义：required 的精确失败不能被 AI 覆盖；缺证据、模型不可用、不确定、超时和未完成人工确认都保留原状并进入等待或人工复核。
- 结果能够绑定 Pack/组件/契约版本、内容哈希、证据引用、run/attempt、执行者或模型和 Gate，同时不把 Prompt、凭据、文档原文或不必要的本地路径写入共享账本。
- 既有 State/Verifier API、单入口脚本、alias、Runtime 完成门禁和历史事件读取保持兼容；已有确定性 Pack 不必因引入通用层而重写。

### 不在本次处理范围

- 不在 Kernel 内捆绑 OpenAI、Anthropic 或其它模型 SDK，不建设通用模型网关或调度平台。
- 不把所有 State/Verifier 合并为同一种领域对象，不把 State transition 或 Verifier Gate 规则塞进通用执行器。
- 不建设一个包办所有领域的超级 Prompt，不把医学、科研、写作等领域判断硬编码进 Kernel。
- 不改变现有 Gate 的 fail-closed 原则，不把 `unchecked`、`uncertain`、超时或人工未确认降级成自动通过。
- 不在首轮重写 `runtime.py` reducer 或批量迁移所有 Skill；只提供兼容接入点和一个端到端混合示例。

## 改进方向

### 抽象 State/Verifier 共用的 Contract Pack 描述

在现有 `packs.py` 的发现与进程边界之上，增加通用的契约描述和执行计划概念。它应统一表达 Pack 的 canonical ID、版本、alias、契约路径、契约内容哈希、执行组件、组件类型、输入证据、顺序/依赖、required 标志、assurance 和副作用边界。

`index.json` 应成为可机器读取属性的单一来源，显式声明组件和 `script`/`agent`/`human` 能力；`STATE.md` 与 `VERIFIER.md` 继续承载命题、阶段含义、判断边界和 Agent 操作说明。旧的单入口 Pack 兼容解释为一个 `script` 组件，没有组件声明的旧文档继续可被发现，但新版本应给出缺失元数据提示。

普通用户看到的变化：查看一个 State 或 Verifier 时，能知道它需要哪些检查者、哪些材料和哪种执行方式，而不是只看到“有没有脚本”。

### 建立通用组件执行与 Agent/human 交接协议

为三类执行者定义统一输入输出边界：

- `script`：复用现有 JSON-stdio 和安全执行限制，返回结构化组件结果；
- `agent`：由外部 Codex/Claude 等 Agent 读取契约并进行自然语言判断，Kernel 提供准备交接的请求和提交结果的校验，不依赖具体模型；
- `human`：生成待确认事项和证据摘要，接收带执行者身份和确认时间的人工结果。

通用交接请求至少包含契约/组件哈希、最小 subject/context、证据 refs 与摘要、输出 Schema、允许的工具/副作用和不确定性规则。提交结果至少包含组件 ID、执行状态、结论、finding/facts、证据 refs、执行者类型、模型或人工来源和不确定原因。原始 Prompt、模型输出和敏感证据只保存哈希或受控引用。

普通用户看到的变化：Agent 不需要自行猜测如何组织验证任务；它可以按标准请求读取说明并返回一份可被 Kernel 检查的验收结果。

### 由 State/Verifier 适配器解释通用结果

通用执行层只负责“组件执行完了什么”，不决定领域含义。新增或整理两个薄适配器：

- `StateContractAdapter`：把组件结果映射到状态的 entry/exit 条件、transition helper 和 invariant；没有 Agent/人工结果时不能声称阶段条件已满足。
- `VerifierContractAdapter`：把组件结果映射到 Verifier 局部 verdict、required/advisory 需求和 Gate；脚本、Agent、人工结果可以属于同一个 Verifier，但组件结果与汇总结果必须分开记录。

这样可以复用 State 已有的 `execute_state()` 思路和 Verifier 已有的 `VerifierRunner`/`FilesystemVerifierRegistry`，逐步把重复的请求、错误和结果处理下沉到通用层，而不破坏 State 图或 Verifier Gate 的语义。

普通用户看到的变化：同一种 Agent/脚本执行方式可以服务“是否允许进入下一阶段”和“引用是否支持论断”两类任务，但系统仍会用不同规则解释最终结论。

### 实现保守的混合编排和结果合并

通用编排器按执行计划运行组件并传递受控事实：先执行可用的脚本组件，再把脚本事实和证据摘要交给 Agent 或人工组件，最后交给 State/Verifier 适配器汇总。首版只支持少量可解释策略：

- `all_required`：所有 required 组件必须完成并通过；
- `rule_failure_blocks`：required 规则失败不可被语义组件覆盖；
- `semantic_uncertainty_requires_review`：Agent 不确定、缺证据或模型不可用进入 `manual_review`/`wait`；
- `human_confirmation_required`：声明人工确认的组件必须产生有效确认结果。

不要用平均分、投票或自由文本覆盖精确失败。脚本可以只负责证据收集，Agent 可以只负责语义解释，人工可以只负责高风险确认；每个组件的职责和结论都要保留。

普通用户看到的变化：一个引用 Verifier 可以先检查 DOI/链接和证据字段，再让 Agent 判断是否支持论断；一个 State 可以先检查输入文件，再让 Agent 判断是否达到阶段目标。

### 统一契约、证据和执行审计

扩展通用结果和事件绑定信息：Pack/契约哈希、组件/执行计划哈希、证据快照 refs、run/attempt、执行者、模型或人工确认来源、结果事件关联和必要的 Prompt/Rubric 哈希。契约、脚本或执行计划发生不兼容变化时升版本；同一版本内容漂移必须被发现并拒绝静默重放。

复用现有 `runtime.py` 的 Kernel Gate 重算、结果事件绑定、State invariant 和 completion guard；不让调用方通过手写 `allow` 或伪造“已执行 Agent”字段绕过门禁。统一脱敏出口，确保可通过 hash/ref 重建关系，但不保存敏感原文。

普通用户看到的变化：复查一次通过或待复核结果时，可以知道使用了哪份契约、哪组证据、哪个组件和哪种执行者。

### 用一个跨 State/Verifier 示例验证底层抽象

不要先批量重构所有内置 Pack。先建立一个最小端到端示例：脚本检查证据结构，Agent 按自然语言契约判断语义，必要时人工确认；同一通用执行记录分别被 State 适配器用于阶段转移、被 Verifier 适配器用于 verdict/Gate。示例应覆盖通过、规则失败、语义不确定、人工等待和超时五条路径，再据此决定哪些字段是真正公共能力。

同步更新 `STATE.md`/`VERIFIER.md` 最小模板、`docs/state-machine-tutorial.md`、`docs/verifier-tutorial.md`、Kernel README、Pack/ID 文档和 CHANGELOG，明确“契约由 Agent 读取”与“Kernel 自动执行脚本”是两种不同但可组合的路径。

## 实施范围与顺序

1. **冻结公共契约。** 盘点现有 `packs.py`、`states.py`、`verifiers.py`、`builtins.py`、索引和事件字段，定义通用 Pack 描述、组件、执行计划、Agent/human 交接、契约哈希和旧格式兼容规则。
2. **下沉通用执行层。** 在不改变 State transition 或 Verifier Gate 的前提下，复用现有目录发现、入口安全和 JSON-stdio，新增通用组件执行/结果归一化能力；为脚本、Agent、人工三种执行方式定义稳定协议。
3. **接入两个语义适配器。** 让 State 的 helper/instruction-only 路径和 Verifier 的 filesystem/in-memory 路径都能消费通用组件结果；保留旧 API 作为兼容外观，避免形成第三套平行注册表。
4. **实现混合编排。** 先落地脚本 → Agent/人工 → 适配器汇总的最小路径，固定失败优先级、等待/复核语义和组件证据传递；将结果写入现有 Runtime 事件和 State checking/完成门禁。
5. **完成跨域示例和内置迁移。** 用一个 State 与一个 Verifier 共享同一执行层完成端到端回归，再为内置 Pack 显式补齐 mode、组件和 assurance 元数据；`citation-truth-fit` 保持语义型示例，不伪装为 Kernel 内置模型判断。
6. **渐进启用与文档收敛。** 先旁路记录并比较新旧结果，再对稳定的纯规则组件启用 required Gate；AI/人工组件在审计证据充分前保持 `manual_review` 或显式等待。同步版本、CHANGELOG、README、教程和 BAC。

## 如何确认完成

- State 和 Verifier 能从同一套 Contract Pack 描述中发现 ID、版本、契约哈希、组件类型、顺序和副作用边界；旧单入口 Pack 仍可运行。
- 同一个通用执行器可以分别运行脚本组件、准备 Agent 交接、接收人工确认，并将结果交给 State 或 Verifier 适配器；不需要特定模型 SDK。
- State 的自然语言阶段手册可以由 Agent 执行并形成可审计组件结果；Verifier 的自然语言判断可以与脚本结果合并；两者最终仍分别遵守 transition/invariant 与 verdict/Gate 规则。
- required 规则失败不可被 AI 或人工的自由文本覆盖；`unchecked`、`uncertain`、超时、缺证据和未确认结果不会自动完成任务。
- 结果和事件包含 Pack/组件/契约绑定、证据 refs、run/attempt 和执行者信息；不出现凭据、完整 Prompt、文档原文或不必要的绝对本地路径。
- 契约或执行计划内容漂移、组件漏跑、顺序错误、重复提交、结果身份不符和历史运行串台都会被检测并 fail-closed。
- 旧 alias、旧事件读取、现有 CLI 和 `build_builtin_registry()` 兼容入口继续工作；新协议不兼容时有明确版本错误和迁移说明。
- 自动化测试至少覆盖：Pack/index 一致性、State/Verifier 共用执行器、脚本/Agent/human 三类结果、混合合并策略、缺证据、超时、契约哈希漂移、事件回放、State invariant、Verifier Gate 和 completion guard。
- 运行包内 pytest、Pack discovery/index 检查、`compileall`、`git diff --check` 和 `bac verify`；人工抽查一条纯规则通过、一条 Agent `manual_review`、一条混合规则失败和一条人工确认通过的脱敏事件链。

## 风险与待确认事项

- **公共层边界：** 需要在设计阶段确认通用执行层只处理组件执行和证据交接，不把 State transition、Verifier Gate 或领域判断下沉进去。
- **Agent 交接形式：** 首版可只提供 Python API，或同时提供薄 CLI；无论选择哪种，Agent 都必须由外部宿主执行，Kernel 不承担模型调用。
- **结果可信度：** Kernel 可以验证结构、版本和证据绑定，不能证明模型真正遵守了自然语言契约；高风险判断仍需人工确认、校准集或独立证据。
- **兼容迁移：** 从“有入口即 rule”的默认推断迁移到显式组件声明时，应先兼容读取并发出诊断，再在新协议版本中要求完整声明。
- **审计隐私：** 契约哈希、Prompt/Rubric 哈希和证据摘要必须足以定位执行版本，但不能把敏感原文、凭据或用户私有路径带入共享事件。
- **范围控制：** 本计划优化的是 State/Verifier 共用底层执行能力，不默认修改所有 Skill、重写 Runtime reducer 或引入分布式模型调度。

## 技术补充（按需阅读）

建议以现有模块增量演进：`packs.py` 继续负责 Pack 发现与进程边界；可在其上新增通用 Contract Pack/组件执行模块；`states.py` 保留状态图、invariant 和 State 结果适配；`verifiers.py` 保留请求、证据、verdict、Gate 和 Verifier 结果适配；`builtins.py` 继续作为兼容注册入口；`runtime.py` 继续负责事件、完成门禁和回放。

首个回归样例应同时证明两件事：同一个“脚本 + Agent + 可选人工”执行链可以被 State 和 Verifier 复用；复用底层并不会混淆“允许状态转移”和“验证命题通过”这两个不同语义。确认该样例的事件链可回放后，再决定是否批量迁移内置和 Skill 本地 Pack。
