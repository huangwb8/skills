# AGENTS.md 与 Skill 正文规范化优化计划

## 通俗解释：究竟发生了什么

- **一句话说明：** 现在的 `AGENTS.md` 已经规定了不少 Skill 开发原则，但没有把 `SKILL.md` 的正文排成固定的阅读路线，因此不同 Skill 可能用不同标题和顺序表达相同内容。
- **生活类比或具体场景：** 这像一套仓库要求所有人填写“出库单”，但只规定必须填信息，没有规定栏目顺序。有人先写货物，有人先写审批，有人把注意事项另附一页；内容可能都在，复核却要重新找。
- **对应到本问题：** `SKILL.md` 是出库单，`AGENTS.md` 是填写规则，`docs/` 是详细的仓储、审批和编号手册；当前缺少一个固定的单据骨架，以及这些手册之间的清晰索引关系。
- **改变前后：** 现在创建 Skill 时，AI 可能自由选择“目的、步骤、注意事项、验证”等标题；改进后，新 Skill 按固定的 `## 目标`、`## 流程`、可选 `## 控制`、`## 约束` 组织，复杂规则链接到对应 `docs/` 文档，检查器可以直接发现缺项。

## 专业判断：问题在哪里

- **当前现象：** `AGENTS.md` 的“技能开发流程”和“SKILL.md 标准结构”已经覆盖 frontmatter、`config.yaml`、脚本路径和质量原则，但没有规定正文一级标题、`流程` 必须包含的输入/步骤/输出/校验/失败处理，也没有建立公共模板目录。
- **文档关系现状：** 工作区、State、Verifier、State ID 和 Verifier ID 已有独立说明；这些文档适合承担详细契约，但 `AGENTS.md` 尚未把它们组织成 Skill 作者可遵循的入口地图。
- **主要影响：** 人类审查需要在不同 Skill 中寻找同类信息；AI 生成内容的结构有较大随机性；公共约束复制到各 Skill 后容易漂移；把所有细节继续堆进 `AGENTS.md` 会使治理入口过长且与专题文档重复。
- **待验证假设：** 运行环境通常优先加载 `SKILL.md`，不会自动读取所有 `references/` 文件，因此不能把关键约束完全隐藏在一个外部引用中；需要通过安装后发现测试或现有宿主验证这一点。

## 要达到什么目标

- **完成后的变化：** 新建或修改的 Skill 都有稳定、可读、可检查的正文骨架；执行者能从 `SKILL.md` 找到与工作区、BAC、State、Verifier、命名和故障处理对应的详细文档。
- **治理分层：** `AGENTS.md` 只保留不可违反的规则、入口和验收门禁；`docs/` 保存跨 Skill 的长说明和模板；每个 Skill 的 `SKILL.md` 保存自身触发边界、输入输出和领域流程。
- **兼容性：** 普通 Skill 不因新规范而默认接入 State、Verifier、Pack 或 Gate；只有明确采用控制组件时才触发相应专题文档和门禁。
- **不在本次处理范围：** 本计划不直接重写全部现有 Skill，不改变 Kernel 协议，不默认引入状态机/验证器，不修改已发布 Skill 的领域语义，也不把 `AGENTS.md` 变成所有专题文档的全文副本。

## 改进方向

### 方向一：固定 `SKILL.md` 的正文骨架与最低内容

在 `AGENTS.md` 的 Skill 开发规则中，将以下一级章节设为规范顺序：

```markdown
## 目标
## 流程
## 控制（按需）
## 约束
```

其中 `目标` 必须说明用途、触发边界和不负责的范围；`流程` 必须至少包含 `输入`、`执行步骤`、`输出`、`输出管理`、`校验`、`失败与恢复`；`控制` 仅在使用 State、Verifier、Gate、Pack 或其它治理组件时出现，并说明组件、调用时机、证据、通过条件和人工介入；`约束` 必须覆盖工作区、BAC、隐私、文件边界和 `bensz-collect-bugs` 协作要求。

这项改变对使用者意味着：打开任意 Skill，都能在相同位置找到“它做什么、怎么做、由谁控制、有哪些不能违反的规则”。

### 方向二：建立 `docs/` 的模板与专题文档入口

后续实施时新增 `docs/templates/`，至少包含：

- `skill-body.md`：只提供四段式正文骨架和二级标题提示；
- `skill-common-constraints.md`：公共约束的权威长版本，涵盖 `.bensz-api`、BAC、隐私和 bug 协作。

建议把模板源文件视为维护入口；Skill 内的 `references/` 副本仅服务运行时读取，并由生成器或静态检查器检查同步关系。`SKILL.md` 仍保留关键约束摘要，并明确要求在需要时读取副本，避免某些宿主只加载 `SKILL.md` 时丢失安全边界。

同时在 `AGENTS.md` 中增加专题文档索引：

| Skill 场景 | 规范入口 | `AGENTS.md` 的职责 |
| --- | --- | --- |
| 中间文件、任务目录、证据和日志 | [`docs/bensz-api-workspace.md`](../bensz-api-workspace.md) | 要求遵守并指向详细契约 |
| State、Verifier、Gate 协作 | [`docs/state-machine-tutorial.md`](../state-machine-tutorial.md)、[`docs/verifier-tutorial.md`](../verifier-tutorial.md) | 声明显式采用条件和边界 |
| State ID / Verifier ID | [`docs/state-id-naming.md`](../state-id-naming.md)、[`docs/verifier-id-naming.md`](../verifier-id-naming.md) | 要求采用控制组件时遵循命名门禁 |
| 公共 Skill 约束 | `docs/templates/skill-common-constraints.md` | 规定模板来源、摘要和同步检查 |

这项改变对使用者意味着：`AGENTS.md` 像目录和交通规则，专题文档像操作手册，Skill 自己只描述实际业务，不必重复整套基础设施说明。

### 方向三：用轻量静态检查把格式要求变成可执行门禁

新增仓库级 Skill 结构检查（具体脚本位置在实施阶段根据现有工具布局决定），检查范围至少包括：

- YAML frontmatter 可解析，`name`、`description` 和 `metadata.author: Bensz Conan` 存在且一致；
- 必选一级标题存在且顺序正确，`控制` 的出现与配置中实际声明的控制组件相符；
- `流程` 的最低二级标题齐全，且没有把输出、校验或失败处理完全省略；
- `约束` 含公共约束摘要及工作区、BAC、隐私、bug 协作入口；
- 相关 `references/` 文件存在，模板副本与 `docs/templates/` 的版本或哈希关系可追溯；
- 文档链接可定位，版本仍以 `config.yaml` 为单一来源。

检查器应先支持报告模式，再作为 `alpha` 发布门禁；对已有 Skill 先生成缺项清单，不因一次规范升级强行重写所有历史文件。

这项改变对使用者意味着：结构问题在提交前就能被指出，不必等到人工阅读完整 Skill 后才发现缺少输入契约或失败路径。

### 方向四：分阶段迁移现有 Skill，并同步治理记录

实施时按以下顺序推进：

1. 先更新模板和 `AGENTS.md` 规则，明确“新建或修改的 Skill 必须遵守”；
2. 用检查器扫描 `skills/alpha/` 与 `skills/beta/`，按缺失章节、引用缺失、模板漂移分类；
3. 优先迁移高频、基础性或最近维护的 Skill，保持领域语义不变，只调整标题、引用和约束位置；
4. 为 `references/` 副本建立同步策略，并在安装后环境验证 Skill 仍可发现；
5. 经过一轮报告模式稳定后，再决定是否将结构检查升级为发布阻断；
6. 实际修改 `AGENTS.md`、模板、检查器或 Skill 时，在根级 `CHANGELOG.md` 的 `[Unreleased]` 记录变更范围，并用 BAC 记录需求、工具结果和验证证据。

这项改变对使用者意味着：旧 Skill 有明确的迁移路径，新 Skill 从第一天就使用统一格式，规范不会因为一次治理调整而造成大面积不可控重写。

## 实施范围与顺序

1. **整理规范边界：** 对照当前 `AGENTS.md` 和已有 `docs/`，删除重复表述，定义四段式正文、专题文档引用规则、公共约束摘要和控制组件的显式采用条件。
2. **建立公共模板：** 在 `docs/templates/` 增加正文骨架和公共约束模板，并写清权威源、Skill 副本、更新和同步方式。
3. **更新 `AGENTS.md`：** 将固定结构、文档路由、模板使用、报告/阻断阶段和迁移要求写入 Skill 开发章节；保留工作区、State/Verifier 和版本兼容的最小不可违反规则，并链接详细文档。
4. **实现检查与迁移：** 增加结构/引用/模板一致性检查，先扫描并报告现有 Skill，再选择代表性 Skill 做小范围迁移验证。
5. **完成治理闭环：** 更新 README 或开发入口（如受影响），同步 `CHANGELOG.md` 和 BAC，运行文档链接、安装发现及必要的轻量 Skill 检查。

## 如何确认完成

- 新建一个最小 Skill 时，生成结果包含规定的一级章节和 `流程` 二级标题；缺少必选项时检查器能稳定报告。
- 一个不使用 State/Verifier 的普通 Skill 不会被误判为必须接入 `控制`；显式声明控制组件的 Skill 会被要求补充组件、证据和失败处理说明。
- `AGENTS.md` 能把作者分别引导到工作区、State/Verifier、ID 命名和公共约束文档；详细文档与治理入口之间没有互相矛盾的默认值。
- 模板源与 Skill `references/` 副本的同步状态可被检查；模板更新后能明确指出受影响的 Skill。
- 现有代表性 alpha/beta Skill 通过报告模式扫描，迁移后的样例通过结构、链接和安装发现检查，且领域行为没有改变。
- `CHANGELOG.md` 有对应的 `[Unreleased]` 记录，BAC 账本可验证；验证产物位于 `.bensz-api/` 或规定的 `tmp/`，没有污染 `tests/`、Skill 源目录或正式交付路径。

## 风险与待确认事项

- **运行时引用风险：** 不同宿主对 `references/` 的自动加载行为可能不同。实施前需用至少一个实际安装/执行路径确认；关键约束必须保留在 `SKILL.md` 摘要中。
- **模板漂移风险：** 直接复制公共模板会产生副本分叉。需要在“复制时锁定版本”“哈希检查”或“生成器同步”中选择一种明确策略，并把选择写入模板说明。
- **治理文件膨胀风险：** `AGENTS.md` 只保留强制规则和路由，不把教程、长示例、Kernel 细节重新复制进去。
- **迁移噪声风险：** 历史 Skill 可能有合法的领域化标题。检查器初期应提供报告和例外说明机制，避免为了标题一致而改写执行语义。
- **控制组件误接入风险：** 不能因为存在 `references/states` 或 `references/verifiers` 目录就自动要求接入运行时；仍以显式配置和本次任务要求为准。
- **待确认：** 检查器放在根级 `tests/`、独立脚本目录还是现有安装/验证入口，需要结合维护者希望的发布门禁和 CI 入口决定；本计划不预先锁定实现位置。
