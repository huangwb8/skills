# Skills 正文规范化优化计划

## 通俗解释：究竟发生了什么

- **一句话说明：** 现在每个 Skill 都能完成自己的工作，但说明书的章节组织方式不统一，像是同一栋楼里的房间各自使用不同的门牌和登记表，检查工具无法稳定判断它们是否完整。
- **具体场景：** 使用者触发某个 Skill 时，模型需要先找到“这个 Skill 负责什么”、再找到“要准备什么输入、按什么顺序执行、怎样验收、失败后怎么办”。目前这些内容散落在不同标题下，有的缺少固定入口，有的把验证、输出管理和安全边界混在一起。
- **对应到本项目：** `SKILL.md` 是 Skill 的操作契约；`config.yaml` 是易变配置和运行时声明的事实来源；`README.md` 面向使用者；`CHANGELOG.md` 与 BAC 记录变更。此次工作只整理契约表达，不改变脚本算法、CLI 参数、网络策略或输出格式。
- **改变前后：** 现在同类内容可能出现在“工作流”“核心功能”“注意事项”等任意标题下；迁移后每个 Skill 都有统一的 `目标 → 流程 → 控制（按需）→ 约束` 入口，原有领域内容作为对应小节的正文保留。

## 专业判断：问题在哪里

- **当前现象：** 结构检查器对 alpha 报告 106 条缺项（涉及 15 个尚未迁移的 Skill；`auto-test-project` 已基本符合），对 beta 报告 69 条缺项（涉及 9 个 Skill）。典型缺项是 `## 目标`、`## 流程`、`## 约束` 及流程六个三级小节；声明了运行时 State/Verifier 的 Skill 还需要补 `## 控制`。
- **影响范围：** 触发语义、输入输出和安全边界仍存在，但自动检查、跨平台安装和后续维护需要依赖人工猜测；新加入的维护者容易把相同内容写成不同格式。
- **已知原因：** Skill 在不同时间、不同模板下创建，历史正文没有统一迁移入口。结构问题不是业务逻辑错误，适合通过增量文档重排解决。

## 要达到什么目标

- 所有顶层 `skills/alpha/*/SKILL.md` 与 `skills/beta/*/SKILL.md`（不包括 `skills/alpha/awesome-code/agents/**`）都符合固定正文骨架。
- 保持每个 Skill 的 frontmatter `name`、`description`、作者信息和触发边界不变；不改变 `config.yaml` 的默认值、脚本参数、输出文件名、State/Verifier ID 或现有安全限制。
- 每个 Skill 都能明确回答：输入是什么、执行顺序是什么、交付物是什么、产物放哪里、如何校验、失败如何恢复。
- 仅在 `config.yaml` 明确声明 `runtime`/State/Verifier/Gate/Pack 时增加 `## 控制`，并准确描述现有声明；普通 Skill 不新增控制组件。
- 迁移后通过结构检查、frontmatter/config 一致性检查、脚本语法检查和各 Skill 轻量 smoke test。

## 改进方向

### 方向一：建立统一迁移骨架与写作规则

以 [`docs/templates/skill-body.md`](../templates/skill-body.md) 和 [`docs/templates/skill-common-constraints.md`](../templates/skill-common-constraints.md) 为唯一模板来源。每个 Skill 只做“标题归位 + 缺失说明补齐”，不整篇重写：

```text
## 目标
## 流程
### 输入
### 执行步骤
### 输出
### 输出管理
### 校验
### 失败与恢复
## 控制（仅在 config.yaml 显式声明时）
## 约束
```

迁移时优先保留现有段落原文，再把段落移动到最接近的固定小节；确实缺失的内容只补“当前实现已经做什么”，不把自然语言要求写成脚本已自动执行的能力。每个 Skill 的 `## 约束` 至少保留 `.bensz-api`、BAC、隐私、文件边界和 `bensz-collect-bugs` 摘要，并链接公共模板。

### 方向二：按领域分批迁移，避免一次性重写

先迁移结构相近、风险较低的文档处理/提示词类 Skill，再迁移带脚本编排、网络访问、安装器和运行时控制的 Skill。每批完成后立即运行 report/strict 检查，发现语义漂移就回退该 Skill 的文档改动，不回退其它 Skill。

### 方向三：运行时控制与普通 Skill 分层

- `write-readme`、`validate-md-ref` 已在配置中声明 State/Verifier：必须有 `## 控制`，写清状态进入/离开条件、required/advisory Verifier、证据和人工介入边界。
- 其它未声明运行时控制的 Skill 不添加 `## 控制`，即使正文出现“阶段”“检查”或“工作流”字样，也只在 `## 流程` 中说明。
- `verifier-state-architect` 的职责是规划控制组件，但自身配置未声明运行时 State/Verifier，因此保持普通 Skill 结构，不把它误写成受控运行实例。

### 方向四：同步治理文件与可追溯记录

每个 Skill 的正文迁移完成后，在其 `CHANGELOG.md` 的 `[Unreleased]` 记录“结构规范化、功能语义不变”；缺少 `CHANGELOG.md` 或 `config.yaml` 的 Skill 先补治理文件。版本号只从 `config.yaml:skill_info.version` 读取，不在正文或 README 复制版本号。根 `CHANGELOG.md` 记录每批迁移范围，BAC 记录计划、文件变更和验证证据。

## 各 Skill 的具体迁移方案

以下条目描述每个 Skill 要把现有内容放到哪里、需要补充什么，以及明确不应改变的功能边界。

### Alpha：生产 Skill

#### `auto-draw-plot`

- `## 目标`：说明根据文字生成绘图 prompt、调用 BenszAPI/Nano Banana、支持通用/roadmap/schematic 与多轮迭代；明确不负责通用图片编辑之外的文档转换。
- `### 输入`：整理用户描述、模式、参考图、输出路径、API 配置和迭代参数。
- `### 执行步骤`：按现有“运行前检查 → prompt 规划 → provider 选择 → 生成/编辑 → 多轮评估”顺序归位；保留 `parallel-vibe` 协作要求。
- `### 输出/输出管理`：明确图片、prompt、评估结果和 `.bensz-api` 运行目录的关系，不改变文件名和 provider 选择。
- `### 校验/失败与恢复`：保留 API 凭据冲突、图片有效性、失败 provider 降级与重试规则。
- 不新增 `## 控制`；State/Verifier 未在该 Skill 配置中声明。

#### `auto-test-code`

- `## 目标`：说明对目标代码做 A 轮批判性审查与 B 轮质量原则检查，并输出可追溯问题与修复建议。
- `### 输入`：目标代码根目录、运行 ID、测试/审查参数和排除目录。
- `### 执行步骤`：将现有会话初始化、A/B 轮、问题分级、修复建议和复测顺序统一到流程小节；保留“不得把 `tests/`、plans/、缓存当作业务源码”的边界。
- `### 输出/输出管理`：明确报告、计划、日志和测试产物全部进入目标 `.bensz-api` 会话目录。
- `### 校验/失败与恢复`：保留会话完整性、A/B 轮证据、失败轮次重试和人工复核条件。
- 不新增控制组件。

#### `auto-test-project`

- 已基本符合新骨架，作为迁移基准。只做标题、公共约束摘要、README/CHANGELOG 一致性复核，不重写现有流程。
- 重点检查其项目级缓存隔离、`tmp/` 产物和 Python 3.11+ 说明与 `AGENTS.md` 一致。

#### `auto-test-skill`

- `## 目标`：固定为“测试一个 Agent Skill 的触发、执行、输出和质量原则”，与 `auto-test-code` 的代码审查边界区分开。
- `### 输入`：目标 Skill 根目录、测试提示、A/B 轮配置、运行 ID。
- `### 执行步骤`：归位 Skill 快照、A 轮测试、B 轮质量检查、结果比较和复测，不改变现有脚本入口。
- `### 输出/输出管理`：明确测试计划、结果、评分和日志在 `.bensz-api` 的层级关系，禁止写回被测 Skill 源目录。
- `### 校验/失败与恢复`：保留触发命中、输出可用性、快照一致性和失败会话恢复规则。
- 不新增控制组件。

#### `awesome-code`

- 仅迁移顶层协调器 Skill；`skills/alpha/awesome-code/agents/**` 明确不改。
- `## 目标`：说明动态发现 Agent、读取配置门禁并选择 single/focused/parallel/sequential 策略。
- `### 输入`：用户任务、项目根目录、Agent 配置和 required route。
- `### 执行步骤`：保持 `get_path.py → agent_coordinator.py → dispatch_gate → AI 选择策略 → dispatch receipts` 顺序。
- `### 输出/输出管理`：说明计划、dispatch manifest、代理结果和任务工作区的位置；不把 agent 子 Skill 内容复制进主 Skill。
- `### 校验/失败与恢复`：保留 required agent 缺失时阻塞、失败代理留痕和单代理回退边界。
- 不新增 State/Verifier 控制组件。

#### `bensz-collect-bugs`

- `## 目标`：明确只记录 Bensz Skill/基础设施设计缺陷，不处理用户数据错误、第三方抖动或用户自行改源码。
- `### 输入`：最小复现、影响范围、环境信息和脱敏证据。
- `### 执行步骤`：保持“判定 → 本地记录 → 当前任务继续 → 用户明确要求时公开上报 → resolution 闭环”。
- `### 输出/输出管理`：区分 `~/.bensz-skills/bugs/` 本地记录和远程 `gh api` 上报，不记录密钥、隐私和完整私有 prompt。
- `### 校验/失败与恢复`：保留 schema 校验、脱敏检查、网络失败时本地保留和不阻断主任务。
- 不新增控制组件。

#### `better-prompt`

- `## 目标`：说明把简陋 prompt 结构化为可执行、可验证的高质量 prompt，并明确不替用户执行 prompt 中的业务动作。
- `### 输入`：原始 prompt、目标模型/平台、受众、输出格式和约束。
- `### 执行步骤`：归位输入验证、问题拆解、模型适配、结构化改写、质量自检和交付。
- `### 输出/输出管理`：保留纯文本/文件两种交付方式和敏感信息脱敏边界。
- `### 校验/失败与恢复`：检查意图保真、约束完整、歧义披露和不可执行要求的降级方式。
- 配置中的 `state_management` 只是 prompt 优化维度，不代表运行时 State，不添加 `## 控制`。

#### `compact-bensz-skills`

- `## 目标`：说明在不改变触发、输入输出和安全边界的前提下压缩 Skill 文档上下文。
- `### 输入`：目标 Skill、压缩范围、保留词/章节和基线快照。
- `### 执行步骤`：保持理解能力 → 删除重复 → 合并规则 → 保留必要示例 → 复测收益的顺序。
- `### 输出/输出管理`：明确草案、快照、差异和压缩报告放入任务工作区，正式 Skill 由主流程写回。
- `### 校验/失败与恢复`：保留触发回归、关键约束覆盖和压缩收益低于阈值时回退。
- 不新增控制组件。

#### `git-commit`

- `## 目标`：说明只分析 Git 改动并生成 Conventional Commit 信息/建议，不擅自提交或推送未授权内容。
- `### 输入`：仓库状态、分支、改动、提交偏好和 hook 选项。
- `### 执行步骤`：归位仓库检查、改动分组、语言检测、信息生成、可选 hook 与提交确认。
- `### 输出/输出管理`：区分 commit 建议、命令预览、hook 日志和实际提交结果。
- `### 校验/失败与恢复`：保留脏工作树保护、无改动返回、hook 失败和 `--no-verify` 明示规则。
- 不新增控制组件。

#### `git-pr-review`

- `## 目标`：说明对 GitHub PR 做只读、证据驱动的合并风险评估，不修改远程 PR。
- `### 输入`：仓库/PR 地址、审查范围、基线和补充上下文。
- `### 执行步骤`：归位隔离工作区、获取证据、并行独立评审、理解变更意图、风险分级和汇总。
- `### 输出/输出管理`：明确评审报告、JSON 证据、日志和 `parallel-vibe` 运行目录。
- `### 校验/失败与恢复`：保留 PR 获取失败、恶意变更、证据不足、评审分歧和只读边界。
- 不新增控制组件。

#### `git-publish-release`

- `## 目标`：说明分析 tag/commit 历史并生成或创建 GitHub Release，区分“预览”与“远程写入”。
- `### 输入`：owner/repo、tag、发布类型、变更历史、GitHub 凭据和用户确认。
- `### 执行步骤`：归位项目识别、Release/tag 获取、历史分析、Release Notes 生成、确认和可选发布。
- `### 输出/输出管理`：明确 release notes、API 响应和本地日志，不回显 token，不把凭据写入普通日志。
- `### 校验/失败与恢复`：保留远程写入前确认、重复 tag、网络失败和可重试边界。
- 计划实施时需补 `config.yaml` 与 `CHANGELOG.md`，版本只放 config；不改变现有发布 CLI。

#### `init-project`

- `## 目标`：说明分析项目并生成 `AGENTS.md`/可选治理文档，不修改业务代码。
- `### 输入`：项目根目录、语言检测、输出选项、BAC 开关和覆盖策略。
- `### 执行步骤`：归位路径安全检查、项目分析、模板变量替换、BAC 检查/初始化、文件写入和结果报告。
- `### 输出/输出管理`：区分正式治理文件、`docs/plans/`、`.bensz-api` 中间产物和备份文件。
- `### 校验/失败与恢复`：保留已有文件不覆盖、系统目录拒绝、Python 3.11+ 门禁、BAC 失败和部分生成恢复。
- 不添加 State/Verifier；生成的是项目治理文件，不是 Skill 运行控制。

#### `install-bensz-skills`

- `## 目标`：说明从 alpha 源复制安装 Skill 到系统目录，默认不安装 beta，支持本地/远程和按 Skill 过滤。
- `### 输入`：源目录、目标平台、Skill 过滤、强制覆盖、远程模式和 Python 版本。
- `### 执行步骤`：归位路径发现、版本/manifest 检查、legacy 清理、复制/回退、报告和安装后发现验证。
- `### 输出/输出管理`：明确 manifest、备份、缓存和安装报告的位置，不把安装运行缓存写入仓库源码。
- `### 校验/失败与恢复`：保留 Python 3.11+ 本地安装器门禁、bootstrap 3.8+ 例外、复制失败回滚和 bootstrap 对齐检查。
- 不新增控制组件。

#### `parallel-vibe`

- `## 目标`：说明用智能模式或代码模式并行执行独立任务并汇总结果，不能把普通 shell 并发误认为独立 Agent。
- `### 输入`：原始任务、线程数、模式、plan/project id 和 runner 参数。
- `### 执行步骤`：归位模式路由、计划生成、thread workspace 隔离、执行、结果收集和主 Agent 汇总。
- `### 输出/输出管理`：保留 `@main/plan.json`、thread `workspace/RESULT.md`、`runner.log`、退出码和 summary 契约。
- `### 校验/失败与恢复`：保留 thread 失败、resume、symlink 策略、退出码和无 subagent 时回退代码模式。
- 不新增 State/Verifier 控制组件。

#### `verifier-state-architect`

- `## 目标`：说明规划/审查最小 Verifier 与 State 架构，可明确得出“不接入”结论。
- `### 输入`：目标 Skill 流程、风险、现有 Kernel/Pack、删除影响和人机分工。
- `### 执行步骤`：归位业务流理解、删除影响闸门、Verifier/State 矩阵、Kernel 复用、实施顺序和验收。
- `### 输出/输出管理`：明确正式计划写入 `docs/plans/`，中间设计证据写入任务工作区，不直接实现 Pack/Kernel。
- `### 校验/失败与恢复`：保留 required/advisory 语义、零组件允许、回退和人工决策点。
- 配置未声明运行时控制，不添加 `## 控制`。

#### `write-readme`

- `## 目标`：说明基于仓库事实生成中文/英文 README，并校验双语结构、链接、敏感信息和证据来源。
- `### 输入`：项目根目录、事实材料、项目类型、模板、输出文件名和链接范围。
- `### 执行步骤`：归位事实清单、模板选择、中文草稿、英文对齐、验证和交付。
- `### 输出/输出管理`：明确 `README.md`、`README_EN.md`、草稿、报告及任务目录的边界。
- `## 控制`：依据 `config.yaml` 的 runtime 声明描述 `bensz.workspace.ready` 到 `delivery-ready/reported` 的进入/离开条件；列出六个 required Verifier、Evidence 来源、Gate 失败和人工确认边界，不虚构 Kernel 自动完成未实现的写作判断。
- `### 校验/失败与恢复`：保留双语结构、链接、代码围栏、token、路径范围和 secret redaction 检查。

### Beta：候选 Skill

#### `any-picture-format`

- `## 目标`：说明把本地文件、URL、剪贴板或批量图片转换为指定格式，保持透明度和元数据策略。
- `### 输入`：输入来源、输出格式/路径、质量、覆盖策略、批量参数和临时目录配置。
- `### 执行步骤`：归位输入探测、URL/剪贴板获取、格式转换、透明度处理、批量保存和清理。
- `### 输出/输出管理`：明确正式图片与临时文件/任务工作区的关系；不改变现有 CLI 和配置字段。
- `### 校验/失败与恢复`：保留格式支持、质量范围、路径边界、网络失败、并发临时文件和清理规则。
- 不新增控制组件。

#### `bensz-rmd-rules`

- `## 目标`：规范 R/Rmd 分析脚本的主业/副业分离、luckyBase 使用、图表可读性和结果解释边界。
- `### 输入`：项目 R/Rmd 文件、已有包资源、数据字典、分析目标和输出规范。
- `### 执行步骤`：归位资源盘点、R 与 Rmd 分工、统计/绘图规则、解释质量检查和交付。
- `### 输出/输出管理`：区分源数据脚本、Rmd、HTML/图表和 `.bensz-api` 过程产物，避免把中间结果写入源码目录。
- `### 校验/失败与恢复`：保留模板检查、图表/表格解释检查、禁用包清单和缺少 R 包时的降级策略。
- 不新增控制组件。

#### `download-fulltext-pdf`

- `## 目标`：说明按 DOI 从合法开放获取、arXiv、期刊官网等来源获取 PDF，并进行完整性验证；明确 Sci-Hub/可选依赖边界。
- `### 输入`：DOI、输出路径、来源配置、Unpaywall 邮箱（配置或环境变量）和验证阈值。
- `### 执行步骤`：归位 DOI 规范化、多源顺序、重试/状态文件、PDF 头校验和报告。
- `### 输出/输出管理`：明确 PDF、日志、轮询状态和任务工作区；保留相对状态文件与路径安全规则。
- `### 校验/失败与恢复`：保留最小/最大文件大小、PDF 头、来源失败切换、网络超时和人工安装可选依赖的处理。
- 不新增控制组件。

#### `find-best-skill`

- `## 目标`：说明根据主题搜索候选 Skill，结合多平台来源和社区/AI 评价进行筛选，不把搜索结果当作安全背书。
- `### 输入`：主题、关键词、平台范围、数量、缓存策略和排序偏好。
- `### 执行步骤`：归位需求解构、缓存查询、GitHub/SkillsMP/Reddit 搜索、去重、评分和推荐。
- `### 输出/输出管理`：明确候选表、来源链接、评分依据、缓存文件和失败来源记录。
- `### 校验/失败与恢复`：保留来源可追溯、重复项去除、网络失败回退缓存和敏感内容过滤。
- 不新增控制组件。

#### `knit-rmd-html`

- `## 目标`：说明在正确 `knit_root_dir` 下渲染 R Markdown 为 HTML，并管理 Pandoc/R 依赖。
- `### 输入`：Rmd 路径、项目根目录、输出目录、Pandoc 选择和渲染参数。
- `### 执行步骤`：归位路径检查、Pandoc 检测/引导、`rmarkdown::render` 参数构造、渲染和结果检查。
- `### 输出/输出管理`：区分 HTML、Pandoc 缓存、日志和任务临时产物；不改变现有输出命名。
- `### 校验/失败与恢复`：保留 R/Pandoc 缺失、下载失败、渲染超时、Linux 资产兼容和失败日志。
- 不新增控制组件。

#### `md-to-word`

- `## 目标`：说明将 Markdown 转为 Word，复用 reference.docx，不修改原始 Markdown。
- `### 输入`：一个或多个 Markdown、模板、输出目录、Pandoc 参数和图片处理选项。
- `### 执行步骤`：归位预检查、逐文件转换、模板选择、RGBA/EXIF 图片处理和轻量自检。
- `### 输出/输出管理`：明确 `.docx`、媒体目录、临时解压目录和失败清理规则。
- `### 校验/失败与恢复`：保留输入扩展名/数量限制、Pandoc/Pillow 检查、输出存在性和不覆盖源文件。
- 不新增控制组件。

#### `prompt-programming`

- `## 目标`：说明把自然语言 prompt 转换为简洁、可组合的 Prompt Program，不替用户执行程序语义。
- `### 输入`：原始 prompt、语言/方言偏好、约束和期望输出形式。
- `### 执行步骤`：归位输入验证、意图理解、六类原子映射、组合、压缩和自检。
- `### 输出/输出管理`：明确最终 Prompt Program、解释性备注和敏感信息处理。
- `### 校验/失败与恢复`：保留语义保真、变量闭合、控制流可读、歧义披露和无法映射时的自然语言回退。
- 不新增控制组件；当前配置未声明 runtime State/Verifier。

#### `validate-md-ref`

- `## 目标`：说明检查 Markdown 引用是否可定位、URL/锚点是否可访问，并输出可审计证据；不替代论文事实判断。
- `### 输入`：Markdown 文件、项目基目录、域名白/黑名单、超时和验证模式。
- `### 执行步骤`：归位强制运行门禁、文件路径校验、引用提取、URL/锚点探测、Kernel 结果归一化和报告。
- `### 输出/输出管理`：明确结构化结果、日志、Evidence 快照和 `.bensz-api` 目录；保留只读文件边界。
- `## 控制`：依据 `config.yaml` runtime 声明描述 `input-ready → checking → reported`，说明 required 的链接完整性 Verifier、advisory 的 citation truth-fit、Evidence 来源、Gate 失败和人工复核。
- `### 校验/失败与恢复`：保留 base_dir 范围、symlink/敏感路径、重定向、域名白黑名单、超时和外部站点不可用时的证据保留。

#### `which-model`

- `## 目标`：说明分析目标 Skill 的工作流和约束，检索官方/社区证据并生成 WHICHMODEL 模型选择建议。
- `### 输入`：目标 Skill 路径、用户场景、模型候选、联网来源和输出 README。
- `### 执行步骤`：归位静态分析、证据搜索、硬编码评分、场景映射、文档生成和验证。
- `### 输出/输出管理`：明确 `WHICHMODEL_*.md`、README 插入位置、来源链接、缓存和失败记录。
- `### 校验/失败与恢复`：保留引用可追溯、推荐不越过证据、联网失败降级和 README 原结构保护。
- 不新增控制组件。

## 实施范围与顺序

1. **基线与模板确认：** 固定模板、检查器、排除路径和每个 Skill 的当前章节清单；先记录根 `CHANGELOG.md` 与 BAC 计划事件。
2. **第一批低风险迁移：** `better-prompt`、`compact-bensz-skills`、`git-commit`、`prompt-programming`、`find-best-skill`、`md-to-word`、`bensz-rmd-rules`、`auto-test-project` 复核。
3. **第二批编排/文档迁移：** `auto-test-code`、`auto-test-skill`、`awesome-code`（仅顶层）、`parallel-vibe`、`git-pr-review`、`write-readme`、`validate-md-ref`；运行时控制 Skill 单独审查控制章节。
4. **第三批高风险边界迁移：** `auto-draw-plot`、`bensz-collect-bugs`、`git-publish-release`、`init-project`、`install-bensz-skills`、`any-picture-format`、`download-fulltext-pdf`、`knit-rmd-html`、`which-model`、`verifier-state-architect`。
5. **治理文件补齐：** 为 `git-publish-release` 补 `config.yaml` 与 `CHANGELOG.md`；为 `which-model` 补 `CHANGELOG.md`；版本号从现有元数据或首个兼容 patch 版本确认，不在 SKILL.md 重复声明。
6. **逐批校验与收尾：** 每批先 report，再 strict；确认所有固定章节、公共约束摘要、运行时控制声明、模板副本哈希、README/CHANGELOG/BAC 一致。

## 如何确认完成

- 结构检查：alpha、beta 均以 `--mode strict` 通过；检查器不扫描并保持忽略 `skills/alpha/awesome-code/agents/**`。
- 语义保持：逐 Skill 对比迁移前后 frontmatter、触发描述、CLI 命令、配置键、输出文件名、State/Verifier ID 和安全限制无变化。
- 脚本回归：对每个含 `scripts/` 的 Skill 至少运行 `--help` 或现有 smoke/QA；安装器额外验证本地与 bootstrap 入口行为一致。
- 路径与产物：运行过程缓存、测试报告和临时文件仅进入 `.bensz-api/`/`tmp/` 约定目录，Skill 源目录不出现 `__pycache__`、`.pytest_cache`、`.ruff_cache`。
- 文档一致性：`config.yaml` 是版本唯一来源；README 仅说明使用方式；CHANGELOG 有对应 `[Unreleased]`；BAC 能追溯计划、改动和验证。
- 排除项检查：`git diff --name-only | rg 'skills/alpha/awesome-code/agents/'` 必须为空。

## 技术补充（按需阅读）

### 固定章节的语义映射

| 固定章节 | 应回答的问题 | 不应做的事 |
| --- | --- | --- |
| `目标` | Skill 负责什么、何时触发、不负责什么 | 不复制整段 README 或版本号 |
| `输入` | 必需输入、可选输入、来源和敏感边界 | 不把默认值从 config.yaml 重抄成第二份事实来源 |
| `执行步骤` | AI 判断与脚本确定性操作的顺序 | 不暗示未实现的自动化能力 |
| `输出` | 用户得到什么、格式和成功语义 | 不承诺未验证的外部结果 |
| `输出管理` | 正式交付物、中间文件、日志放在哪里 | 不把中间文件写进 Skill 源目录 |
| `校验` | 如何证明结果可交付 | 不只写“检查通过”而不给可观察条件 |
| `失败与恢复` | 失败证据、重试、回滚、人工介入 | 不吞掉错误或把不确定当成功 |
| `控制` | 仅已声明 State/Verifier/Gate 的运行边界 | 不因出现“阶段/检查”字样而擅自接入控制组件 |
| `约束` | `.bensz-api`、BAC、隐私、文件边界、bug 记录 | 不写入密钥、令牌、邮箱等敏感信息 |

### 版本与兼容策略

- 文档结构调整且功能语义不变，Skill `config.yaml:skill_info.version` 使用 patch 版本；若只在同一版本发布前完成迁移，可由发布流程合并记录。
- 不修改脚本公开参数、配置键、输出格式、网络来源、State/Verifier canonical ID 或历史事件。
- 若迁移发现正文与实现不一致，先在计划/CHANGELOG 标记为待修复项，不在结构迁移中顺手重写业务逻辑。

## 风险与待确认事项

- 仓库共有 25 个顶层 Skill（其中 `auto-test-project` 作为已迁移基准复核，约 24 个需要实质迁移）；批量迁移仍可能造成标题移动时的语义遗漏，必须保留逐 Skill diff 和迁移前快照。
- `write-readme` 与 `validate-md-ref` 的 `## 控制` 需要严格对齐配置和现有 Pack，不得新增未实现的 Gate 语义。
- `git-publish-release` 缺少治理文件时，版本号和作者信息需先从现有 README/发布记录确认；若无法确认，先生成待人工确认的草案。
- `skills/alpha/awesome-code/agents/**` 是明确排除范围，任何自动脚本、结构检查或批量改写都必须验证未触碰该目录。
- 本计划只覆盖正文规范化；下载 SSRF、自动 pip、临时文件竞态、凭据脚本等运行时安全修复另列独立变更，避免与文档迁移混在同一批次。
