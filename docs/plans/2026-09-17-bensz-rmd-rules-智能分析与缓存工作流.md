# bensz-rmd-rules 智能分析与缓存工作流优化计划

## 通俗解释：究竟发生了什么

- **一句话说明：** 当前 Skill 已经会把重型计算与 Rmd 报告分开，但还不会像有经验的分析者一样，在动手前规划多个分析步骤、选择值得保存的中间数据，并从最近的成功步骤继续运行。
- **生活类比或具体场景：** 这像准备一桌复杂宴席。现在通常把备料和慢炖一口气做完，最后才保存两个成品；中途失败时可能重新洗菜。改进后先列菜单和先后关系，只在关键阶段保存有标签、可检查的半成品，调整摆盘时不重新慢炖。
- **对应到本问题：** 菜单是用户需求与分析计划；食材是 `raw/` 中的原始数据；半成品是 `products/` 中可审查、可恢复的数据产品；摆盘是 Rmd 的筛选、绘图和解读；`reports/` 保存可以直接用于论文的正式图表。
- **改变前后：** 现在可以避免部分报告层重算，但长流程中途失败仍可能从头开始；改进后，AI 先形成有序分析地图，只保存高价值检查点，并在输入、参数或代码改变时只重跑受影响步骤。

## 专业判断：问题在哪里

- **正确基础：** 当前 `.R` 负责重型计算和全量结果、`.Rmd` 负责报告层筛选与解读的原则应保留。
- **缓存过粗：** 标准模板在预处理和核心计算全部完成后才保存 `processed_data.rds`、`computation_results.rds`，能支持“计算一次、报告多次”，不能支持长流程内分步恢复。
- **文档与实现漂移：** README 声称存在 `dv_mut_mode = "postprocess"`，配置却只有没有执行逻辑的 `analysis_mode`；`SKILL.md` 的“输出管理”也没有真正区分科学数据产品与 AI 临时材料。
- **单脚本假设过强：** 当前默认一个主 `.R`、一个 `_functions.R` 和一个 `.Rmd`，不适合大型、零碎且存在多个报告的分析。
- **缓存没有身份：** 文件存在不代表结果仍然有效；当前缺少输入、参数、相关代码、上游产品、输出结构和完成状态的标准记录，也没有原子写入与失效传播。
- **人类审查不足：** RDS 适合恢复复杂 R 对象，但不适合直接阅读、diff 或跨语言复用，当前没有要求重要检查点同时提供可读摘要、表格或结构说明。
- **运行前审查不足：** 现有流程重视交付检查，却没有在昂贵计算开始前串行审查数据流、R 实现和科学合理性。
- **维护信息漂移：** `config.yaml` 是版本单一真相源，但 README 顶部仍复制旧版本字面值；本次不能再增加新的重复默认值。

## 要达到什么目标

- AI 先盘点用户目标、原始数据、约束和交付物，再决定分析单元、依赖、缓存边界与恢复方式。
- `00.Environment.R` 默认唯一；`.R`、`_functions.R`、`.Rmd`、`.html` 数量由复杂度决定，不要求每个分析单元四类文件齐全。
- 分析单元使用 `AA.BB.CC. 名称` 词干，编号同时表达层次、紧密程度和默认执行顺序。
- 代码、Rmd 和同名 HTML 位于项目根目录；`raw/` 只读；`products/` 保存完整可恢复数据；`reports/` 只保存正式图表和补充材料；`.bensz-api/` 保存 AI 内部材料。
- 只有输入、参数、相关代码、上游身份和完整性均符合时才复用检查点；某一步失效时只重跑该步及必要下游。
- 复杂对象可用 RDS 保真，但重要矩形数据、结构、参数和运行摘要必须有适合人类阅读的副本或预览。
- 主 Agent 完成整体初稿后，依次由至少三个独立、只读的子 Agent 审查；每轮修正后下一轮检查最新版本。
- 保留 Nature 图表、PDF/JPG 自检、HTML widget、数字追溯、指标导读和专家解读等现有能力。

### 不在本次处理范围

- 不缓存每个临时变量，不把简单任务强制拆成复杂流水线。
- 不默认引入 `targets`、`drake` 或新的工作流框架。
- 不修改 `luckyBase`，不把领域规则下沉到 Kernel。
- 不默认接入 State、Verifier、Pack 或 Gate。
- 不自动迁移、删除或覆盖已有 `tmp/`、`products/`、`reports/` 或用户脚本。

## 改进方向

### 一、把“先理解、再规划”设为分析入口

`SKILL.md` 应要求 AI 先确认分析目标、原始输入、数据字典、统计边界、报告用途和重跑成本；对 `raw/` 只做足以规划的轻量只读盘点，不在这一阶段意外启动完整计算。

规划结果形成分析单元表，至少包含编号、目的、上游依赖、主要数据产品、是否缓存和报告关系。只有在需求有对应步骤、依赖无循环且没有前向依赖后才生成代码。

这意味着 AI 不再看到数据就写一个巨型脚本，而是先说明“做哪些分析、为什么按这个顺序、哪些结果值得留下”。

### 二、建立多分析单元和三段式编号契约

同一单元可按需出现：

```text
AA.BB.CC. 名称.R
AA.BB.CC. 名称_functions.R
AA.BB.CC. 名称.Rmd
AA.BB.CC. 名称.html
```

四类文件都在项目根目录，但不要求全部存在。`00.Environment.R` 默认唯一，只承担包加载、项目根路径、全局选项和真正跨单元的配置；分析特有逻辑留在相应 `.R` 与 `_functions.R`。

编号按数字元组升序就是默认执行顺序。上游依赖不得指向更后的编号；综合报告必须取得晚于其所有输入的编号。`_functions.R` 不是执行节点，由同词干 `.R` 或 `.Rmd` 加载。

新增轻量校验，检查编号格式、同词干配对、重复身份、前向依赖、循环和缺失上游；不能把函数文件误判为独立步骤。

### 三、将目录定义为稳定的数据边界

| 位置 | 职责 | 禁止混入 |
| --- | --- | --- |
| 项目根目录 | 环境脚本、编号 R/functions/Rmd 和同名 HTML | 大量无编号临时脚本 |
| `raw/` | 用户原始输入，默认只读 | 清洗结果、缓存、AI 日志 |
| `products/` | 可审查、可恢复、可供下游复用的完整中间数据 | 只服务本轮 Agent 的草稿 |
| `reports/` | Rmd/HTML 引用及论文直接使用的正式图、表、补充材料 | Rmd、HTML、模型缓存、审查日志 |
| `.bensz-api/` | AI 输入引用、草稿、子 Agent 结果、命令与验证日志 | 续算所必需的唯一科学数据副本 |

`products/<流程名>/<AA.BB.CC. 名称>/` 与根目录脚本共享分析单元身份；`reports/figures/`、`reports/tables/` 和可选 `reports/supplementary/` 的文件也使用同一编号前缀。

### 四、建立缓存选择和最小数据产品契约

AI 在规划阶段判断一个边界是否计算昂贵、被多个下游复用、经历高风险或有损转换、需要人工审查、依赖可变外部请求，或者中断后重做代价高。命中任一条件通常值得缓存，但仍应结合体量和维护成本；毫秒内可重建、只服务下一行或纯展示格式的对象不默认缓存。

每个持久检查点至少满足四类职责：

1. 机器可恢复的完整主对象；
2. 人类可读的全量表、受控预览、schema 或 Markdown 摘要；
3. 记录单元、输入、参数、相关代码、上游身份、数据结构和耗时的元数据；
4. 全部验证成功后才出现的完成标记。

建议布局为：

```text
products/<流程>/<AA.BB.CC. 名称>/
├── <完整主对象>.rds
├── <全量表或受控预览>.tsv
├── summary.md
├── metadata.yaml
└── SUCCESS
```

文件名可按领域调整，但四类职责不能缺失。巨大矩形数据不必重复写成巨大文本，可使用高效完整格式，加 schema、统计摘要和有限预览。

写入采用“临时文件 → 重新读取验证 → 替换正式文件 → 最后写完成标记”。编号解析、路径构造、摘要、完整性与原子落盘应收敛为可复用 helper，避免每个项目重新即席实现。

### 五、定义缓存身份、失效传播和恢复

缓存身份至少包含：上游输入摘要、影响本步骤的参数、相关代码摘要、上游产品身份、输出契约版本，必要时加入会改变结果的 R/包版本。时间戳不能作为身份，否则每次运行都会失效。

默认按编号遍历：有效步骤记为 cache hit；无效、损坏或未完成步骤执行，并使必要下游失效。“从 03 恢复”仍应记录 01、02 依次命中缓存，再执行 03，保证日志顺序与文件顺序一致。

计算层提供一致的自动复用、强制某步重算和从某步恢复控制；Rmd YAML 只保留报告层参数。删除未落地的 `dv_mut_mode`，并移除或真正实现含义模糊的 `analysis_mode`，不能继续让报告参数假装控制重型计算。

### 六、在真实运行前执行三轮独立串行审查

主 Agent 完成所有代码初稿后，依次启动三个新的只读子 Agent：

1. **结构与数据流审查：** 需求覆盖、编号、依赖、目录、缓存边界与 `raw/` 只读性。
2. **R 实现与恢复审查：** 对象生命周期、路径、随机性、缓存身份、原子写入、损坏识别和断点恢复。
3. **科学与统计审查：** 方法选择、偏差与混杂、多重检验、数据泄漏、模型假设、不确定性和结论边界。

每轮读取当时最新版本，只输出问题、证据和建议；主 Agent 是唯一修改主体，修正后再进入下一轮。无问题时记录通过，不制造形式性改动。审查记录保存在 `.bensz-api/`。

宿主不能创建独立子 Agent 时必须披露降级，可执行三轮职责分离的顺序自检，但不得冒充独立审查；用户明确要求真实多 Agent 或任务高风险时，能力缺失应安全停止。

### 七、同步模板、确定性工具和门禁

- 将 R、functions、Rmd 模板改成“单个编号分析单元”模板，不再暗示整个项目只有一个主脚本。
- R 模板读取上游 `products/`，写完整产品与完成标记；Rmd 从 `products/` 读取全量数据，在报告层筛选，将正式图表写入 `reports/`，Rmd/HTML 留在根目录。
- `00.Environment.R` 模板明确唯一性和职责，不吸收分析特有逻辑。
- 增加命名/依赖、目录边界、元数据、完成标记和缓存命中/失效的轻量确定性检查；默认支持报告模式，新项目交付时使用严格模式。
- helper 只提供协议、路径、摘要和落盘能力，不包含差异表达、生存分析等领域语义。

### 八、同步文档、兼容策略和评测

同步修改 `SKILL.md`、`config.yaml`、README、CHANGELOG、混合架构指南与示例、工作流清单、交付验证、模板和 QA。长契约下沉到专门 reference，`SKILL.md` 保留必须执行的主链与路由，避免继续膨胀。

兼容策略：

- 新项目默认使用根目录编号文件和 `raw/products/reports/.bensz-api`；
- 已有项目仍使用 `tmp/{主脚本名}/` 时先识别并保留，不自动迁移或覆盖；
- 仅用户明确要求迁移时才制定映射、校验、原路径保留与回退；
- README 不再复制版本号，版本只记录在 `config.yaml:skill_info.version`。

按 `skill-creator` 建立旧版快照与新版对比评测，覆盖简单单报告、多阶段昂贵分析、中途失败恢复、仅修改报告阈值/配色、以及旧 `tmp/` 项目。评测产物放在任务工作区或 `tmp/`，不进入 Skill 发布目录。

## 实施范围与顺序

1. **锁定公开契约：** 固化根目录布局、三段式编号、目录职责、分析单元、缓存与三轮串行审查，明确旧 `tmp/` 兼容边界。
2. **重组 Skill 与 references：** 让 `SKILL.md` 聚焦“理解—规划—实现—审查—运行—交付”，把编号、产品、缓存和兼容细节下沉到定向 references。
3. **更新配置和模板：** `config.yaml` 托管稳定默认值；模板改为单分析单元，并新增最小产品/checkpoint helper。
4. **实现轻量检查：** 增加命名依赖、目录边界、元数据、完成标记和缓存失效检查，先报告后严格。
5. **接入串行审查：** 固定三个角色、只读权限、主 Agent 单点修改、轮次输入和能力降级。
6. **补齐 QA 与场景评测：** 测试首次运行、命中、参数/代码/上游失效、半成品、损坏缓存、简单任务不过度设计及旧项目兼容。
7. **收敛发布记录：** 用 `write-readme` 更新使用者文档，同步 CHANGELOG、版本与 BAC，运行结构、路径、Rmd、现有 QA、新 QA 和 beta 安装发现回归。

### 验收矩阵

| 场景 | 应观察到的结果 |
| --- | --- |
| 简单低成本 Rmd | 只创建一个必要分析单元，不强拆或生成无价值检查点。 |
| 多阶段昂贵分析 | 先形成无循环分析图，再创建多个编号单元和必要 products。 |
| 根目录排序 | 同词干文件一致；编号顺序与依赖顺序一致；函数文件不是执行节点。 |
| 报告输出 | Rmd/HTML 在根目录；正式图表在 reports；完整未筛选数据在 products。 |
| 相同输入重跑 | 按编号遍历并显示 cache hit，不重复昂贵计算。 |
| 只改阈值或配色 | 不使重型产品失效，只重渲染相关报告。 |
| 修改上游参数 | 当前单元及必要下游失效，较早无关单元仍复用。 |
| 中途崩溃 | 失败步骤没有完成标记，前序有效产品保留，重跑从失败边界恢复。 |
| 缓存损坏 | 不因文件存在而误命中，正确失效并重算。 |
| 三轮审查 | 三份职责不同的只读结果按序产生，每轮审查前轮修正后的版本，只有主 Agent 改代码。 |
| 无子 Agent 宿主 | 披露降级，不将三轮自检冒充独立子 Agent。 |
| 历史 `tmp/` 项目 | 不自动迁移或覆盖，仍可非破坏性维护。 |
| 现有质量门禁 | PDF/JPG、图表可读性、HTML widget、数字追溯和解读检查继续通过。 |
| 跨平台与隐私 | 相对路径和 `file.path()` 可用，日志与元数据不泄露绝对私有路径或凭据。 |

## 如何确认完成

- 复杂需求会先得到编号、依赖、数据产品、缓存决定和报告关系明确的分析图，而不是直接生成巨型脚本。
- 新项目只有一个 `00.Environment.R`，可有任意必要数量的根目录编号 R/functions/Rmd/HTML。
- 编号、依赖、products 目录和 reports 文件能用同一分析单元身份互相定位。
- `raw/` 无输出覆盖；`products/` 不只是二进制黑盒；`reports/` 不包含 Rmd/HTML 或模型缓存；删除 `.bensz-api/` 不破坏正式流程重跑。
- 缓存复用、局部失效、中途失败和损坏识别均有可执行测试。
- 首次真实运行前存在三轮串行审查及轮间修正证据，能力不足时不冒充完成。
- 当前 Rmd/HTML、图表、表格、数字准确性和专家解读门禁全部回归通过。
- README、SKILL、config、templates、references、QA 和 CHANGELOG 表述一致；版本只由 config 声明；Skill strict 结构检查与 beta 安装发现通过。

## 风险与待确认事项

- **过度设计：** 必须保留“单分析单元 + 最小产品”的轻量路径。
- **大文件摘要成本：** 完整 hash 可能接近重算成本，需要通过原型测试决定大文件摘要策略和显式强校验边界。
- **并发写入：** 本次先保证单进程原子性；只有真实用例需要并发时再增加锁，不预建分布式调度。
- **跨宿主子 Agent 差异：** 必须同时规定真实子 Agent 路径、披露式降级和高风险停止条件。
- **历史项目：** 新默认不能隐式重写仍读取 `tmp/` 的现有项目。
- **根目录文件较多：** 这是三段式编号要解决的场景，应验证中文、空格和 Windows 路径，不得又把脚本移入隐藏目录。
- **数据体积：** 人类可审查不等于复制巨大 TSV，应在完整高效格式、schema、摘要和有限预览之间选择。
- **待实测选项：** 元数据格式、纳入身份的包版本、大文件摘要阈值、helper 文件名和 CLI 参数，应在模板原型与首轮测试后锁定，不在无性能证据时写死。
