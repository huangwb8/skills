# bensz-rmd-rules 报告标题与章节编号优化计划

打开一份科研报告，页首先要让读者知道研究的是什么，正文的节号则帮助定位方法、结果和讨论。test-02 主报告用「还剩多少基因，才能相信一个程序分数？」作页首标题，读者要看副标题才知道它研究的是固定参考 TSP。三份报告的文件名有阅读编号，打开后却看不到正文节号。改完后，读者可以从主标题「乳腺癌表达谱中固定参考 TSP 程序评分的基因缺失偏差与误差界」识别研究对象与分析范围，并在正文中看到「1 摘要」「2 引言」及对应的子节号。

## 示例项目的定位

`templates/project/` 提供一个可运行、可改造的起点。目录、文件名、代码、数据、分析方法和报告结构等全部内容均供参考。AI 可按实际研究和项目现状选用、调整或跳过其中任一部分。需要统一的交付行为应在 Skill 中明确写出，由实际交付物的验收确认。比如，正文编号可以写入生成骨架的默认配置，自建或已有 Rmd 则可在原有渲染入口中实现和核验。

## 根因

**编号只接进了部分生成路径。** 骨架生成器把 `number_sections: true` 放在 Liquid Glass 的主题片段里，`plain` 和 `flatly` 没有这个配置。test-02 沿用自己的三份 Rmd 和渲染入口，虽然应用了 Liquid Glass 样式，三份 YAML 都省略了该项，现有 HTML 的 47 个正文标题均无节号。用当前 R Markdown 和 Pandoc 最小渲染复现了该行为：省略或显式关闭时无节号，开启后得到 `1`、`2`、`2.1`，页首题名不参与编号。现行交付检查核对目录和文件编号，却没有要求在 HTML 正文中检查节号。 [生成器](../../skills/beta/bensz-rmd-rules/scripts/new_project.py#L11) · [主题规范](../../skills/beta/bensz-rmd-rules/references/visuals.md#liquid-glass-html) · [交付检查](../../skills/beta/bensz-rmd-rules/references/delivery.md#先核对结果再读-html)

**题名缺少针对实际研究的审阅要求。** test-02 把「固定参考 TSP」留给了副标题，主标题中的「才能相信」暗示存在通用的可信阈值，超出了给定容差和固定参考条件下的误差分析。现行规范规定了报告语言和摘要结构，可以进一步明确如何从研究对象、分析设计和实际证据形成题名。现有材料只支持判断成品题名是否妥当，无法确定当时采用该题名的原因。 [报告规范](../../skills/beta/bensz-rmd-rules/references/report.md)

## 修改方案

### 把章节编号设为报告默认行为

- 在 `SKILL.md` 明确区分文件名的三级阅读编号、YAML 页首题名和 HTML 正文章节编号。前者标示多份报告的阅读顺序，后者由 R Markdown 和 Pandoc 按 Markdown 层级生成。
- 将 `number_sections: true` 放进配对骨架公共的 `output.html_document` 配置，从 Liquid Glass 专属片段移除。三个主题共用同一规则。用 `## 数据与方法`、`### 研究设计` 这类标题层级生成节号，避免在源码里手写编号和在成品里出现双编号。
- 在 `references/visuals.md` 与 `references/delivery.md` 补齐既有报告路径。任务涉及新写或修订完整报告时，检查其原有渲染入口是否生成节号，必要时补齐 Rmd 配置。用户或投稿模板明确规定关闭编号的情形采用对应设置。验收从成品中的正文标题、目录和跳转链接入手，同时保留项目原有的主题和入口。

### 让正式题名准确说明分析范围

- 在 `references/report.md` 写清起草和定稿的依据，由 `SKILL.md` 的报告撰写步骤引用。AI 根据实际研究对象、分析目标、设计和证据范围自主拟定题名，在主要结果确认后回核。队列、设计或关键方法能帮助界定范围时，可写进标题。句式根据实际内容选择。采用问句时，检查问题是否具体、报告是否实际回答。用户明确指定题名或文体时沿用其要求。
- 验收时单独读一次页首题名，再与主要结果和结论核对，检查题名能否独立说明研究范围，是否把探索、模拟或单一任务验证写成普适结论。以 test-02 为例，历史架构页可用「乳腺癌表达谱的程序评分架构比较与跨队列稳定性评估」，读数页可用「乳腺癌表达谱程序评分的读数消融、ER 区分与技术重复评估」。这些措辞分别对应两页实际提供的证据。

## 实施与验收

1. 在 Skill 中说明示例项目的适用方式，同步报告、主题和交付规范。将公共编号配置接入骨架，随后同步双语 README 与变更记录。
2. 用正式入口渲染 Liquid Glass、`plain` 和 `flatly` 骨架。检查正文一级和嵌套标题各有一个正确节号，页首题名独立显示。启用目录时，核对目录显示、节号和跳转链接。再验证显式关闭编号的兼容情形。在桌面和窄屏实际打开 Liquid Glass 输出，排除节号已进 HTML 却被样式隐藏的情况。
3. 在隔离的既有报告样例上复验：先保留缺项和原题名作为失败反例，再按新规则仅改报告配置与题名，使用原入口重渲染。优先取 test-02 的副本并复用有效结果，核对三份 HTML 的题名、节号和链接，同时比对报告数值、正式结果和 targets 元数据。若有效 store 无法复用，用有相同 YAML、主题和标题层级的最小副本验证渲染行为，并在交付记录中标明实际覆盖范围。
4. 用两种研究设计做题名写作验收，例如前后配对估计与外部队列验证。分别给出研究背景、比较和结果，评估写作者能否自主拟出准确且可区分的题名。至少一个样例从零组织报告或沿用既有项目结构，核验成品是否符合明确的交付要求。
5. 分别记录正式渲染、浏览器检查和题名语义审阅，注明实际验证的平台。三种主题默认编号、显式关闭有效、既有入口可复验，并且从零写作和既有报告修订都能产出与证据相符的题名，才算完成。
