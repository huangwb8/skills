# Research-Idea：Agent Skills 项目的科研化评估（BIV 风格重写版）

## 调研摘要

- 输入资料：用户提供的 Agent Skills 项目科研化专家报告，以及随后对 BIV 研究问题与假设的讨论。
- 重写原则：每个候选只保留一个研究对象、一个核心机制、一个可比较结果和一条反证路径。
- 首篇建议：研究“版本绑定验证是否减少 Agent 的错误完成”，不要把整个 runtime assurance 架构写成一个总假设。
- Premium 查新状态：五个方向均完成检索与去重阶段；逐篇 AI 评分阶段因交互式入口限制未完成。因此查新判断是方向性判断，不等同于完整系统综述。

## 为什么按 BIV 风格重写

BIV 的问题之所以显得干净，是因为它没有把“系统拥有哪些组件”当作科学问题，而是建立了一个简单的比较关系：

```text
一种明确的方法
        ↓
是否改善一个明确的检测结果
        ↓
相对于哪些基线、在什么条件下、改善多少
```

原报告的问题在于把 State、Verifier、Gate、Event Ledger、Evidence、ActionProposal、时序策略、校准、预算路由和 SVCO 同时放进一个命题。这些是不同层次的内容：有些是实现组件，有些是实验因素，有些是后续研究问题，不能共同构成一个干净的假设。

本报告因此采用以下分离：

- `ArtifactVersion`、`EvidenceSnapshot`、Gate 等是实现研究处理因素所需的工程组件，不是科学问题本身。
- false-completion、故障定位率、验证成本等是结果变量。
- Action interposition、组合验证和自适应路由暂不放入首篇主假设。
- 每个候选单独成问；候选之间是后续论文顺序，不是一个“大一统理论”。

## 多个科学问题-科学假设对

### 候选 1：版本绑定验证与错误完成

**科学问题**：当 Agent 在验证通过后修改产物或证据时，将验证结果绑定到被验证对象的具体版本，是否比未绑定版本的验证机制更能防止错误完成？

**可证伪科学假设**：在存在产物修改、证据陈旧和错误版本交付的工作流中，版本绑定验证相比未绑定验证能够降低 false-completion rate，同时不显著降低 valid-completion rate。

**核心比较**：未绑定验证 vs 仅绑定产物版本 vs 同时绑定产物与证据版本。

**关键预测**：PASS 后的产物/证据变化会自动使旧结果失效；错误版本不会被系统承认为有效完成。

**反证路径**：若版本绑定不能降低 false completion，或任务成功率明显下降，或普通 content-addressed cache/provenance 已能达到相同效果，则假设不成立。

**查新结论**：部分研究但关键缺口存在。运行时策略研究已覆盖行动约束，构建系统已有版本与依赖追踪；但 Agent 证据漂移、验证结果重放和完成完整性的结合仍需直接验证。**处理：保留，作为首篇主线。**

**初步评价**：新颖性中高（必须实证超越缓存失效类比）；重要性高；可行性高。

### 候选 2：结构化证据与验证可靠性

**科学问题**：typed finding 和精确 evidence reference 是否比自由文本评审更能提高验证结果的可靠性？

**可证伪科学假设**：在相同模型和 token 预算下，结构化证据验证能够降低证据幻觉，并提高跨运行一致性和证据定位准确率。

**核心比较**：自由文本评审 vs typed finding；再比较无证据定位 vs 有精确证据定位。

**关键预测**：精确证据定位会提高人工复核和后续修复的成功率。

**反证路径**：若收益完全来自输出格式，或在固定长度、固定提示和盲法人工评审下没有可靠性提升，则假设不成立。

**查新结论**：部分研究但关键缺口存在。BIV 和 LLM-as-judge 研究已有结构化测量与偏差分析；证据定位对恢复的独立贡献仍需验证。**处理：作为候选 1 的实验因素。**

**初步评价**：新颖性中；重要性中高；可行性高。

### 候选 3：组合验证与复合缺陷

**科学问题**：组合多个原子 finding 的 FindingGraph，是否比逐项原子验证更能发现 Agent 工作流中的复合缺陷？

**可证伪科学假设**：在相同原子验证器预算下，FindingGraph 能提高复合故障召回率，同时不造成不可接受的误报增加。

**核心比较**：原子验证 OR/加权分数 vs FindingGraph 组合规则。

**关键预测**：低风险原子行为组成的高风险链能够被识别，而单个原子验证器均可能通过。

**反证路径**：若组合方法的收益完全来自增加规则数量，或在未见 motif 上不能泛化，则假设不成立。

**查新结论**：部分研究但关键缺口存在。BIV 与 VIGIL 已有安全组合链；跨领域可复用性仍未充分证明。**处理：P1 或第二篇论文。**

**初步评价**：新颖性中；重要性高；可行性中。

### 候选 4：验证器路由与成本

**科学问题**：在固定关键故障漏检率约束下，自适应选择验证器能否降低验证成本？

**可证伪科学假设**：风险感知的验证器路由相比固定 run-all 或静态 cascade，能够在不超过预设漏检率上限的条件下降低 token、延迟和费用。

**核心比较**：run-all、cheap-only、静态 cascade、风险感知动态路由。

**关键预测**：校准信息和历史 finding 能减少不必要的强验证器调用。

**反证路径**：若分布外任务导致漏检率超界，或简单静态 cascade 已达到同等成本—可靠性前沿，则假设不成立。

**查新结论**：部分研究但关键缺口存在。模型路由和自适应推理已有大量工作；验证器依赖、硬风险约束和人工升级是待验证差异。**处理：P2，先 shadow mode。**

**初步评价**：新颖性中高；重要性高；可行性中低。

### 候选 5：状态—验证遥测与故障定位

**科学问题**：联合 State 和 Verifier 遥测是否比只看最终结果更能定位 Agent 轨迹中的最早关键故障？

**可证伪科学假设**：在包含隐藏随机故障的轨迹中，联合遥测能够提高 earliest-failure 的 Top-k 定位率，并降低 targeted recovery 成本。

**核心比较**：终局结果、State-only、Verifier-only、State+Verifier。

**关键预测**：联合遥测能减少 full rerun，并降低重复副作用率。

**反证路径**：若收益只是增加日志或 token，或依赖读取未来事件和注入器标签，则假设不成立。

**查新结论**：部分研究但关键缺口存在。过程监督、AgentGuard/ProbGuard 与通用可观测性提供基础；可回放的 State×Verifier 定位和 targeted recovery 仍需 benchmark。**处理：候选 1 的次级问题，或在有真实失败轨迹时独立成文。**

**初步评价**：新颖性中高（依赖 benchmark）；重要性高；可行性中。

## 为什么选择这些科学问题-科学假设对

这些候选不是一个总系统的五个宣传词，而是五个可以分别实验的问题：候选 1 研究版本绑定，候选 2 研究证据表示，候选 3 研究组合推理，候选 4 研究成本控制，候选 5 研究故障定位。

选择候选 1 作为首篇主线有三个原因：

1. **变量最少**：只有“是否绑定版本”这一个核心处理因素，因变量是 false completion。
2. **真值最清楚**：产物修改、证据陈旧、错误版本交付都可以程序化注入和判定。
3. **最容易形成闭环**：可以在不实现完整时序 DSL、组合验证或 RL 的情况下完成实验。

候选 5 的科研潜力可能更高，但它需要根因标注、真实失败轨迹和恢复干预；因此更适合作为第二阶段，而不是与候选 1 平权放在同一主假设中。

## 最佳科学问题-科学假设对

**最佳选择**：候选 1，版本绑定验证与错误完成。

### 通俗解释：这项研究到底在防什么

可以把 Agent 想成代替人完成编程或写文档的助手，把 Verifier 想成提交前的检查员，把产物和证据分别想成“交上去的作业”和“检查记录”。现在的风险是：检查员说“这份作业合格”之后，助手又改了文件，或者拿另一份旧检查记录来提交；系统只看到一个 `PASS`，却没有确认这个 `PASS` 仍然对应眼前这份文件，于是可能把错版本当成已完成。

版本绑定验证相当于给每次检查贴上带编号的封条：检查结果明确写着“只对产物版本 A 和证据版本 B 有效”。如果文件或证据后来变成了版本 C，封条就对不上，旧的 `PASS` 自动失效，系统必须要求重新检查。

| 研究术语 | 通俗含义 |
|---|---|
| Agent | 代替人执行任务的软件助手 |
| 产物（artifact） | 助手实际生成的代码、文档或配置文件 |
| 证据（evidence） | 测试结果、日志或评审记录等“为什么可以通过”的依据 |
| 错误完成（false completion） | 实际不合格，却被系统记录为完成 |
| 有效完成（valid completion） | 确实合格，并被系统正确接受 |

**具体例子**：未绑定时，版本 A 的代码通过测试后被改成版本 B，系统仍沿用版本 A 的 `PASS`，可能错误放行版本 B；绑定后，版本 A 的检查结果只认版本 A，代码一改为 B 就会被拦下或触发重验。

**白话版问题**：助手交作业后又改了文件，系统能不能认出“这已经不是刚才检查过的那一份”，从而避免把错版本当成完成？

**白话版假设**：如果把检查结果同时拴在文件版本和检查证据版本上，系统就会少收错版本，同时不会明显拒绝原本正确的提交。

**原因**：

- 科学重要性：错误完成是可观察、可计数且具有实际后果的失败。
- 新颖性：研究重点从“哈希字段设计”转为 Agent 证据漂移和验证结果重放条件下的完成完整性。
- 可证伪性：有明确基线、故障条件、主终点和反证路径。
- 可行性：无需首期完成整个 runtime assurance 栈即可验证。
- 解释力：若有效，可以明确说明错误完成为何被阻断；若无效，也能定位版本绑定机制的边界。

**优化后的科学问题**：当 Agent 在验证通过后修改产物或证据时，版本绑定验证是否比未绑定验证更能防止错误完成？

**优化后的可证伪科学假设**：在预注册的 coding 与文档任务中，面对 PASS 后产物修改、证据陈旧和错误版本交付，版本绑定验证相比未绑定验证能将 false-completion rate 降低至少一个预先规定的最小有意义差异，同时 valid-completion rate 不低于基线的非劣界。

**最关键的反证实验/观察**：

1. 在相同轨迹和验证预算下，随机注入 PASS 后修改、陈旧证据和错误版本交付。
2. 与未绑定 gate、普通 content-addressed provenance 和 post-hoc reverify 做对照。
3. 在至少两个任务族、两个模型和 hidden fault set 上复现，并按域报告置信区间。

## 设计解释与研究边界

本次重写没有把“runtime assurance”作为主假设，是因为它同时包含至少四个不同问题：版本完整性、行动拦截、验证组合和成本调度。把它们合在一起会导致实验无法回答“究竟是哪一个机制产生了效果”。

本次先选“版本绑定验证”，是因为它最接近 BIV 的研究风格：

```text
对象：Agent 的完成验证
机制：验证结果是否绑定对象版本
基线：未绑定验证
结果：false-completion rate
条件：产物/证据发生漂移
反证：无改善、成功率下降或成本不可接受
```

这不是说 State、Verifier、Gate 或 Event Ledger 不重要，而是把它们放回正确位置：它们是实现处理因素和保证实验可复现的基础设施，不是需要同时证明的五个科学贡献。

## 风险与下一步

- 最大不确定性：真实 Agent 轨迹中的版本漂移和错误交付是否足够常见；若只能依靠合成故障，应把结论限定为 controlled benchmark。
- 关键边界：如果系统只能事后拒绝“记录完成”，不能在 action 前拦截真实副作用，就不要把结果宣传为完整 runtime assurance。
- 0–6 个月闭环：冻结一个任务族和故障定义 → 实现版本绑定与自动失效 → 完成回放/兼容测试 → pilot 估计基线故障率 → 预注册正式对照实验。
- 停止标准：最小有意义差异未达到、置信区间不支持改善、成本超过预设上限，或效果只在单一模型/任务出现，则停止扩展为“大架构论文”，改写为工程边界报告或转向候选 5。
- 首期不做：完整 temporal DSL、CompoundVerifier 全家桶、自适应 router、RL、分布式编排、自动 rollback 和“causal optimization”宣传。
