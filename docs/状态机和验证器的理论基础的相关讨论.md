# 状态机和验证器的理论基础的相关讨论

> 本文建立在 [Premium 系统综述](reviews/state-verifier-theory/状态机和验证器的理论基础_review.pdf) 及其 [LaTeX 正文](reviews/state-verifier-theory/状态机和验证器的理论基础_review.tex)、[参考文献](reviews/state-verifier-theory/状态机和验证器的理论基础_参考文献.bib) 的基础上，专门讨论它们为何可能改善 Agent Skill 的自动循环优化，以及哪些问题值得在本项目中优先研究。

## 核心判断

状态机和验证器值得研究，但理由不是它们能把 Agent Skill 变成一个天然可微、凸或快速收敛的系统。更准确的判断是：它们能够把一个只留下终局文本的黑箱，转化为一个带有阶段、证据、约束、干预和回放能力的受控随机过程。这个变化使三个原本混在一起的问题可以分别研究：

- 这一次运行究竟在哪一步失败；
- 改动某一步对最终质量的因果影响有多大；
- 在有限 Token、时间和人工审核预算下，下一次最值得尝试什么。

因此，建议把研究主题命名为 **State–Verifier–Causal Optimization（SVCO）**，中文可称“状态—验证器因果优化”。它不是一个必须一次性实现的平台，而是一套可以逐步验证的理论与实验框架。

## 为什么自动循环优化容易失效

常见循环是“生成 demo → 让 AI 找问题 → AI 修改 → 再生成 demo”。它把生成、评价、归因、决策和停止五件事交给同一条自然语言链路。只要其中一环不可靠，错误就会在下一轮被当成新的事实。

第一，终局奖励过于稀疏。一个文档最终被判定为“不好”，并不能告诉系统是输入解析、检索、推理、格式转换、引用还是交付门禁出了问题。长时序强化学习和多智能体研究都把这种问题称为信用分配困难；自然语言策略还额外具有巨大的离散动作空间和高方差。

第二，自我评价并不等于独立评价。Self-Refine 一类方法说明在受控任务上自我反馈可以有效，但它默认反馈方向可靠、目标稳定且修订不会破坏其它属性。真实 Skill 同时追求事实、格式、证据、安全、成本和用户意图，模型很容易只改善可见表面指标。

第三，循环缺少可靠的停止条件。只要模型还能提出一条新建议，系统就可能继续消耗预算；当质量变化很小、置信区间包含零或风险已经上升时，继续循环反而是负收益。远程写入、发布或批量转换还会带来不可逆副作用，重复尝试不能被视为“更多探索”。

第四，循环结果不可审计。没有 canonical State、产物快照、验证器版本和事件顺序时，失败只能靠重新猜测，无法回答“哪一个版本的哪一步在什么证据上做出了什么判断”。

## 理论模型

### Skill 作为受控随机过程

把一个 Skill 运行表示为：

```text
s0 -- step1(θ1) --> s1 -- step2(θ2) --> ... -- stepk(θk) --> sk
```

其中：

- `si` 是 canonical State、证据快照、阶段不变量和产物摘要的组合；
- `θi` 是该步骤的 Prompt、模型、工具、阈值、重试策略和人工介入规则；
- `Vi` 是挂在阶段或产物上的 Verifier，输出 `pass`、`fail`、`uncertain`、`unchecked`、`error`、`timed_out` 或 `skipped`，并携带独立的 `execution_status` 与证据引用；
- `G` 是 Gate，根据验证结果和授权范围决定继续、等待、人工复核、拒绝或回滚；
- `Y` 是终局质量，`C` 是 Token、时间和人工成本，`R` 是安全风险。

更完整的目标不是最大化一个分数，而是最大化：

\[
J = E[Y] - \lambda C - \kappa R
\]

并且要求 required Verifier 的安全约束始终满足。LLM、网络和工具具有随机性，因此转移应被视为概率分布，而不是假设同一输入必然得到同一状态。

### State 是过程坐标，Verifier 是测量仪器

State 的第一职责是描述“哪个阶段已经成立、允许走向哪里、恢复时从哪里继续”；它不应替代 Skill 的检索、推理或排版逻辑。Verifier 的第一职责是测量一个可陈述的命题，例如“必需文件存在”“引用 key 可定位”“证据没有过期”“写入后回查到目标状态”。

这一区分很重要：Verifier 不是最终真值。它可能误报、漏报，也可能被优化器针对性操纵。因而必须单独测量灵敏度、特异度、校准、调用成本和对任务质量的预测能力。`unchecked` 代表证据不足，不能静默转成 `fail`；`uncertain` 代表证据冲突，通常应进入 `manual_review`。Kernel 还将执行失败和超时保留为 `error`/`timed_out`，避免把工具故障伪装成业务判断。

### 事件账本是因果数据层

一次运行至少应记录：任务与 Skill 版本、随机种子、State 转移、动作配置摘要、产物哈希、Verifier 版本与结果、Gate 决策、人工介入、最终评价和成本。事件序号和证据引用使轨迹可回放，也使“改动某一步后发生了什么”具备时间顺序。

这与本项目已经形成的 `bensz.runtime.state-transition`、`bensz.runtime.event-integrity`、`bensz.runtime.task-completeness`、`bensz.evidence.provenance` 等能力相吻合。下一步不是把更多领域术语搬进 kernel，而是确保这些通用事件字段足以支持统计和因果分析。

## 四层研究议程

### 第一层：测量效度与故障可辨识性

首要问题不是“验证器能否提高分数”，而是：

> 在相同运行预算下，State + Verifier 遥测是否比只看终局结果更准确地定位故障步骤？

可证伪假设是：在注入故障位置已知的盲测中，State + Verifier 的 Top-1、Top-3 定位准确率和概率校准显著优于 endpoint-only。如果没有提升，说明当前状态粒度或验证器设计没有提供有效信息。

建议比较四种信息条件：

1. 只提供终局结果；
2. 提供阶段 State 和 checkpoint；
3. 提供 Verifier 向量；
4. 同时提供 State 与 Verifier。

不仅要测定位准确率，还要测条件互信息、Brier/ECE、误报率、日志开销和人工阅读时间。这样可以回答“哪些遥测值得保留”，而不是盲目追求全量记录。

### 第二层：步骤级因果归因与交互

第二个问题是：

> 对某一步做受控替换、关闭或增强，最终质量、成本和风险分别改变多少？

用潜在结果定义步骤的平均处理效应：

\[
ATE_i = E[Y\mid do(\theta_i=\text{improved})] - E[Y\mid do(\theta_i=\text{baseline})]
\]

二阶交互为：

\[
I_{ij}=Y_{ij}-Y_{i0}-Y_{0j}+Y_{00}
\]

在顺序流程中，后续 State 和 Verifier 是中介变量，不能简单把它们全部作为普通回归特征，否则可能阻断真实因果路径。应采用配对随机种子、按状态顺序随机化、分层混合模型或顺序 g-formula，并区分总效应、直接效应和路径效应。

Shapley 值可以解释多个步骤的整体分摊，但不应替代受控干预。它的计算成本随步骤数指数增长，且依赖候选步骤集合。更实际的做法是先用单步 ATE 筛选，再对 Top-k 步骤做二阶或 fractional-factorial 设计。

### 第三层：预算受限的自动优化

第三个问题是：

> 在固定 Token、时间和人工审核预算下，利用中间遥测的优化器是否比只看终局分数的黑箱循环更快达到目标？

主指标应是达到 `Y ≥ τ` 所需的评估次数、总成本、质量曲线下面积、累积遗憾和风险上界，而不是最后一次运行的最高分。

建议采用三阶段优化器：

1. 因果筛选：对每个步骤做小规模随机化干预，估计效应和不确定度；
2. 交互优化：对高影响步骤和高交互边使用约束、多保真 Bayesian Optimization，局部 Verifier 作为低保真信号，隐藏验证器或人评作为高保真信号；
3. 局部微调：在交互较弱的区域使用坐标下降，保留回滚和停止规则。

只有当 Skill 存在明显的上下文分支时，才进入 contextual bandit 或保守离线 RL。直接把整个自然语言循环交给 RL，通常会遇到组合动作、高方差、奖励劫持和离线评估不可靠的问题。

### 第四层：迁移、安全与主动验证器布置

第四层包含两个值得长期研究的问题。

其一，重要性排序能否迁移？同一 Skill 家族内，步骤的 ATE 或交互图是否稳定；换到另一类 Skill 后，哪些规律失效？建议按任务、Skill 家族、模型版本和时间做嵌套留出，避免把某个基准集的排序误当成普遍规律。

其二，验证器应挂在哪里？把 Verifier 看成传感器，可以研究在固定开销下选择哪些阶段能最大化故障可辨识度。流程割点、高 betweenness 状态和高风险远程 effect 可能是优先布置位置，但这必须通过随机布置、全量布置和结构启发式布置的对照实验验证。

## 对本项目现有设计的具体映射

### Kernel 层

Kernel 应继续只负责协议和可复用能力：解析 Verifier/State 契约、校验 canonical ID、启动规则 helper、归一化结果、冻结证据摘要、应用 Gate、写入事件和重建投影。它不应内置文献综述、病例推理、NSFC 写作或 Sub2API 计费公式。

### Skill Adapter 层

每个 Skill 决定调用哪些 Pack、哪些结果是 required、哪些只是 advisory，以及何时需要人工复核。Adapter 把领域对象转换成统一的 `subject/evidence/requirements`，不把领域术语扩散到 kernel。拔掉 Adapter 后，原 Skill 应仍能运行；挂回后只增加观测、证据和门禁。

### State 层

State 只承载阶段成立条件、允许迁移、恢复点和不变量。不要把“执行检索”“调用模型”“生成 PDF”直接命名成 State；这些是动作或事件。生命周期投影（planned、active、checking、delivering 等）也不应与领域 State 混为一谈。

### Verifier 与 Gate 层

确定性规则优先，语义判断后置。文件范围、Schema、链接、引用 key、构建退出码、事件完整性和密钥脱敏适合做 required 规则；引用真实性、结论适切性和复杂质量评价需要 hybrid 或 human verifier。Kernel 的 Gate 保持保守且区分 required/advisory：无结果时为 `wait`；required 的 `fail`、`error` 或 `timed_out` 为 `reject`；`unchecked` 或 `uncertain` 为 `manual_review`；仅 advisory 失败时为 `allow_with_warnings`；全部通过才为 `allow`，不能用平均分覆盖硬失败。

## 最小可行实验

建议先选择一个四步、低风险、可复现的 Skill：

```text
输入与 Schema → 规划 → 生成 → 验证与交付
```

使用 JSON 抽取、文档转换、Markdown 链接检查三类任务。每一步准备两到三种 mutation，例如漏字段、错误规划、生成噪声、验证器失灵和交付范围越界。每个任务使用配对随机种子，进行单故障和少量双故障注入。

实验分两阶段：

- 定位阶段：比较四种信息条件，盲测故障位置，输出 Top-k、校准、误报和开销；
- 优化阶段：比较终局随机搜索、黑箱 Bayesian Optimization、State-aware 坐标下降和混合方法，记录达到阈值的评估数、Token、人工时间、风险和跨任务表现。

合成 mutation 只用于获得清晰真值，第二阶段必须加入真实历史失败回放。否则很可能得到“合成故障上很容易归因、真实运行中失效”的虚假成功。

## 关于“几何结构”和收敛的谨慎表述

有限状态图带来的确定收益是可达性、路径长度、割点、恢复边界和合法转移约束；它不自动带来凸性。只有在以下性质得到实证支持后，才适合讨论快速收敛：

- 状态图近似无环，或存在可处理的有限回路；
- 每步动作空间有限且转移概率可估计；
- 失败或质量对局部干预近似单调；
- 交互主要是低阶且稀疏的；
- 局部 Verifier 信号与终局质量具有稳定关系；
- 成本和风险可以在路径上近似加总。

满足这些条件时，可以研究动态规划、branch-and-bound、块坐标优化、结构化 Bayesian Optimization 或次模目标下的贪心近似。否则应使用更保守的措辞：状态和验证器帮助结构化实验、减少无效评估并提高样本效率，而不是保证普适快速收敛。

## 主要威胁与控制办法

| 威胁 | 可能表现 | 控制办法 |
|---|---|---|
| Verifier Goodhart | 优化器迎合可见规则，真实质量下降 | 隐藏验证器、人工抽样、冻结验证器版本 |
| 顺序因果混杂 | 把下游连锁失败错误归因给某一步 | 配对干预、总效应/直接效应分解、顺序模型 |
| 状态粒度失衡 | 过粗无法定位，过细成本高且噪声大 | 信息增益—成本曲线、最小充分状态集 |
| 合成故障偏差 | 注入故障比真实失败更干净 | 历史失败回放、按时间和 Skill 留出 |
| 模型与任务漂移 | 重要性排序过期 | 版本、日期、任务难度分层，设置 freshness 阈值 |
| 奖励劫持与风险转移 | 质量略升但人工负担或副作用激增 | 质量—成本—风险 Pareto，人工时间纳入目标 |
| 自动化过度 | 不确定性被循环吞掉，远程动作重复执行 | `unchecked/uncertain` 分支、幂等键、回查和回滚 |

## 优先级建议

### P0：先证明“能看见”

冻结统一的运行事件和 Verifier 结果 Schema，建立四步 Skill 基准，验证 State + Verifier 是否带来可测量的信息增益。这一步不改变生产 Gate，只做旁路观察，避免把测量系统本身的错误混入业务结果。

### P1：再证明“改哪一步有效”

引入单步替换、关闭和增强操作，估计 ATE、交互和不确定性。把用户反馈关联到具体运行、阶段、产物和 Verifier 版本，而不是只记录一条“结果不好”的评论。

### P2：最后证明“能否少试错”

在固定预算和独立留出集上比较因果筛选加多保真优化与终局黑箱循环。只有当质量、成本和风险同时改善时，才把旁路观察升级为 advisory 或 required Gate。

## 最终研究问题

最适合作为本项目首个正式研究问题的是：

> **在有限评估预算下，State–Verifier 遥测能否提高 Agent Skill 的步骤故障定位和因果归因准确率，并使因果筛选加多保真优化比仅依据终局质量的黑箱循环更快、更安全地达到质量—成本目标？**

这个问题足够窄，可以用四步 Skill 和可控 mutation 取得真值；又足够深，能够逐步连接运行时验证、流程挖掘、因果推断、信用分配、Bayesian Optimization 和人机协同。无论结果支持还是否定假设，都会产出可复用结论：哪些 State 值得保留、哪些 Verifier 真正有效、哪些自动化边界必须由人类维护，以及何时“继续循环”已经不再是优化而是风险。
