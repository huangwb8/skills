# 写计划

开始前，简要说明正在使用 `writing-plans` 来整理计划。先读需求、已有材料和项目约束，弄清计划要回答的问题、供谁阅读，以及什么结果能够帮助读者作出决定。修订旧计划时保留有效事实、约束和已确认的决定，按当前选择的风格组织内容。用户指定的输出格式优先。

## 选择风格

用户明确指定了当前支持的风格时，直接采用。其余情况按这份计划的主要目标选择最贴切的风格。尚无专门风格适用时，使用 `general`。

| 风格 | 何时采用 | 写作指南 |
| --- | --- | --- |
| `general`（默认） | 软件实施、缺陷修复、一般变更或其他以交付可用成果为主的任务。即使项目有科研背景，若这份计划主要用于搭建工具、迁移管线或修复代码，也采用此风格。 | [通用计划](styles/general.md) |
| `research` | 计划的主要目标是回答科学问题，需设计实验、比较数据或检验假设。只用已有数据开展的观察性、模拟或探索性分析也适用。 | [科研计划](styles/research.md) |

- 同时包含科研和工程工作时，看用户最终要据此判断什么。若要形成科学结论，按 `research` 组织，必要的工程工作写入实施安排。若要验收软件或流程的交付，按 `general` 组织。用户要求分别交付两份计划时，按各自目标选用风格。
- 用户点名的风格若未收录，简要说明并按目标选用已有风格。若用户明确要求只使用该风格，请用户提供相应规范。
- 每份计划只读取所选风格的完整指南，阅读路径相对于本 `SKILL.md`。维护者新增风格时，在 `styles/` 加一份 Markdown 并在表中说明适用边界及指南路径。每份指南写明自己的写作要求、正文结构和交付前检查。

## 撰写与交付

1. 按选定指南写出完整计划。先用读者熟悉的语言讲清目标和理由，再展开必要的专业细节。区分已知事实、假设和待确认事项，并按任务规模、风险和读者调整深度。
2. 按所选风格自检。确认计划覆盖用户需求，关键步骤的顺序和依赖清楚，完成标准可观察。遇到未确认的前提，交代如何核实，以及它会影响哪些决定。
3. 遵循用户指定的交付位置和项目约定。需落盘且无其他约定时，将正式计划保存到 `docs/plans/YYYY-MM-DD-<主题>.md`。用户要求在对话中讨论或交付时，直接在对话中给出。落盘后说明保存位置，并按用户原有授权决定是否继续执行。

### 公共硬约束

本块由 `docs/templates/skill-common-constraints.md` 统一维护；每个 `SKILL.md` 的 `## 约束` 必须逐字同步本块，不得在副本中改写公共规则。

- 任务需要落盘时，使用唯一的 `./.bensz-api/task-{yyyymmdd-hhmm}-{简短描述}/` 根目录；共享材料放入 `shared/`，Skill 专属材料放入该 Skill 的 `input/`、`output/`、`log/`。
- 正式交付物、源代码和正式计划按项目约定保存，不写入任务工作区；未经授权不覆盖、删除、迁移或远程写入。
- 项目维护变更检查 BAC 可用性并记录需求、AI 产出、工具结果、文件改动和验证摘要；BAC 只做过程审计，不替代署名、责任或合规判断。
- 不记录 API Key、访问令牌、密码、Cookie、环境/凭据文件、私有 Prompt、身份信息、本地用户名、主机名或不必要的大体积原始数据。
- 文件路径必须规范化并限制在授权项目范围内；外部 URL、子进程和网络访问遵循最小权限，防止路径遍历、SSRF 和命令注入。
- Skill 版本唯一记录在自身 `config.yaml:skill_info.version`；公开 API、协议、目录或配置变更同步文档与 `CHANGELOG.md`。
- `bensz-collect-bugs` 是一个 Agent Skill；仅将 Bensz Agent Skill 或 Bensz 基础设施本身的设计缺陷交给它。先脱敏写入 `~/.bensz-skills/bugs/`，当前任务不中断，只有用户明确要求才公开上报，禁止直接修改用户已安装的 Skill 源码。
