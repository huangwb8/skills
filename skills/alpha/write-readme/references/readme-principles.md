# README 原则与技巧（调研提炼）

## 一般原则

1. **读者和任务先于作者结构**：先让新用户成功运行，再解释内部实现。
2. **价值主张具体**：一句话说明对象、动作、受益者和差异点，避免“下一代/革命性”等空泛词。
3. **可执行而非可想象**：命令、环境变量、路径、版本和输出都以仓库事实为准；Quick Start 必须闭环。
4. **渐进披露**：首屏只放决策所需信息；高级配置、设计细节和完整 API 链接到 `docs/`。
5. **证据与诚实**：徽章、截图、性能数字、兼容性和安全承诺必须可定位；不确定就标注。
6. **可导航、可维护**：标题语义清楚，长文档提供目录或 GitHub Outline；使用相对链接和稳定的文件名。
7. **为贡献者降低门槛**：说明如何提问、运行测试、提交 PR、遵守行为准则和许可证。
8. **双语同一契约**：两种语言保持相同标题层级、示例、命令、链接、版本和限制；翻译自然但不改变事实。

## 具体技巧

### 首屏

- 项目名 + 一句可验证定位；必要时加维护状态、许可证和 CI 徽章。
- 有真实 UI/输出时放一张有替代文本的截图或 GIF；没有就不要硬塞视觉材料。
- 在首屏给出 `Quick Start` 锚点和语言切换链接。

### Quick Start

- 用“前置条件 → 安装 → 配置 → 运行 → 预期结果”五步闭环。
- 命令可复制，代码块前用一句话解释用途；示例使用占位符而不是秘密。
- 对多个安装路径分流：本地开发、Docker、云部署或宿主插件，不要混写成一条含糊命令。

### 示例与导航

- 先放最小成功案例，再放 1–3 个高价值场景；每个场景说明输入、动作和结果。
- 用表格呈现“需求 → 推荐路径/配置”；用链接把长教程、API 参考和设计文档分层。
- 目录只在文档较长或层级复杂时提供；GitHub 已自动生成 Outline。

### 可信度与安全

- 说明支持的 Python/Node/OS/数据库版本和已验证矩阵，不把开发环境默认为生产环境。
- 明确外部服务、费用、数据收集、模型/数据许可、默认监听地址和凭据处理。
- 性能数字附测试条件或链接；没有基准就写“未提供基准”，不要用星级代替证据。

### 维护

- README 只描述当前行为；路线图、新闻和版本历史分别链接到 Releases/CHANGELOG。
- 当命令或目录变化时，同步两种语言并运行 `check_readme_pair.py`。
- 让 README、安装脚本、CI 和配置文件共享真实入口；不要复制易变默认值到多处。

## 项目类型分化

应分化，但只分化高价值的首屏和 Quick Start；通用的限制、支持、贡献和许可证保持一致。

| 类型 | 必须回答的问题 | 常见误区 |
|---|---|---|
| 库/SDK | 如何安装？最小 API 是什么？支持哪些版本？ | 只列 API 名称，不给可运行示例 |
| CLI/服务 | 如何启动？配置/端口/健康检查是什么？ | 把开发命令误写成生产部署 |
| Web/桌面 | 用户能看到什么？如何体验/部署？ | 大图无 alt、Demo 失效、缺少无图 fallback |
| 数据/ML | 数据和权重从哪来？如何复现？资源/许可是什么？ | 只给训练命令，隐去数据条款和硬件需求 |
| Agent Skill | 何时触发？输入输出是什么？如何安装宿主？ | 把内部 `SKILL.md` 协议全文复制给使用者 |

## 常见反模式

- 只有口号，没有安装和运行路径。
- 徽章/截图/链接来自模板但目标文件不存在。
- Quick Start 省略依赖、环境变量或数据库初始化。
- 中英文一边更新，另一边缺章节、旧命令或不同版本。
- 把未经测试的性能、兼容性和安全结论写成保证。
- 为了“完整”复制数百行 API 或源码，读者反而找不到入口。
